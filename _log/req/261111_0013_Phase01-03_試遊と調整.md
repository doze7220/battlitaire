## 【実装要件】
01-02 までで、段取り（めくる・置く・捨てる・放つ）→ 攻防 → 次のフェーズを決着まで遊べる。今回は、発注者のテストプレイで出たルールの調整を入れる。「置けずに捨てる場面」を減らすための3つ（1 の後に 7、束の移し替え、手札）と、敵の調整2つ（HP、防御の行動）である。演出（Phase 2）・敵の種類（Phase 3）は作らない。

*   **要件1: 1 の後に 7（数字の一周）**
    *  列の一番上のカードが 1 のとき、その列に 7 を置ける（スートは問わない）。ほかの置ける条件（空いた列、一番上の数字がちょうど1つ上）はそのまま。
    *  「1 の次は 7」の関係は、数字の最小値・最大値の設定値（`minRank`・`maxRank`）から決める（1・7 を直書きしない）。一周を許すかどうかを設定値で切り替えられるようにする（初期値: 許す）。
    *  この「置ける並び」の判定（あるカードの上に別のカードを置けるか）はルール層の1か所に置き、山札から置く・手札から置く・束を移す（要件2）のすべてで同じ判定を使う。
    *  **列の長さに上限は設けない。** 一周により列は 7 枚を超えて積める（実際に起きるのはかなりまれ）。今の `Game.maxColumnLength`（列に積める最大の枚数）の扱いは計画で見直すこと。

*   **要件2: 列が長いときの表示**
    *  列の領域に今までどおりの重ね幅で収まる枚数までは、今と同じ見た目で描く。
    *  収まらないほど長くなったときは、**上から3枚（一番上のカードとその下2枚）だけを今までどおりの重ね幅で描き**、それより下のカードは列の領域に収まるまで重ね幅を詰めてよい（詰めた部分の数字が見えなくなってもよい）。列は列の領域からはみ出さない。
    *  詰めた部分のカードの当たり判定（要件3の束を選ぶ操作）は、描いた位置と合っていればよい（押しにくくてもよい）。

*   **要件3: 束の移し替え**
    *  列の上にある、置ける並び（要件1の判定で、下のカードの上に次のカードを置ける関係）で続いた束を、その束の一番下のカードを置ける別の列へ、1回の操作でまとめて移せる。束の並びは崩さない。スートは問わない。空いた列へも移せる。移すと行動回数が1減る。1枚だけ（列の一番上のカード1枚）でも束として移せる。
    *  例: 列A が 5・3・2・1・7・6（下から）なら、「3・2・1・7・6」「2・1・7・6」「1・7・6」「7・6」「6」はそれぞれ束として選べる。「5・3・2・1・7・6」は 5 の上に 3 を置けないので選べない。「3・2・1・7・6」は、一番下の 3 を置ける列（一番上が 4 の列、または空いた列）へ移せる。
    *  **操作**: 山札・手札を選んでいない状態で、列の中のカードをタップすると、そのカードから一番上までを束として選ぶ（束になっていないカードをタップしたときは選ばない）。選んでいる束が分かるように描く（例: 枠で囲む）。続けて移す先の列をタップすると移る。移せる列が分かるように描く（今の「置ける列」の目印と同じ考え方）。同じ束（同じ列のカード）をもう一度タップする、移せない場所をタップする、などで選択を外す。行動が0のときは選べない。
    *  移せるかの判定・移す操作はルール層に置く（束の範囲が置ける並びか、移す先に一番下のカードを置けるか、移す先が元の列と違うか、行動が残っているか、段取り中か）。移す操作も、ほかの操作と同じく「何が起きたか」（元の列、移した先の列、移したカード、残り行動回数など）を返す。
    *  放つ操作（列ごとの「放つ」ボタン）はそのまま変えない。

*   **要件4: 手札**
    *  手札の枠を持つ。枠の数は設定値（初期値1）。手札は画面に表示され、空いている枠とカードの入った枠が分かる。枠の数が設定で2以上になっても表示が崩れない作りにする（初期値1で見た目を整えればよい）。
    *  **入れる**: 山札の一番上のカードを、列に置く代わりに手札の空いている枠に入れられる。置ける列があっても入れられる。**入れると行動回数が1減る。** 手札がすべて埋まっていれば入れられない。入れた後、山札の補充は置くときと同じく行う。
    *  **置く**: 手札のカードを、置ける列（要件1の判定）に置ける。**置くと行動回数が1減る。** 行動が0なら置けない。
    *  **捨てる**: めくったカードがどの列にも置けないときに捨てられる、という今の決まりは変えない（手札が空いていても、捨てるか手札に入れるかをプレイヤーが選べる）。手札のカードを捨てる操作は作らない。
    *  手札のカードは放つ束に入らない（放つのは列だけ）。束の移し替えの移す先・移す元にもならない。
    *  手札はフェーズをまたいで残る。新しいゲームでは空で始まる。
    *  **操作**: 山札を選んでいるときに空いている手札の枠をタップすると、その山札の一番上のカードが手札に入る。カードの入った手札の枠をタップすると、そのカードを選ぶ（山札の選択は外れる）。手札のカードを選んでいるときに置ける列をタップすると置く。手札を選んでいるときは置ける列が分かるように描く（山札を選んだときと同じ目印）。同じ枠をもう一度タップする、置けない場所をタップする、で選択を外す。山札を選んでいるときは、手札の空いている枠に入れられることが分かるように描く。
    *  入れられるか・置けるかの判定、入れる・置く操作はルール層に置き、「何が起きたか」を返す。

*   **要件5: 敵の HP**
    *  敵の最大 HP の設定値を 50 にする（城の HP 50、敵の攻撃 10 はそのまま）。

*   **要件6: 敵の防御の行動**
    *  敵の行動に「防御」を足す。フェーズの頭（ゲーム開始時のフェーズ1を含む）に、敵の次の行動として「攻撃 10」か「防御 15」のどちらかを予告する。
    *  どちらにするかは、ルール層に渡された乱数で決める。攻撃の重み 2・防御の重み 1（攻撃 2/3、防御 1/3）とする。行動の種類ごとの量と重みは設定のファイルにまとめ、書き換えで変えられるようにする。`Math.random` は使わない。
    *  **防御のフェーズの攻防**: 敵は攻撃しない（城は被害を受けない。自軍の防御のゲージは使われずに消える）。自軍の攻撃のゲージが敵の防御と相殺し（相殺する量 = 攻撃と敵の防御の小さい方）、残りが敵の HP を減らす。敵の防御の余りは消える（持ち越さない）。回復はこれまでどおり。計算の順は「敵の行動 → （攻撃なら）防御で相殺 → 城の被害 → 負けの判定 → （防御なら）敵の防御で相殺 → 敵へのダメージ → 勝ちの判定 → 回復」とする。
    *  攻防の出来事の並びに、敵の防御（量）と、敵の防御で相殺した量を出す。量が0の相殺を並びに入れない、という 01-02 の決まりは保つ。結果の窓に、例えば「敵の防御 15」「敵の防御で相殺 15」「敵に与えたダメージ 21」と出る。
    *  画面の敵の予告は「防御 15」のように表示する。
    *  01-02 で敵の行動を「攻撃」1種類に限っていた作り（`combatants.js` の `planEnemyAction`、`battle.js` の入力 `enemyAttack`、`battleText.js` の `ACTION_LABELS` など）を、種類と量で分かれる形に広げる。敵の回復・力溜め、敵の種類・特殊行動の仕組みは作らない。

*   **要件7: 調整値**
    *  一周を許すか、手札の枠の数（1）、敵の最大 HP（50）、敵の行動の種類ごとの量と重み（攻撃 10・重み 2、防御 15・重み 1）は、ルール層の設定のファイル（`js/rules/config.js`）にまとめる。ほかのファイルに直書きしない。
    *  見える枚数と倍率の数値は、発注者が設定のファイルを書き換えて試す（今回は値を変えない）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。あわせて、`PROJECT_ARCHITECTURE.md` 4章の `piles.js` の説明にある「捨て札の生成」（捨て札を作るのは `Game.js`）の文言を直す。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **ルールと画面の分離** : 置ける並びの判定、束の範囲と移せるかの判定、手札に入れられるか・置けるかの判定、敵の行動の決定、攻防の計算は、すべてルール層（`js/rules/`）に書く。シーン・描画は、ルール層の問い合わせ・状態・出来事の並びを読むことと、ルール層の操作を呼ぶことだけを行う。どの山札・手札・束を選んでいるか（選択の状態）はシーンが持つ（01-01 の `selectedDeck` と同じ考え方）。出来事・敵の行動を表示文字に直すのは `js/view/` の仕事。
*   **ルール層の独立** : `js/rules/` は `oz` も `js/` のほかのフォルダも import しない。Canvas・DOM・音・時間・`Math.random` に触れない。乱数は `Game` に渡された関数を使う。
*   **ルール層の肥大化を避ける** : `js/rules/Game.js` はすでに約310行ある。置ける並び・束の判定は `columns.js`、手札の状態と判定、敵の行動の決定（`combatants.js`）、攻防の計算（`battle.js`）のように、責務ごとのファイルに純粋関数として置き、`Game.js` には状態の取りまとめと操作・問い合わせの入口だけを置く。それでも `Game.js` が大きくなりすぎる場合（目安: 400行を超える）は、入口を責務ごとに分ける設計（例: 操作の結果の型定義の別ファイル化など）を計画で示すこと。
*   **シーンの肥大化を避ける** : `js/scenes/BoardScene.js` の入力処理は、選ぶもの（山札・手札・束）が増えて分岐が増える。選択の状態の扱い（何を選んでいるか、次のタップで何をするか）を分かりやすく保ち、必要なら責務ごとに別ファイル（`js/scenes/` 内）に分けることを検討する。ルールの判定を書き写さない。
*   **先回り実装の禁止** : 攻防の演出、効果音、敵の種類・特殊行動、敵の回復・力溜め、撃退数、次の敵の出現、余った防御・攻撃の持ち越し、見える枚数を2枚にする、「下なら置ける」、捨てるときの得、手札のカードを捨てる操作、手札から放つ、ドラッグでの操作、列の長さの上限は作らない。
*   **エンジンの使い方** : 入力は `Scene` の `onPointer` で受け、当たり判定は `js/view/layout.js` の `hitTest` で行う（手札の枠、列の中のカードの当たりを足す。`Engine.addButton` は使わない）。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない。必要な機能がエンジンにないときは、回避策を書かずにRESに記録して作業を止める。
*   **配置** : 手札の枠を足しても、既存の表示（山札・列・捨て札・ゲージ・行動回数・放つボタン・行動終了・状況の帯）と重ならず、1280×720 の中に収まる配置にする。
*   **既存ファイル** : 変更してよい既存ファイルは `js/rules/config.js`、`js/rules/Game.js`、`js/rules/columns.js`、`js/rules/combatants.js`、`js/rules/battle.js`、`js/rules/piles.js`（先頭の責務定義から「捨て札の生成」に当たる文言を直す場合のみ）、`js/scenes/BoardScene.js`、`js/view/layout.js`、`js/view/boardView.js`、`js/view/columnView.js`、`js/view/cardView.js`、`js/view/deckView.js`、`js/view/hudView.js`、`js/view/statusView.js`、`js/view/battleText.js` とする。そのほかの既存ファイル（`js/main.js`・`js/scenes/BootScene.js`・`js/scenes/MenuScene.js`・`js/scenes/BattleResultScene.js`・`js/ui/`・そのほかの `js/rules/`・`js/view/` のファイル）は変更しない。変更が必要だと分かった場合は、計画の中で理由を書いて対象に加えるのではなく、RESの懸念事項に記して発注者の判断を仰ぐこと。新しいファイルは `js/rules/`・`js/scenes/`・`js/view/` に作ってよい。
*   **1ファイル1責務** : 手札の描画、束の選択の目印の描画のように、描画も責務ごとにファイルを分けることを検討する。既存ファイルの先頭の責務定義から外れる処理を足さない。
