## 【実装要件】
02-03 までで、段取りの操作はカードの動きで、攻防は兵の動きで見えるが、音はまったく鳴らない。今回は、段取りの操作と攻防の出来事に効果音（SE）を付ける。音のファイルは、発注者が用意するのではなく、仮の音を生成スクリプトで作って `assets/sounds/` に置く（あとで同じ名前のファイルを差し替えれば本番の音になる）。BGM・音の入り切り（ミュート）の操作は作らない。

*   **要件1: 段取りの操作で鳴る**
    *  次の操作で、それぞれの効果音が鳴る。鳴らすのは、操作がルール層で成り立った（状態が変わった）ときだけで、置けない場所を押した・何も選んでいない、などで何も起きなかったときは鳴らさない。
        *  **めくる**: 山札の一番上をめくった（選んだ）とき。
        *  **置く**: めくったカードを列に置いたとき、手札に入れたとき、手札から列に置いたとき、束を移し替えたとき（同じ音でよい）。
        *  **捨てる**: めくったカードを置けずに捨て札へ捨てたとき。
        *  **放つ**: 列の「放つ」を押して束を放ったとき。
        *  **行動終了**: 「行動終了」を押して攻防に入ったとき。
    *  鳴る時期は、操作を受けた時点（タップした時点）でよい。カードの動きの到着に合わせなくてよい（ただし要件3の連鎖の音を除く）。
    *  1つの操作で複数の結果が起きる場合（例: めくったカードの置き先の操作で、置くと同時に山札が補充される など）でも、1回の操作で鳴る音は、その操作を表す1つでよい。どの操作でどの音を鳴らすかは計画で一覧にすること。

*   **要件2: 攻防の出来事で鳴る**
    *  攻防の演出（`BattleShowScene`）で、次の段が始まる（または当たる）時点で、それぞれの効果音が鳴る。演出の見た目と合うように、段が始まった時点か、兵がぶつかった・当たった時点のどちらで鳴らすかは計画で決めてよい。
        *  **相殺**: 守備兵と敵兵の相殺（出来事 `block`）、兵士と敵の守りの相殺（出来事 `enemyBlock`）。同じ音でよい。
        *  **城へのダメージ**（出来事 `castleDamage`）
        *  **敵へのダメージ**（出来事 `enemyDamage`）
        *  **修理**（出来事 `heal`）
        *  **勝ち**（出来事 `win`）・**負け**（出来事 `lose`）: 決着の表示が出たとき。別々の音にする。
    *  並びにない出来事（量が0で並びに入らなかったもの）の段では鳴らない。1つの段で鳴るのは1回でよい（兵の人数分鳴らさない）。
    *  **早送り**: 音はエンジンの仕様で `Engine.timeScale` の影響を受けず実時間で鳴るので、3倍速のときは音が詰まって重なってよい。音を速くする処理は書かない。
    *  **スキップ**: 押したとき、飛ばした段の音はまとめて鳴らさない。決着した場合は、勝ち・負けの音は鳴る。

*   **要件3: 放った束の連鎖の音（音程の上昇は保留）**
    *  束を放ったとき、放ったカードの枚数の分だけ、1枚ごとに短い「連鎖」の音が、少しずつずれて順に鳴る（カードが捨て札へ動いていくのに合わせる。ずらし方は計画で決めてよい）。
    *  DIR の要件「連続の枚数が増えるほど音程が上がる」は、エンジン（`oz/ENGINE_API.md` 21章）に音程（再生速度）の指定がないため、**今回は作らない**。発注者の判断で、OZ Engine へ連絡票を出し、エンジンに音程の指定が入ってから別の作業で足す。今回は、どの枚も同じ音程で鳴る。
    *  音程違いのファイルを用意する・音を鳴らす別の仕組み（Web Audio API を直接使うなど）を作る、といったゲーム側の回避策は書かない（憲法「エンジンの不足への対応」）。
    *  後で音程を足すときに直す場所が分かるよう、連鎖の音を鳴らす箇所で「何枚目か」が分かる作りにしておくことは構わない（ただし音程を変える処理・音程違いの名前は作らない）。

*   **要件4: 仮の音の生成**
    *  上の要件で使う効果音（めくる・置く・捨てる・放つ・連鎖・行動終了・相殺・城へのダメージ・敵へのダメージ・修理・勝ち・負け。音の数と名前は計画で一覧にすること）を、生成スクリプトで作る。
    *  生成スクリプトは Node.js で動き、外部のパッケージを使わない（`npm install` をしない）。1回の実行で全部の音のファイルを `assets/sounds/` に書き出す。置き場所は `tools/`（新しく作るフォルダ。ゲームの実行時には読まない）とし、実行のしかたをスクリプトの先頭のコメントに書く。
    *  音は短い合成音（正弦波・矩形波・ノイズなどと音量の減衰の組み合わせ）でよい。1つ 1 秒以下（勝ち・負けは 2 秒以下）。種類ごとに聞き分けられる程度に違えばよい。ファイル形式はブラウザで鳴らせる WAV（16bit・モノラル）とする。
    *  生成した音のファイルは `assets/sounds/` に置いてコミットする（ゲームの実行時に生成スクリプトは使わない）。
    *  スクリプトの実行と、書き出されたファイルの確認（数・名前）は、実装AIが行ってよい。

*   **要件5: 音の読み込みと設定は1か所**
    *  音の名前とファイルのパスの一覧、効果音の音量（`Sound.seVolume` の初期値）は、設定の1か所（新しく作るファイル。置き場所は計画で決める）にまとめ、そこを書き換えるだけで変えられる。音のファイルを本番の音に差し替えるときは、ファイルを同じ名前で置き換えるか、この一覧のパスを書き換えるだけで済む。
    *  音は、盤面のシーンに入る前に `Assets.load` で読み込む。どこで読み込むか（`js/main.js` の起動時の準備、タイトルの画面の前後など）は、`oz/ENGINE_API.md` 20〜21章（最初の入力より前の音の扱い、ロードの完了）に従って計画で決める。読み込みに失敗した音は、エンジンの仕様どおりエラーにならず鳴らないだけでよい。
    *  タイトルの画面（「TAP SCREEN」）の見た目と操作は変えない。

*   **要件6: ゲームの結果は変わらない**
    *  音は見せ方の一部であり、鳴らす・鳴らさないでルール層の状態・操作の結果・演出の進み方が変わらない。

## 【計画書に必ず含めるべきタスクごとの作業】

*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する（音の設定のファイル・`tools/` の追加、フォルダ構成と 4章の責務の表（音を鳴らしてよい場所）、3章の起動の流れでの音の読み込み、作成済みのファイルの表の更新など）。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **ルール層は変えない** : `js/rules/` のファイルは変更しない。ルール層は音に触れない（憲法）。どの操作が成り立ったか・何枚放ったかは、ルール層の操作の戻り値（操作の結果）から読む。足りないと分かった場合は、ルール層を変える計画を書くのではなく、RESの懸念事項に記して発注者の判断を仰ぐこと。
*   **音を鳴らす場所** : `Sound.playSe` を呼ぶのはシーン（`js/scenes/`）、またはシーンから呼ばれる音のための小さな補助のモジュールとする。`js/anim/`・`js/view/`・`js/rules/` は `Sound` を import しない（`anim` は見た目の値と時間を作るだけ、`view` は描くだけ、という責務を保つ）。演出の時間に合わせて鳴らす音（攻防の段、連鎖の音）は、`anim` が「いつ・何が起きたか」（段が変わった、何枚目のカードが動き始めた・着いた など）を見た目の値や問い合わせとして答え、シーンがそれを見て鳴らす形にする。`anim` に音の名前を持たせるかどうかは、責務の線引きとして計画で決めて理由を書くこと。
*   **1回だけ鳴らす** : 時間で鳴らす音は、1つの出来事につき1回だけ鳴る（`update` が呼ばれるたびに鳴り続けない。早送りで1回の `update` に複数の出来事がまたがっても取りこぼさない）。`draw` の中では鳴らさない（`draw` でシーンの状態を変えない。`oz/ENGINE_API.md` 13章）。
*   **先回り実装の禁止** : 連鎖の音程の上昇（要件3）、BGM、音の入り切り・音量の操作の画面、早送り・スキップのボタンの押した音、敵の種類ごとの音は作らない。カードの動き・兵の動きの見た目と速さは変えない。
*   **エンジンの使い方** : 音は `Assets.load` の `sounds` と `Sound.playSe`・`Sound.seVolume` だけで扱う（`oz/ENGINE_API.md` 20〜21章）。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext`・`setTimeout`・`setInterval`・`AudioContext`・`Audio` を書かない。必要な機能がエンジンにないときは、回避策を書かずにRESに記録して作業を止める。
*   **既存ファイル** : 変更してよい既存ファイルは `js/main.js`、`js/scenes/BoardScene.js`、`js/scenes/BattleShowScene.js`、`js/anim/boardAnimator.js`・`js/anim/planningMotion.js`・`js/anim/battleDirector.js`（音を鳴らす時期をシーンが知るための問い合わせ・見た目の値を足すだけ。動きの見た目と速さは変えない）とする。`js/rules/`、`js/scenes/boardSelection.js`、`js/scenes/BootScene.js`、`js/scenes/MenuScene.js`、`js/ui/`、`js/view/`、`js/anim/` のそのほかの既存ファイル、`index.html`、`oz/` は変更しない。変更が必要だと分かった場合は、計画の中で理由を書いて対象に加えるのではなく、RESの懸念事項に記して発注者の判断を仰ぐこと。新しいファイルは `js/scenes/`・`js/anim/`、音の設定のための新しいファイル（`js/` の下。新しいフォルダを作る場合は理由を書く）、`tools/`、`assets/sounds/` に作ってよい。
*   **1ファイル1責務** : 音の名前とパスの一覧・音量の設定、どの操作・出来事でどの音を鳴らすかの対応、生成スクリプトを、既存のシーンや演出のファイルに詰め込まない。各ファイルの先頭に責務定義を書く。
*   **検証** : 音が鳴るかの確認はテストプレイで発注者が行う。実装AIは、生成スクリプトの実行と、書き出したファイルの数・名前が設定の一覧と一致することの確認までを行う。
