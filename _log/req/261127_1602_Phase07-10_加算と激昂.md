## 【実装要件】
ステージの加算（HP・防御）を下げ、1体との戦闘が長引いたときの**疲弊をやめて激昂に置き換える**。あわせて、戦闘の BGM をどの敵でも同じにし、激昂で切り替える。
* **狙い**: 発注者の試遊で「防御をしていれば負けないが、勝てもしない」戦闘が長引いた。原因は、HP と防御が両方伸びることと、守りに行動を回すぶん攻撃が減ることの重なり。疲弊は守りを固めて粘るほど得になり、逆向きなのでやめる。長く戦わせるのではなく、攻撃の痛さで「死ぬか倒すか」を突きつける。

**決まりごと**
* **数値の置き場所**: 数値はすべて設定（ルールは `js/rules/config.js`、音は `js/audio/soundConfig.js`）に置く。下の値は初期値で、発注者が試すたびに変える。
* **呼び名**: 画面の呼び名は TURN・ターン（内部の名前は phase）。「戦闘のターン」は、その敵との戦闘で何ターン目か（`battleTurn`。敵が替わると 1 に戻る。盤面の TURN の番号）。
* **変えないもの**: 攻撃の加算、敵の行動の型・周期・確率・防御の抽選、攻防の計算、強化、スコア、★の並び、1ターンの流れ、ほかの機能。

### 今の作り（現場設計で確かめたこと）
* **加算**: `stageBonus.js` の `stageBonusOf` が、設定 `stageGrowth`（`stagesPerChapter: 5`、4つの章）から加算量を求める。
  * ステージ 1 は加算 0 で、ステージ 2 から1ステージごとに、その章の量を足す（最後の章の量はそれより先でも使う）。
  * 章の量: HP の百分率 5・7・9・12、攻撃 0.5・0.75・1・1.25、防御 0.25・0.25・0.5・0.5。攻撃・防御は合計の端数を切り捨てる。
  * 最大 HP は `grownMaxHp`（元の HP ×（100 + 百分率）/ 100 の切り捨て。1体のポイントを持つ敵はその倍数に切り捨て）。
* **疲弊**: 設定 `fatigue`（`{ fromTurn: 21, defenseRate: 0.5 }`・`{ fromTurn: 26, defenseRate: 0 }`）。
  * 予告の `baseDefense`（疲弊の前）と `defense`（疲弊の後）を持ち、`refreshIntent` がターンの番号から `defense` を数え直す（DEBUG のターンの番号の変更で使う）。
  * 疲弊しているかは `Game.isEnemyFatigued`。敵の名前の行の右詰め（HP ゲージの下。`layout.js` の `topGauges.fatigue`）に「疲弊」と出る（`topGaugeView.js`）。
* **予告の攻撃の量**: `enemyIntent.js` の `createIntent` が、行動の量に攻撃の加算（1体のポイントの倍数に切り捨て）を足す（振りかぶり・吸い込む・防御だけは 0 のまま）。
  * スライムの子スライムの数（`minions`）は予告の攻撃の量とは別に持つ（`enemySplit.js`）。猪の親子のうり坊の攻撃は、ふつうの攻撃の予告。
* **戦闘のターン**: `Game.advancePhase` で、敵が替わらなければ `battleTurn` を 1 増やしてから予告を決める（`planIntent`）。中断データは `battleTurn` を持つ（版 8）。
* **BGM**: `soundConfig.js` の `STAGE_BGM` が敵ごとに曲を持つ（ドラゴンだけ `dragon`、ほかは `stage`）。`bgmCues.js` の `playStageBgm(typeId)` を、`boardFlow.js` がステージの始まり・再開の最初のターン・DEBUG で敵が替わったときに呼ぶ。城か敵の HP が 0 になると止める（`stopBgmOnKnockout`）。
* **DEBUG**: ターンの番号のスライダー（`debugTab.js` の `TURN_SLIDER`。1〜30）で `setBattleTurn` を呼び、予告の防御を数え直す。ルールの値（`debugRuleItems.js`）は 66 個で、疲弊（`fatigue`）とステージの加算（`stageGrowth`）は項目にない。

### 要件1: ステージの加算を改める（ルール）
* **HP**: 元の HP に「1ステージごとに +2%」を足す。章で変えない。
  * 数え方は今のまま（発注者の決定）: ステージ 1 は加算 0、ステージ 2 から足す。ステージ 10 は +18%、20 は +38%、30 は +58%。
* **防御**: 全章で1ステージごとに +0.25（合計の端数の切り捨ては今のまま）。ステージ 10 は +2、20 は +4、30 は +7。
* **攻撃**: 変えない（今の章ごとの 0.5・0.75・1・1.25 のまま）。
* 設定の形は計画で決める（今の章の形のまま値だけ変えてもよい）。`stageBonusOf` を呼ぶ側（最大 HP・予告の加算）の作りは変えない。

### 要件2: 疲弊をやめて激昂にする（ルール）
* **疲弊をやめる**: 防御が減る決まり（設定 `fatigue`・`fatiguedDefense`・`isFatigued`・`isEnemyFatigued`）と「疲弊」の表示をなくし、使わなくなる関数・設定・予告の項目（疲弊の前の防御 `baseDefense` など）は残さず整理する（ほかから使われていないことを確かめる）。21 ターン目以降も、敵の防御はふつうどおり。
* **激昂の決まり**（どの敵も同じ。敵の識別子で分岐しない）:
  * 戦闘のターンが 15 までは、ふだんどおり戦う。
  * 16 ターン目に入ると、敵が激昂する。
  * 激昂した敵の攻撃の量には倍率がかかる: 16 ターン目に ×1.2、17 ターン目に ×1.4 …と、1ターンごとに 0.2 ずつ足す（上限なし）。
  * 倍率は百分率の整数で持ち（初期値: 始まるターン 16・上がる量 20%）、量の計算も整数で行う（浮動小数の誤差で数字が変わらない形）。始まるターンと上がる量は設定で変えられる。
  * **端数**（発注者の決定）: 倍率をかけた量は切り捨て（例: 7 × 1.2 = 8.4 → 8、3 × 1.2 = 3.6 → 3）。1体のポイントを持つ敵（オーガなど）は、その倍数に切り捨てる。
  * **かける量**: 予告の攻撃の量（ステージの加算を足した後の、最後の量）にかける。振りかぶり・吸い込む・防御だけなど、攻撃の量が 0 の行動は 0 のまま。
  * **かけないもの**: 防御の量・行動の型・周期・確率・攻撃の直後の回復・札を燃やす数は変えない。スライムの子スライムの数にもかけない（発注者の決定。倍率はスライム自身の攻撃の量だけ）。
  * 予告の攻撃の量は、倍率をかけた後の数字になる（予告の札・ターンの始まりの文字・攻防の量がすべて同じ数字）。
  * 次の敵には持ち越さない（敵が替わると戦闘のターンは 1 に戻り、激昂していない）。
* 激昂しているか・今の倍率は、戦闘のターンと設定から決まる値としてルール層で答える（`Game` に読む口を置く。置き場所は計画で決める）。
* DEBUG でターンの番号を変えたときに予告の攻撃の量を数え直せるように、倍率の前の量を予告に持つかどうかは計画で決める。

### 要件3: 表示（画面）
* 激昂している間、敵の名前の行の右詰め（今の「疲弊」の場所。HP ゲージの下）に「激昂 ⚔×1.2」のように今の倍率を出す（倍率は小数第1位まで。例: ×1.2・×2.0）。
* 文字の色・大きさは今の「疲弊」に合わせた初期値でよい（試遊で決め直す値として定数に置く）。「⚔」の字が PC・スマホで出るかは目視で確かめる（出ないときの扱いは RES の懸念事項に書く）。
* 激昂に入るターンの特別な合図（「激昂！」の文字や演出）は出さない（発注者の決定。表示・予告の数字・BGM で伝える。演出は P10）。
* 激昂までの予告（あと N ターン）は出さない。

### 要件4: BGM（音）
* **戦闘の BGM はどの敵でも同じ曲**（今の `stage`）にする。ドラゴン戦だけの曲をやめる。
* **敵が激昂すると BGM が激昂の曲に変わる**。激昂の曲には、今のドラゴン戦の曲（`assets/bgm/dragon.mp3`）を使う。
  * 激昂に入るターン（16 ターン目の始まり。TURN の表示のとき）に切り替える。クロスフェードの長さなどは `soundConfig.js` の初期値として置く。
  * 敵が替わる（次のステージの始まり）と、ふだんの曲に戻る。
  * 中断から再開したとき・DEBUG で敵を替えた・ターンの番号を変えたときも、そのときの激昂の状態に合う曲が流れる。
  * 城か敵の HP が 0 になったときに止める決まりは今のまま。
* 曲を決めるのは今と同じく `bgmCues.js` の1か所。激昂しているかはルール層の答えを読むだけにする。敵ごとの曲の表（`STAGE_BGM`）を残すか、1曲にまとめるかは計画で決める（敵の識別子で分岐する if は書かない）。
* `assets/bgm/` のファイルは変えない（名前も変えない）。

### 要件5: 中断データ
* 激昂は戦闘のターンから決まるので、今の `battleTurn` から求める。
* 予告の形が変わる（疲弊の前の防御をなくす・倍率の前の量を足すなど）ときは、`SUSPEND_VERSION` を 9 に上げ、RES に理由を書く（版 8 の途中のゲームは一度だけ捨てられる）。形が変わらなければ版は上げない。
* 激昂している途中で閉じて再開しても、同じ倍率・同じ予告・同じ曲で続く。

### 要件6: DEBUG タブ
* **ターンの番号**: 今のスライダーで、激昂を試せるようにする。
  * 番号を変えると、今の予告の攻撃の量を倍率に合わせて数え直す（乱数は呼ばない）。激昂の表示と BGM も合わせて変わる。
  * スライダーの範囲は、激昂の始まるターンを動かしても試せる大きさにする（計画で決める）。
* **ルールの値**（発注者の決定）: 激昂の「始まるターン」と「上がる量」の2本をルールの値のスライダーに出す（「元に戻す」で戻る）。
  * 範囲・刻みは計画で決める（上がる量は刻み 10%（0.1）にすると表示の倍率が小数第1位に収まる）。
  * 変えた値の効く時期の表示は、今のルールの値の決まり（`debugRules.js` の `ruleTiming`）に合わせる。

### 要件7: 古い説明コメントの直し（発注者の決定。動きは変えない）

### 要件8: 確かめ（一時スクリプトで行い、結果を RES に書く）
* **加算**: ステージ 1〜200 で、HP の百分率・攻撃・防御の加算が要件1のとおり（ステージ 10・20・30 の値を書く）。攻撃の加算は変更前と同じ。
* **激昂の倍率**: 戦闘のターン 1〜40 で、倍率と量が要件2のとおり（15 までは変わらない、16 で ×1.2、17 で ×1.4、端数の切り捨て、1体のポイントの倍数、攻撃 0 の行動は 0、防御は変わらない、子スライムの数は変わらない）。どの敵でも同じ決まりになる。
* **疲弊がない**: 21 ターン目以降も防御の量が変わらない。
* **持ち越さない**: 激昂した敵を倒して次の敵になると、戦闘のターン 1・激昂していない。
* **中断データ**: 激昂している途中の状態を保存して戻すと、同じ倍率・同じ予告で続く（版を上げたときは、古い版のデータが読まれないこと）。
* **DEBUG**: ターンの番号を変える・戻すと、予告の攻撃の量が倍率どおりに変わり、元の番号に戻すと元の量に戻る。始まるターン・上がる量のスライダーの値が効く。
* **変わっていないこと**: 同じ乱数の状態から比べて、15 ターン目までの敵の行動・予告（攻撃の量。防御は加算が変わる分を除く）・攻防・強化・スコアが変更の前と同じ（加算の変わる HP・防御は除いて比べる）。乱数を呼ぶ回数が変わっていない。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. **加算**: `?debug` の DEBUG でステージ 10・20・30 に移ると、敵の HP・防御が前より低い（HP は元の約 1.18・1.38・1.58 倍、防御の加算は +2・+4・+7）。攻撃は前と同じ。
2. **激昂の始まり**: 1体との戦闘の 15 ターン目まではふだんどおり。16 ターン目に入ると、敵の名前の横に「激昂 ⚔×1.2」が出て、予告の攻撃の数字が倍率をかけた後の数字になる。17 ターン目は ×1.4、18 ターン目は ×1.6 …と上がる。「⚔」の字が PC・スマホで出る。
3. **かけないもの**: 激昂しても敵の防御・行動の型は変わらない。スライムの子スライムの数は増えない。21 ターン目以降に「疲弊」は出ず、防御も減らない。
4. **持ち越さない**: 激昂した敵を倒すと、次の敵は TURN 1 から始まり、激昂していない。
5. **BGM**: どの敵（ドラゴンを含む）でも同じ戦闘の曲が流れる。敵が激昂すると、今のドラゴン戦の曲に変わる。次の敵になると、ふだんの曲に戻る。
6. **中断と再開**: 激昂している途中で閉じて「再開」すると、同じ倍率・同じ予告・激昂の曲で続く（中断データの版を上げたときは、前の途中のゲームは一度だけ消える）。
7. **DEBUG**: ターンの番号を 16 以上にすると激昂の表示・予告の数字・曲が変わり、15 以下に戻すと元に戻る。ルールの値の「激昂の始まるターン」「上がる量」を変えると、それに従う。「元に戻す」で戻る。
8. **ほかの機能**: 攻防・強化・スコア・★の並び・結果の画面は前と同じように動き、タイトルから負けまで、PC とスマホで通しで遊べる。

AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   激昂の決まり（始まるターン・倍率・端数・かけるもの・かけないもの）と BGM の切り替えが分かる形にし、疲弊・章ごとの HP と防御の加算の古い記述が残っていないことを検索で確かめる。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: 各タスクの終わりで、起動とプレイが壊れない順・大きさに分ける。
    *   順の例: 加算の設定 → 激昂のルール（疲弊の整理を含む）→ 表示 → BGM → DEBUG → 古い説明コメントの直し。
    *   やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**:
    *   激昂の計算（激昂しているか・倍率・量）はルール層の純粋な計算で決める。画面（表示）と BGM は、ルール層の答えを読むだけにする。
    *   ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない。
*   **アーキテクチャの維持**:
    *   敵の種類の識別子で分岐する if を足さない（激昂はどの敵も同じ。BGM も表で持つ）。
    *   1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`Game.js`・`layout.js`・`debugTab.js` は大きいので、足す処理は分けて置けないか先に検討する。
    *   使わなくなる関数・設定・定数（疲弊の段・`fatiguedDefense`・`isFatigued`・`isEnemyFatigued`・「疲弊」の文字と色・`topGauges.fatigue` の名前・ドラゴンだけの曲の対応など）は、残さず整理するか、激昂に合わせて名前を改める。
*   **描画**:
    *   `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。
    *   `js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。
*   **エンジンの使い方**:
    *   エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。
    *   必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **今回やらないこと**:
    *   敵ごとの激昂の振る舞い（ゴーレムの体当たりなど、攻撃の量を組み立てで決める敵の扱い）。P8・P9 で敵を足すときに決める。
    *   激昂で防御を 0 にすること（防御を攻撃に使う敵の動きが崩れるため、入れない）。
    *   激昂までの予告（あと N ターン）、激昂に入るターンの特別な演出。
    *   攻撃の加算・敵の数値・強化・スコアの値の調整（発注者が試すたびに見て変える）。
    *   1ターンの演出のテンポの調整（P10）。
    *   `Game.isOver` の整理・`drawEnemyPortrait` に組み込みの名前を渡したときの例外（Phase クローズで仕分ける）。
    *   遊び方のページに激昂を書き足すこと。
    *   `assets/` の変更（BGM のファイルの名前も変えない）。
    *   `README.md`・`_doc/` の資料の書き換え。
