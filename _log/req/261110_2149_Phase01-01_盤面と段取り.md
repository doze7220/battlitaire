## 【実装要件】
ソリティア風の盤面を作り、1フェーズ分の段取り（めくる・置く・放つ）を画面の操作（タップ／クリック）で行えるようにする。ゲームのルールはルール層（`js/rules/`）に、画面はシーン（`js/scenes/`）と描画（`js/view/`）に分ける（`PROJECT_ARCHITECTURE.md` 3章・4章）。攻防・城・敵・フェーズの繰り返しは次のサブフェイズで作るため、今回は作らない。

*   **要件1: 起動と盤面の表示**
    *  起動して「TAP SCREEN」をタップすると、盤面のシーンに進む（`js/main.js` の boot 画面の `next` を盤面のシーンに変える）。
    *  `js/main.js` の `virtualPad` を `false` にし、バーチャルパッドを表示しない。
    *  盤面には次を表示する: 山札4つ（剣・盾・薬・力こぶ）、列4本、捨て札、ゲージ4つ（攻撃・防御・回復・力こぶ）、残りの行動回数、各列の「放つ」ボタン。
    *  画面は 1280×720（横長）の中に収める。列は最大7枚（数字7〜1）まで積めるので、7枚積んでも画面からはみ出さない配置にする。
*   **要件2: カードと山札の表示**
    *  カードは角丸または四角の枠に、スートの絵文字と数字（1〜7）で描く。スートの絵文字は 剣🗡️／盾🛡️／薬🧪／力こぶ💪 を基本とする（読みやすさのため、実装で別の絵文字に替える場合はRESに記載する）。
    *  山札は一番上の1枚だけが表で見え、その下の残りの枚数が数字で分かる。山札が空のときは空であることが分かる表示にする。
    *  捨て札は、枚数が分かる表示にする（中身の一覧は不要）。
    *  ゲージ4つは、それぞれの名前と現在の数値を表示する。
*   **要件3: 置く（タップ2回）**
    *  山札をタップするとその山札が「選択中」になり、その一番上のカードを置ける列が強調表示される。
    *  強調された列をタップすると、そのカードが列の一番上に置かれ、行動回数が1減り、選択は解除される。山札の一番上には次のカードが表で出る。
    *  置ける列の条件: 空いた列か、列の一番上のカードの数字が、置くカードの数字よりちょうど1大きい列（スートは問わない）。
    *  選択中に別の山札をタップすると、選択がその山札に替わる。置けない列・山札・ボタン以外の場所（何もない所）をタップすると、選択が解除される。選択中の山札をもう一度タップしたときは、要件4の場合を除き選択を解除する。
*   **要件4: 置けない札を捨てる（選んで捨てる）**
    *  選択した山札の一番上のカードがどの列にも置けないとき、その山札は「捨てる」状態の表示になる（例: 山札の上に「捨てる」と出る）。
    *  その状態でもう一度同じ山札をタップすると、そのカードが捨て札に入り、行動回数が1減る。
    *  どこかの列に置けるカードは捨てられない（捨てるのは置けないカードだけ）。
*   **要件5: 放つ**
    *  カードが1枚以上ある列の「放つ」ボタンを押すと、その列のカードがすべて捨て札に入り、ゲージが増え、行動回数が1減る。空の列の「放つ」は押せない（押せないことが見て分かる表示にする）。
    *  ゲージの増え方: 列の下から順に、同じスートが続いた区切りごとに「区切りの数字の合計 × 区切りの枚数」をそのスートのゲージ（剣→攻撃、盾→防御、薬→回復、力こぶ→力こぶ）に加える。
        *  例: 剣5・剣4・剣3 → 攻撃 (5+4+3)×3 = 36
        *  例: 剣5・盾4・剣3 → 攻撃 5+3 = 8、防御 4
        *  例: 剣5・剣4・盾3・剣2・剣1 → 攻撃 (5+4)×2 + (2+1)×2 = 24、防御 3（区切りが途切れたら、続いた区切りごとに別々に掛ける）
    *  倍率の式に使う値（「区切りの枚数」をそのまま倍率にする、という式の係数など）は設定のファイルにまとめ、後から式の強さを変えやすくする。
*   **要件6: 山札の補充**
    *  山札が尽きたら（最後の1枚を置いた・捨てた直後）、捨て札のうちその山のスートのカードをすべて取り出して混ぜ、その山札に戻す。捨て札にそのスートのカードがなければ、その山札は空のままになり、選べない。
    *  空のままの山札も、のちに同じスートのカードが捨て札に入れば（放つ・捨てるの後）、その操作の直後に同じ方法で補充される。つまり「各操作（置く・捨てる・放つ）の終わりに、空の山札があれば、捨て札にあるそのスートのカードで補充する」とする。空の山札が永久に使えなくなる状況を作らない。
*   **要件7: 行動回数**
    *  1フェーズの行動回数は5（設定値）。置く・捨てる・放つで1ずつ減る。
    *  行動回数が0になると、それ以上の選択・置く・捨てる・放つはできない。画面に行動を使い切ったことが分かる表示（例: 「行動終了」）を出す。攻防や次のフェーズは作らない（次のサブフェイズで足す）。
*   **要件8: 調整値と乱数**
    *  調整値（スートの種類と順、各スートの数字の範囲（1〜7）、列の数4、見える枚数1、基本の行動回数5、倍率の式に使う値）は、ルール層の設定のファイル1か所にまとめる。画面の座標・色・大きさは調整値ではないので `js/view/` に置く。
    *  ゲーム開始時に各山札を混ぜる。ルール層は外から渡された乱数の関数だけを使う。乱数の関数を作って渡すのはシーンまたは `js/main.js` の側とする（種を固定できる形にするかは任意。固定しない場合でも、ルール層は渡された関数だけを使う）。
    *  列は空の状態で始める。捨て札も空で始める。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **ルールと画面の分離** : 置けるかの判定、捨てられるかの判定、放ったときのゲージの計算、山札の補充、行動回数の増減は、すべてルール層（`js/rules/`）に書く。シーン・描画は、ルール層の状態を読むことと、ルール層の操作（置く・捨てる・放つ、置ける列の問い合わせなど）を呼ぶことだけを行う。強調表示する列も、ルール層の判定結果を使って決める（画面の側で判定を書き写さない）。
*   **ルール層の独立** : `js/rules/` は `oz` も `js/` のほかのフォルダも import しない。Canvas・DOM・音・時間・`Math.random` に触れない。
*   **操作の結果を返す** : ルール層の操作（置く・捨てる・放つ）は、状態を変えるとともに「何が起きたか」（置いたカードと列、捨てたカード、放った束の区切りごとの内訳・倍率・ゲージへの加算量、補充が起きたか など）を返す形にする。今回は演出（`js/anim/`）を作らないが、Phase 2 の演出がこの結果を使えるようにする。
*   **選択状態の置き場所** : 「どの山札を選択中か」は画面の操作の途中の状態であり、ゲームのルールの状態ではない。シーンに持たせてよい。ルール層の状態に混ぜない。
*   **先回り実装の禁止** : 攻防、城、敵、フェーズの繰り返し、力こぶの行動回数への換算、手札、「下なら置ける」、演出（アニメーション）、効果音、タイトル画面は作らない。
*   **エンジンの使い方** : 入力は `Scene` の `onPointer` または `Engine.addButton`（`oz/ENGINE_API.md` 16章・18章）で受ける。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない。必要な機能がエンジンにないときは、回避策を書かずにRESに記録して作業を止める。
*   **既存ファイル** : 変更してよい既存ファイルは `js/main.js` だけとする。`js/scenes/BootScene.js`・`js/scenes/MenuScene.js`・`js/ui/` は変更しない（使わないファイルも削除しない）。
*   **1ファイル1責務** : ルール層は、カード・山札と捨て札・列・放つ計算・設定・ゲーム全体の状態と操作 のように、責務ごとにファイルを分けることを検討し、1ファイルに集めて肥大化させない。描画も、カード・山札・列・ゲージなどの部品と、画面の配置（座標・当たり判定）を分ける。
