## 【実装要件】
01-01 で作った段取り（めくる・置く・捨てる・放つ）の後に、城と敵の攻防を計算し、フェーズを繰り返して勝ち・負けの決着まで遊べるようにする。攻防の計算・フェーズの進行・決着の判定はルール層（`js/rules/`）に書き、画面は文字で結果を見せるだけにする。攻防の演出（兵の群れ等）は Phase 2 で作るため、今回は作らない。

*   **要件1: 城・敵・フェーズの表示**
    *  盤面に、城の HP（「現在値 / 最大値」）、敵の HP（「現在値 / 最大値」）、敵の次の行動の予告（例: 「攻撃 10」）、いま何フェーズ目か（例: 「フェーズ 1」）を表示する。
    *  既存の表示（山札・列・捨て札・ゲージ・行動回数・放つボタン）と重ならず、1280×720 の中に収まる配置にする。列に7枚積んでもはみ出さない、という 01-01 の条件は保つ。

*   **要件2: 行動終了のボタンで攻防に入る**
    *  行動回数が0になると、01-01 の「行動終了」の表示が **押せるボタン** になる（押せることが見て分かる表示にする。例: 「行動終了」の下に小さく「タップで攻防へ」）。行動が残っている間は、このボタンは出ない（01-01 と同じく行動が0のときだけ出る）。
    *  ボタンを押すと攻防が計算され、結果の窓（要件4）が出る。行動回数が0になっただけでは攻防は始まらない（行動を使い切った後に操作が生まれる可能性に備え、プレイヤーが押すまで待つ）。
    *  行動が0の間、ボタン以外の場所をタップしても何も起きない（01-01 と同じ）。

*   **要件3: 攻防の計算（ルール層）**
    *  次の順で計算する。
        1.  防御のゲージが敵の攻撃と相殺する。相殺する量 = 防御と敵の攻撃の小さい方。
        2.  残った敵の攻撃（敵の攻撃 − 相殺した量）が城の HP を減らす（0未満にはしない）。
        3.  城の HP が0になったら、その時点で **負け** とし、以降（自軍の攻撃・回復）は計算しない。
        4.  攻撃のゲージが敵の HP を減らす（0未満にはしない）。
        5.  敵の HP が0になったら、その時点で **勝ち** とし、以降（回復）は計算しない。
        6.  回復のゲージが城の HP を戻す（最大値まで）。
    *  防御が敵の攻撃より多くても、余った防御は使われずに消える（持ち越しは作らない。調整候補として 01-03 で扱う）。
    *  攻防の操作は、状態を変えるとともに、起きたことを **出来事の並び**（順番つきの配列）として返す。各出来事は種類と量を持つ（例: 相殺した量、城が受けたダメージ、敵に与えたダメージ、回復した量、勝ち、負け）。量は実際に変わった値とする（例: 城の残り HP が3で残った敵の攻撃が10なら、城が受けたダメージは3、敵に与えたダメージも敵の残り HP を超えない）。量が0の出来事を並びに入れるか省くかは計画で決め、RES に記す（画面で「相殺 0」のような行を出すかどうかにつながる）。Phase 2 の演出がこの並びをそのまま順に見せられる形にする。
    *  攻防の後、ゲームの段階は「攻防の結果を見ている」状態になる。この状態では、置く・捨てる・放つ・攻防の操作はできない（ルール層が拒む）。

*   **要件4: 攻防の結果の窓**
    *  攻防の結果は、盤面の上に重ねる窓で見せる。窓が出ている間、盤面は少し暗くして見えたままにする。窓は `Engine.pushScene` で積む別のシーンとして作る（Phase 2 でこのシーンを演出に置き換える想定。`PROJECT_ARCHITECTURE.md` 3章の「攻防中」）。
    *  窓には、攻防の出来事を、上から順に1行ずつ文字で出す（例: 「敵の攻撃 10」「防御で相殺 6」「城が受けたダメージ 4」「敵に与えたダメージ 36」「城の回復 3」）。どの行を出すかは、ルール層が返した出来事の並びから作る（画面の側で計算をし直さない）。
    *  決着していないとき: 窓の下に「タップで次のフェーズへ」と出し、タップで窓を閉じて次のフェーズ（要件5）を始める。
    *  決着したとき: 出来事の行の後に「勝ち」または「負け」を大きく出し、その下に「タップでタイトルへ」と出す。タップで「TAP SCREEN」の画面（`js/scenes/BootScene.js`）に戻る。そこからタップすると、山札を混ぜ直した新しいゲームがフェーズ1から始まる。
    *  窓が出た直後の誤タップで閉じないよう、ボタンを押した `'down'` の直後に届く `'up'` などで窓が閉じない作りにする（`oz/ENGINE_API.md` 16章の最後の項目）。

*   **要件5: 次のフェーズ（ルール層）**
    *  次のフェーズの頭に、ルール層が次を行う。
        *  フェーズの番号を1増やす。
        *  攻撃・防御・回復のゲージを0に戻す。力こぶのゲージは残す。
        *  力こぶのゲージ5ごとに行動回数が1増える（最大+2。基本5なので最大7行動）。行動に換えた分だけ力こぶのゲージが減る（例: 力こぶ12 → +2行動、力こぶ2が残る。力こぶ17 → +2行動（上限）、力こぶ7が残る）。
        *  そのフェーズの行動回数（最大と残り）を決める。
        *  敵の次の行動を予告する（今回は毎フェーズ「攻撃10」。設定値）。
    *  山札・列・捨て札はそのまま残る（放たなかった列は残る）。
    *  次のフェーズの操作も「何が起きたか」（力こぶを何行動に換えたか、残った力こぶ、行動回数、敵の予告）を返す形にする。今回の画面では使わなくてよい。
    *  ゲーム開始時（フェーズ1）は、行動回数は基本の5、力こぶは0、敵の予告は出た状態で始まる。

*   **要件6: 決着**
    *  敵の HP が0になると勝ち、城の HP が0になると負けとする（要件3の順番どおり）。決着すると、ルール層はそれ以上の操作（置く・捨てる・放つ・攻防・次のフェーズ）を拒む。
    *  決着の表示と遊び直しは要件4のとおり。

*   **要件7: 調整値**
    *  城の最大 HP（50）、敵の最大 HP（100）、敵の行動（毎フェーズ「攻撃10」）、力こぶの換算（5ごとに+1行動、最大+2）は、ルール層の設定のファイル（`js/rules/config.js`）にまとめる。ほかのファイルに直書きしない。
    *  敵の行動は「種類と量」を持つ形にしておく（Phase 3 で種類が増える）。ただし今回作る種類は「攻撃」だけとし、種類ごとの分岐や、敵の種類・特殊行動の仕組みは作らない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **ルールと画面の分離** : 攻防の計算、決着の判定、フェーズの進行（ゲージの戻し、力こぶの換算、行動回数、敵の予告）、段階ごとに操作を許すかの判定は、すべてルール層（`js/rules/`）に書く。シーン・描画は、ルール層の状態と出来事の並びを読むことと、ルール層の操作を呼ぶことだけを行う。出来事を文に直す（「城が受けたダメージ 4」のような表示文字を作る）のは画面の側（`js/view/`）の仕事であり、ルール層に表示文字を持たせない。
*   **ルール層の独立** : `js/rules/` は `oz` も `js/` のほかのフォルダも import しない。Canvas・DOM・音・時間・`Math.random` に触れない。
*   **ルール層の肥大化を避ける** : `js/rules/Game.js` は 01-01 の時点で約190行ある。攻防の計算（出来事の並びを作る部分）、城・敵の状態、フェーズの進行（力こぶの換算など）は、責務ごとに `js/rules/` の別ファイルに分けることを検討し、`Game.js` には状態の取りまとめと操作の入口だけを置く。攻防の計算は、入力（ゲージ・城・敵の値）から出来事の並びと結果を求める純粋関数にできるとよい（01-01 の `release.js` と同じ考え方）。
*   **段階の置き場所** : ゲームの段階（段取り中／攻防の結果を見ている／決着）はルールの状態であり、ルール層に持たせる。結果の窓を出しているかどうかはシーンのスタックで表す。
*   **シーンのつなぎ方** : 結果の窓のシーンは、盤面のシーンから `Engine.pushScene` で積み、`Engine.popScene` で外す。タイトルへ戻るときは `Engine.changeScene` を使う。盤面のシーン・結果の窓のシーンが `BootScene` を直接 import して組み立てることは避け、`js/main.js` から「タイトルの画面を作る関数」を渡す形にする（今 `js/main.js` が `BootScene` の `next` に盤面のシーンを作る関数を渡しているのと同じ考え方）。シーンの操作を呼んでよい場所（`oz/ENGINE_API.md` 7章）を守る。
*   **先回り実装の禁止** : 攻防の演出（兵、城の絵、アニメーション、早送り・スキップ）、効果音、敵の種類・特殊行動、撃退数、次の敵の出現、余った防御・攻撃の持ち越し、手札、「下なら置ける」、「1 の後に 7」、結果の画面としての独立したシーン（窓のシーン以外）は作らない。
*   **エンジンの使い方** : 入力は `Scene` の `onPointer` で受け、当たり判定は `js/view/layout.js` の `hitTest`（または結果の窓用に同じ考え方で作る判定）で行う（`PROJECT_ARCHITECTURE.md` 3章。`Engine.addButton` は使わない）。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext` を書かない。必要な機能がエンジンにないときは、回避策を書かずにRESに記録して作業を止める。
*   **既存ファイル** : 変更してよい既存ファイルは `js/main.js`、`js/rules/config.js`、`js/rules/Game.js`、`js/scenes/BoardScene.js`、`js/view/layout.js`、`js/view/boardView.js`、`js/view/hudView.js` とする。そのほかの既存ファイル（`js/scenes/BootScene.js`・`js/scenes/MenuScene.js`・`js/ui/`・01-01 で作ったそのほかの `js/rules/`・`js/view/` のファイル）は変更しない。新しいファイルは `js/rules/`・`js/scenes/`・`js/view/` に作ってよい。
*   **1ファイル1責務** : 描画も、城・敵・フェーズの表示、結果の窓の描画、出来事を表示文字に直すこと、窓の配置 のように、責務ごとにファイルを分けることを検討する。
