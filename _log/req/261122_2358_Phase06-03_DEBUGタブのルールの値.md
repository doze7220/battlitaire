## 【実装要件】
デバッグスタートから始めたゲームの DEBUG タブで、城と敵のルールの値（最大 HP・常時防御力・行動の量や確率など）をその場で変えて試せるようにする（Phase 7 の数値の調整に備える）。変えた値は保存しない。

* 座標はすべて論理座標（画面 720×1280）で書く。部品の大きさ・位置・スライダーの範囲は定数に置き、試遊で決め直す値と書く。
* タイトルからクリア・負けまで、通しで遊べること（デバッグの定数が ON でも OFF でも）。スマホの縦画面を優先し、PC でも同じように使えること。
* `js/rules/config.js` の数値は変えない（DEBUG タブで変えるのは、ゲームの中で使う写しの値である）。

*   **要件1: 変えられる値と置き場所**
    *  次の **25 個**の値を、DEBUG タブで変えられるようにする。各値はスライダー（`addSlider`）で変え、今の値を出す。
        *  **城**: 最大 HP
        *  **ゴブリンの軍勢**: 最大 HP、常時防御力、攻撃の量（最小・最大）、防御の量（最小・最大）、攻撃の重み、防御の重み（重みの比が行動の確率）
        *  **巨人**: 最大 HP、常時防御力、周期（攻撃までのターン数）、攻撃の量（最小・最大）、攻撃の直後に回復する確率、回復の量
        *  **ドラゴン**: 最大 HP、常時防御力、爪の量（最小・最大）、ブレスの量（最小・最大）、ブレスで燃やす札の枚数（最小・最大）、吸い込む確率
    *  置き場所は、**今の DEBUG タブの項目（兵の数・敵・次の行動・HP・FPS）の下に続けて**、「城」「ゴブリンの軍勢」「巨人」「ドラゴン」の見出しを付けて並べる（発注者の決定）。スクロールする領域に入れる。
        *  どうしても1つのタブに収まらないとき（エンジンの決まりで入らない、スマホで使いにくすぎる、など）は、「DEBUG2」「DEBUG3」のようにタブを分けてよい（発注者の決定）。分ける場合は、DEBUG タブの右に続けて足し、デバッグスタートから始めたゲームでだけ出す。分けるかどうか・どこで分けるかは計画で決め、理由を RES に書く。
    *  見出しと各値の文字（項目名）は、`js/view/debugText.js` などの文字だけのファイルに置く。
    *  **スライダーの範囲と刻み**の目安（計画で見直してよい。定数に置き、試遊で決め直す値と書く）:
        *  城の最大 HP: 5〜200、刻み 5
        *  敵の最大 HP: 5〜300、刻み 5
        *  常時防御力: 0〜20、刻み 1
        *  攻撃・防御・爪・ブレスの量（最小・最大）、回復の量: 0〜50、刻み 1
        *  重み: 0〜10、刻み 1
        *  確率（巨人の回復・ドラゴンの吸い込む）: 0〜100%、刻み 5%（値の文字は百分率）
        *  巨人の周期: 1〜8、刻み 1
        *  ブレスで燃やす札の枚数（最小・最大）: 0〜10、刻み 1
    *  **組になった値の決まり**:
        *  「最小」と「最大」の組は、いつも 最小 ≤ 最大 を保つ。最小を最大より大きくしたら最大も同じ値に上がり、最大を最小より小さくしたら最小も同じ値に下がる（どちらのスライダーにも、次の描画で合った値が出る）。
        *  ゴブリンの攻撃と防御の重みは、両方とも 0 にはできない（もう片方が 0 のときに 0 にする操作は効かない）。
*   **要件2: いつから効くか（発注者の決定: 値ごとに、いちばん早く効く時期で効かせる）**
    *  各値の横（項目名の中など）に、その値がいつから効くかを文字で出す（例: 「すぐ」「次の予告から」「次の周期から」「次の攻防から」「出てきたときから」）。文字は文字だけのファイルに置く。
    *  **すぐ効く値**:
        *  城の最大 HP。
        *  今の敵の最大 HP・常時防御力（今戦っている敵の種類の値を変えたとき）。
        *  **最大 HP を変えたときの今の HP**（発注者の決定）: 今の HP は変えない。新しい最大 HP を超えるときだけ、最大 HP まで下げる（満タンにしたいときは、06-02 の「満タンにする」を押す）。最上部の HP のゲージと数字は、新しい最大 HP に合った割合・文字になる。ゴブリンの群れの数（HP）も、HP が下がったときはそれに合う。
    *  **次の予告から効く値**（今出ている予告は変わらない。次のターンの始まりに予告を決めるときから効く）: ゴブリンの攻撃・防御の量と重み、巨人の攻撃の量、ドラゴンの爪・ブレスの量・燃やす札の枚数・吸い込む確率。
    *  **次の周期から効く値**: 巨人の周期。今の数え下ろしはそのまま進み、攻撃した後の次の周期から新しい長さになる（数え下ろしの表示もそれに合う）。
    *  **次の攻防から効く値**: 巨人の攻撃の直後に回復する確率・回復の量（攻防のときに抽選するので、次の攻防から効く。06-02 の「攻撃して回復」で指定したときの回復の量も、変えた量になる）。
    *  **今戦っていない敵の値**: その敵が出てきたとき（次の敵に進んだとき、06-02 の敵の切り替えで切り替えたとき）から、変えた値で出てくる（最大 HP は変えた値で、HP は満タン）。項目の文字は、今戦っている敵の種類かどうかで変えてよい（例: 今の敵でなければ「出てきたときから」）。
    *  どの時期で効く値も、効いた後はふつうのルールのとおりに計算される（攻防の結果・決着・次の敵への進み方）。
*   **要件3: 元に戻す操作**
    *  「ルールの値を元に戻す」ボタンを1つ置く（ルールの値の並びの近く。置き場所は計画で決める）。押すと 25 個の値が全部 `js/rules/config.js` の値に戻る。戻した値も、要件2と同じ時期で効く（今の HP が戻した最大 HP を超えるときは、最大 HP まで下げる）。
*   **要件4: 保存しないことと、効くゲームの範囲**
    *  変えた値は保存しない（`Storage` に書かない）。ページを読み込み直すと `js/rules/config.js` の値に戻る。
    *  変えた値は、ページを読み込み直すまで残り、次にデバッグスタートから始めたゲームにも効く。**「はじめる」から始めたゲームは、いつも `js/rules/config.js` の値で遊ぶ**（DEBUG タブで変えた値は効かない）。
    *  遊び方の文章（`js/view/howToText.js`）の数字は、変えた値に合わせない（今のまま）。
    *  06-02 の兵の数のスライダーの上限 63 は、今回変えられる値（数字の範囲・束の補正・行動回数・金貨の換算は含まない）に関わらないので、今のまま。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   3章の画面の流れ（DEBUG タブの中身。タブを分けた場合はそのタブ）と、4章の責務の表（ルールの値の写しの持ち主、`config.js` とゲームが使う値の関係）を、実際に合わせて直す。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **ルールの値の持ち主はルール層**（憲法 3章）: ルールの値の正本は `js/rules/config.js`。DEBUG タブで変える値の写しを持ち、変え、元に戻し、ゲームが使う値に効かせる口は、ルール層に作る。DEBUG タブ（`js/scenes/`）は、その口を呼ぶだけにする。画面・シーン・窓の部品の `write`・`onPress` が、ルールの値やルールの状態（`game.config`・`game.enemy`・`game.castle` など）を直接書き換えない。値の写しの置き場所（新しいファイルにするか、06-02 の `debugControls.js` に足すか）は、肥大化を避けて計画で決める。
*   **ルールの値の形を変えない**: `config.js` の `Rules` の形（項目の名前と入れ子）は変えない。ゲームの中で使う値は、同じ形の写しにする（ほかのルール層の関数が、写しを `config` として今と同じように読めるようにする）。
*   **「はじめる」のゲームに混ぜない**: デバッグスタートかどうかで、ゲームに渡すルールの値を分ける。定数が OFF のときは、今と同じく `config.js` の値だけを使う。
*   **見た目は anim・view の口で合わせる**: 最大 HP・HP が変わったときの見た目（HP のゲージ・数字・ゴブリンの群れ）は、シーンが anim の口を呼んで合わせる。描画層（`js/view/`）にデータ・状態を持たせない。
*   **窓と入力**: 窓（`Ui`）はシーンが持つ。`read`・`format`・`label`・`enabled` は `draw` の中から呼ばれるので、状態を変えない。値を変えるのは `write`・`onPress` の中だけ。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **時間**: 時間は `update(dt)` の `dt` と `draw` の `time` だけを使う。`draw` の中で状態を変えない。
*   **今回やらないこと**:
    *   上の 25 個以外のルールの値（スート・数字の範囲・列の数・手札の枠・行動回数・束の補正・金貨の換算・敵の名前と順番など）を変えること。
    *   変えた値を保存すること、書き出すこと（`config.js` への書き戻しを含む）。
    *   遊び方の文章を変えた値に合わせること。
    *   キャンバスキャッシュ（Phase 06-04）。デバッグの定数を OFF にすること（後のサブフェイズ）。
    *   06-02 で作った DEBUG タブの項目（兵の数・敵・次の行動・HP・FPS）の動きを変えること。
