## 【実装要件】
敵を1体倒すたびに、強化を1つ選ぶ3択が出るようにする。強化の仕組み（枠・重み・一覧）を作り、そのうち城の強化（最大 HP・自動兵士）を入れる。

* 数値はすべて設定（ルールは `js/rules/config.js`、動きの時間は `js/anim/` の設定、配置は `js/view/` の配置の定数）に置き、下の値は初期値（試遊で変える）。
* 座標はすべて論理座標（画面 720×1280）で書く。画面の呼び名は TURN・ターン（内部の名前は phase）。
* 攻防の計算・敵・ステージの加算・疲弊・1ターンの流れ（段取り → 攻防）は変えない。

### 今の作り（現場設計で確かめたこと）
* 攻防で敵の HP が 0 になると、`Game.resolveBattle` は段階を `'result'` にし、結果に `defeat`（倒した敵の名前）を入れる。演出のシーン（`BattleShowScene`）は演出の終わりに「〜を倒した！」と「タップで次へ」を出し、タップで `goToNextPhase`（`Game.startNextPhase` → 中断データの保存 → 盤面へ戻る）に進む。`startNextPhase` が、敵の HP 0 を見て次のステージへ入れ替える（`enterStage`）。次のステージの始まりの演出（STAGE N・敵の入り）は盤面のシーンが出す。
* 中断データ（`suspendData.js`。版番号 `SUSPEND_VERSION` 2）は「ターンの始まり」だけを前提にしていて、段階（`stage`）を持たず（いつも `'planning'` として戻す）、敵の HP が 1 以上でないと捨てる。保存は `BattleShowScene.goToNextPhase` と、盤面のシーンのゲームの始まりだけ。タイトルの「再開」の下の文字は `titleText.js` の `resumePlaceText`（`STAGE 6・TURN 3`）。
* 城は `game.castle`（`hp`・`maxHp`。始まりは `config.castleMaxHp`）で、ゲームの状態として持っている。ゲージ（攻撃・防御・修理）はフェーズの頭に `phase.js` の `computePhaseStart` で 0 に戻り、段取りで放った札の分が足される。攻防の兵の数は攻防の前のゲージの値である。
* 段取りの間に陣地で待つ自軍の兵は `campTroops.js`（放った玉から兵になる）で、攻防の演出は待っていた兵の数（`waiting`）を引き継ぐ。人数の表示（`troopCountView.js`）は、ルール層の値からまだ着いていない分を引いた数。
* メニューの窓は `MenuScene` が UI 部品の窓とタブ（`ENGINE_API.md` 26章）で作り、タブの一覧は `menuTabs.js`（「設定」「クレジット」）、デバッグのときは「DEBUG」が足される。演出の途中ではメニューを開けない。
* 次のステージの敵の種類は `stageOrder.js` の `enemyTypeIdOfStage(config, seed, stageNumber)`、加算は `stageBonus.js` から、前のステージを計算せずに求められる。
* DEBUG タブの兵の数のスライダーの上限は 65（`debugTab.js` の `TROOP_SLIDER`。札から出る兵の最大から求めた値）。

*   **要件1: 強化の仕組み（ルール層）**
    *  **強化の一覧**: 強化の種類ごとに、識別子・枠・重み・出せる条件・効き方・選択肢の文字の作り方を、1種を1行足すように持つ（P9 で増える）。強化の種類の識別子で分岐する if は書かない。
    *  **取った強化**はゲームの状態として持つ（種類ごとの回数と、効いた量）。強化で変わる値（城の最大 HP・自動兵士の数など）は `config.js` の値を書き換えず、ゲームの状態として持つ（デバッグのルールの値の写しと混ざらないように）。負けると新しいゲームになるので、取った強化はすべて消える。
    *  **枠と重み**: 枠は 城・兵士・カード・特別 の4つ（重みは 1・1・1、特別だけ 0.5）。3択は、出せる強化のある枠から3つの枠を重みで選び（同じ枠は2回選ばない）、それぞれの枠の中から強化の重みで1つずつ選ぶ。
        *  まだ強化のない枠（今回は兵士・カード・特別）は選ばない。3つに足りないときは、出せる強化のある枠の中から、まだ選ばれていない強化を重みで選んで埋める（同じ強化は2つ出ない）。今回は城の枠だけなので、城の強化4種から3つが出る。
        *  出せる強化が3つ未満なら、その数だけ出す。1つもなければ「城を修理」だけになる。
    *  **城を修理**: 3択とは別に、いつも選べる。城の HP を最大 HP の 30%（切り捨て）だけ回復する（最大 HP で頭打ち。満タンでも選べる）。
    *  **抽選**: 3択の候補と、候補の中の値（最大 HP の増える量など）は、3択が出る時点で、プレイ用の乱数で決める。毎回ランダムで、敵の並びの種とは関係しない。決まった候補は、選ぶまで変わらない（中断して再開しても同じ候補）。
    *  **流れ**: 攻防で敵を倒し、「〜を倒した！」の後のタップで3択が出る。1つを選ぶと強化が効き、次のステージが始まる（今の STAGE N の始まり）。選んだ強化は次のステージから効く（最大 HP は選んだときにすぐ増える）。ルール層に「3択を選んでいる」段階を足し、選ぶ操作で次のステージへ進む。3択を選ぶ前に次のステージへは進めない。
*   **要件2: 城の強化**（ここで入れる強化。重みは枠の中の重み）

    | 強化 | 重み | 効き方 | 選択肢の文字の例 |
    |---|---|---|---|
    | 最大 HP | 3 | 最大 HP が +5〜+10（整数。3択が出たときに決まる）増え、増えた分だけ今の HP も増える | 「城の最大 HP +7」 |
    | 自動兵士（剣） | 2 | 毎ターン、攻撃の兵が1人加わる。取るたびに +1、上限なし | 「毎ターン 剣の兵 +1」 |
    | 自動兵士（盾） | 2 | 同じく防御の兵 | 「毎ターン 盾の兵 +1」 |
    | 自動兵士（ハンマー） | 2 | 同じく修理の兵 | 「毎ターン ハンマーの兵 +1」 |

    *  **自動兵士のルール**: ターンの頭（`startNextPhase` のゲージの戻しの後）に、取った回数だけ攻撃・防御・修理の値へ足す。札と関係なく加わり、攻防ではふつうの兵と同じに数える。次のステージの最初のターンにも加わる。
    *  **自動兵士の見た目**: ターンの始まり（TURN の表示と同時）に、陣地に現れ、段取りの間はほかの兵と混じって待ち、攻防ではふつうの兵と混じって動く。体の色は薄いオレンジ（持ち物は剣・盾・ハンマーのまま）。人数の表示には含め、数字の色は変えない。焼き付け（`troopBakes.js`）は薄いオレンジの兵の分も作る（入り切りで同じ見た目）。
    *  城の最大 HP の表示（最上部のゲージ）は、増えた最大 HP に合わせる。
*   **要件3: 3択の画面**（発注者の決定）
    *  「〜を倒した！」の後のタップで、盤面の上に3択の画面が出る。上の方に**次の敵の絵・名前・Lv**（次のステージの番号）が出る（強さの数値や★は出さない。発注者の決定で、詳しい強さはメニューの「敵情報」タブとして後の Phase に回した）。
    *  その下に、3つの選択肢と「城を修理（+実際に回復する量）」が並ぶ。それぞれ、文字で何が起きるかが分かる（最大 HP は増える量、自動兵士は種類と今の数→取った後の数など。文言は計画で決めてよい）。
    *  **誤タップの防ぎ方**: 選択肢は、画面の右から少しずつずれて**スライドして入ってくる**（いきなり出さない。待つだけの間を作らず、動きで身構えさせる）。入ってくる途中は押せず、全部が止まった後は、**1タップでその場で決まる**。決まったときに、選んだものが分かる短い反応（光る・押し込むなど）を見せてから、次のステージへ進む。スライドの長さ・ずれは設定の値（目安: 1つ 250〜350ms、ずれ 80〜120ms）。動きの時間は `dt` だけで進め、演出の速さ（普通・速い）の設定に合わせるかは計画で決めてよい。
    *  3択の間はメニューを開けなくてよい。押せる大きさはスマホで 80px 以上、文字が読める。
    *  BGM は、今と同じく敵を倒した時点で止まったままで、次のステージの始まりで流れる。
*   **要件4: メニューの「強化」タブ**（発注者の決定）
    *  盤面のメニューの窓に「強化」タブを足し、取った強化を見られる（種類ごとの回数と、効いた量。例: 「城の最大 HP +17（3回）」「毎ターン 剣の兵 +2」）。1つも取っていなければ、取っていないことが分かる文字を出す。タイトル画面のメニュー（ゲームの外）には出さない。
    *  タブの並びは 設定・強化・クレジット（・DEBUG）の順を目安にする。
*   **要件5: 中断と再開**
    *  3択が出た時点（候補が決まった時点）で、中断データを保存する。再開すると、**同じ候補の3択**（次の敵の表示を含む）から続けられる。選んだ後は、今と同じく次のステージの最初のターンの始まりで保存される。
    *  中断データに、取った強化と、3択の段階（段階・候補・候補の値）を足す。敵の HP が 0 のデータは、3択の段階のときだけ有効にする。形が変わるので `SUSPEND_VERSION` を 3 に上げる（前の中断データは捨てられてよい。設定は残る）。
    *  タイトルの「再開」の下の文字は、3択の段階では「STAGE 5・強化を選ぶ」のように出す（倒したステージの番号）。
    *  同じ手順で遊べば、同じ札・同じ候補が出る（プレイ用の乱数の状態を保存しているので、再開しても引き直しにならない）。
*   **要件6: DEBUG タブ**
    *  強化を付けられる: 強化の種類ごとに「+1」で取った扱いにする（最大 HP はその場で +5 など、効き方どおり）。取った強化をすべて外す操作もある。
    *  3択を出せる: 押すと、その場で候補を引いて3択の画面を出す。選ぶと強化が効き、今のターンの段取りに戻る（ステージは進めない）。
    *  兵の数のスライダーの上限を 99 にする（自動兵士の分を足しても届くように。現場設計の決定）。
    *  デバッグでは、今までどおり中断データを保存しない。
*   **要件7: 遊び方**: 遊び方の文章（`howToText.js`）が新しいルールと食い違う所があれば直す（なければ変えない）。4ページ目の敵の段は変えない。
*   **要件8: 確かめ**（一時スクリプトで行い、結果を RES に書く）
    *  3択の抽選を多数回行い、枠と強化の出る割合が重みどおり・同じ強化が2つ出ない・出せる強化が3つ未満のときの数・最大 HP の値の幅（5〜10）になる。乱数の呼び出しが決まった順で、同じ乱数の状態から同じ候補になる。
    *  自動兵士を取ったゲームで、ターンの頭のゲージが取った回数だけ増え、攻防の結果がそれを含めて計算される。最大 HP の強化で今の HP も増え、修理が 30% の切り捨てで頭打ちになる。
    *  中断データを、ふつうのターンと3択の段階の両方で保存して戻し、同じ操作（3択の選択を含む）で同じ結果になる。版番号 2 のデータが「なし」になる。3択の段階でない敵の HP 0 のデータが「なし」になる。
    *  強化を取らないゲームでは、攻防の結果・予告・乱数の呼び出し（3択の抽選の分を除く）が変更の前と同じ。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. 敵を倒して「〜を倒した！」の後にタップすると、次の敵の絵・名前・Lv と、右から選択肢が少しずつずれてスライドして入ってくる。入ってくる途中は押しても反応しない。
2. 入りきった後は、選択肢を1タップで選べ、選んだものが分かる反応の後に次のステージが始まる。
3. 3つの選択肢はいつも別々で、「城を修理」がいつもある。最大 HP は +5〜+10 の値が選択肢に出る。
4. 最大 HP を選ぶと、最上部の城の最大 HP と今の HP が増える。修理を選ぶと HP が 30% 戻る。
5. 自動兵士を選ぶと、次のステージから毎ターン、TURN の表示と同時に薄いオレンジの兵が陣地に現れ、攻防でふつうの兵と一緒に動く。人数の表示に含まれる。何回か取ると、その数だけ増える。
6. メニューの「強化」タブで、取った強化と回数が見られる。
7. 3択が出た状態で閉じて開き直すと、タイトルの「再開」の下に「STAGE N・強化を選ぶ」と出て、同じ候補の3択から続けられる。ふつうのターンの再開も今までどおりできる。
8. 負けて新しく始めると、取った強化はすべて消えている。
9. `?debug` の DEBUG タブで、強化を付けられ・外せ、「3択を出す」で3択が出て、選ぶと今のターンに戻る。兵の数のスライダーが 99 まで動く。
10. スマホで、選択肢が押しやすく、文字が読める。PC とスマホで、タイトルから負けまで通しで遊べる。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   強化の種類を足すときに書き足す所（一覧・文字・効き方・DEBUG）が、資料から分かる形になっていること。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: ルール層（強化の一覧・取った強化の状態・抽選・3択の段階と選ぶ操作・自動兵士・修理）→ 中断データ → 3択の画面（シーン・配置・スライド）→ 自動兵士の見た目 → メニューの「強化」タブ → DEBUG タブ のように、各タスクの終わりで起動とプレイが壊れない順・大きさに分ける。やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**: 候補・値・効き方・段階はルール層で決め、画面は状態を読んで操作の口を呼ぶだけにする。ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない。
*   **アーキテクチャの維持**: 強化の種類の識別子で分岐する if を足さない（一覧の表で分ける）。1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`Game.js`・`layout.js`・`BoardScene.js` は大きいので、足す処理は分けて置けないか先に検討する。
*   **動きの時間**: 動きの時間は `dt`・時計だけで決め、状態は時計から求められる形にする。
*   **描画**: `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。描く体の数は敵と兵を合わせて 500 体を目安とする。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **触るファイルの古い説明**: 次の動作に影響しない古い説明が残っている。同じファイルを触るなら一緒に直す: `BattleShowScene.goToNextPhase` の「保存はここだけ」、`BoardScene` の `rng`・`seed` の型、`TitleScene` の先頭の責務、`soundCues.js`・`bgmCues.js` の「はじめる」、`boardDebug.js` の `ruleItemInfo` の型の説明に項目 `unit`（値の刻み）がない。
*   **今回やらないこと**:
    *   兵士・カード・特別の枠の強化（精鋭・スートや数字の強化・4スートそろい／コンボの強化・アクションポイント・手札の枠）。
    *   3択の画面に次の敵の強さの数値・★を出すこと、メニューの「敵情報」タブ。
    *   スコア・ボーナス・結果の画面の作り直し、ベストの保存。
    *   敵・ステージの加算・疲弊の値の変更、新しい音・曲。
    *   `README.md`・`_doc/` の資料の書き換え。
