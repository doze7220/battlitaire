## 【実装要件】
★2・★3のステージに、同じ★の中のどの敵を出すかを、**くじ袋の決まり** にする。★2の全種を1体ずつ袋に入れ、★2のステージごとに袋から1体を引き、袋が空になったら全種を入れ直す（★3も同じ）。★1の並びの決まりは今のまま。
* **狙い**: 強敵のステージで同じ敵ばかり続かず、どの強敵もまんべんなく出る。後で★2の敵が増えても（ネクロマンサー・ゴーレム・侵略軍。別の REQ）、設定に1行足すだけで袋に入る。

**決まりごと**
* **数値の置き場所**: 数値・決まりの切り替えは設定に置く（`js/rules/config.js`）。
* **呼び名**: 画面の呼び名は TURN・ターン（内部の名前は phase）。ステージの番号（`stageNumber`）は何体目の敵か。
* **変えないもの**:
  * ★1の並び（動きの組の決まり。07-04a の「同じ敵・同じ動きを続けない」・ステージ 1〜3 に3つの動きが1回ずつ）。同じ種・同じステージで、★1の敵の種類が今と同じになる。
  * 各ステージの★（`starDraw.js` の★の抽選。07-09）と、同じ★の中の何番目か（`position`）の数え方。
  * 敵の数値・動き・見た目、攻防、強化、スコア、ほかの機能。

### 今の作り（現場設計で確かめたこと）
* **敵の選び方**: `stageOrder.js` の `enemyTypeIdOfStage(config, seed, stageNumber)`。
  1. `starDrawAt` でそのステージの★と、同じ★の中の何番目か（`position`。0 から）を求める。
  2. `position` が 0 で、その★の抽選の行（`stageStars.draws`）に `first` があれば `first`（★2 巨人・★3 ドラゴン）。
  3. それ以外は、その★の敵を動きの組（`enemyTypes.js` の `enemyMotionsOfStar`。組の鍵は `motionKeyOf`）にまとめ、`motionOrder.js` の `motionIndexAt(seed, position, 動きの数)` で動きを、`seededIndex(seed, STREAM.member, stageNumber, 数)` で同じ動きの中の敵を選ぶ。
  * どれも種・用途の鍵（`seededIndex.js` の `STREAM`）・番号だけで決まり、乱数を呼ばず、前のステージを順に計算しない（★の抽選だけは前のステージの結果に依るので、`starDraw.js` が並びを覚えて伸ばす）。並びはゲームの状態ではないので、中断データは並びを持たない。
* **今の★2**: 巨人（`cycle`）と毒キノコ（`confuse`。08-01 で足した）の2種。動きの組が2つなので交互に近い形で出るが、最初の1体（`first` の巨人）は「同じ動きを続けない」の数に入らないため、2番目の★2がまた巨人になる種がある。
* **今の★3**: ドラゴンだけ。
* **DEBUG タブの先の並びの一覧**: `debugLineup.js` の `stageLineupRow(game, offset)` が1行（ステージの番号・★・名前・今か）を求め、`debugText.js` の `lineupRowText` で文字にし、`debugLayout.js` の `LINEUP_ROWS`（20 行）だけ並べる。今のステージの行は今の敵（DEBUG の敵の切り替えの後も画面と合わせる）。

### 要件1: くじ袋の決まり（ルール層。★2・★3）
* **袋の中身**: その★の全種を1体ずつ（設定の `enemies` でその★の敵。書いた順は袋の中身の数え方だけに使う）。動きの組（`motion`・`behavior.type`）は袋では使わない。
* **引き方**: その★のステージごとに、袋から1体を引く。同じ★の中の何番目か（今の `position`）が、何番目に引くかに当たる。袋が空になったら、全種を入れ直す（袋の大きさ＝その★の種類の数）。
* **最初の袋**: その★の抽選の行の `first` があれば、`first` を先頭に固定し、残りの順を混ぜる（最初の★2は巨人・最初の★3はドラゴンのまま）。`first` がなければ全部を混ぜる。`first` が設定にない・★の違う敵なら Error（今と同じ）。
* **入れ直した直後**: 入れ直した袋から最初に引く1体は、直前に出たその★の敵（前の袋の最後の1体）と同じにならない。
  * その★の種類が1つしかないときは、同じでよい（★3は今ドラゴンだけなので、ドラゴンが続く）。
  * 同じにならないようにする方法（混ぜ直す・入れ替えるなど）は計画で決めて RES に書く。袋の中の順が種だけで決まることは崩さない。
* **種だけで決まる**: 袋の中身の順は、ゲームを始めた日付の種（`seed`）で決まる。同じ日に何度始めても同じ並び、DEBUG でステージを移っても・中断して再開しても並びは変わらない。プレイ用の乱数は呼ばない。用途の鍵は新しく足してよい（`STREAM` に1行）。
  * 前の袋を順に計算しなくても求められる形が望ましい（直前の袋の最後だけが要る）。順に計算して覚える形にするなら、`starDraw.js` と同じく「計算結果の写しでゲームの状態ではない」扱いにし、理由を RES に書く。
* **どの★が袋か**: ★ごとにどちらの決まり（★1は今の動きの組の決まり、★2・★3は袋）を使うかは、設定で決まるようにする（★の数字で分岐しない。持ち方は計画で決める。例: `stageStars.draws` の行に項目を足す）。
* **敵を足すとき**: ★2・★3の敵は `config.js` の `enemies` に1行足すだけで袋に入る（08-03 以降でネクロマンサーなどを足す）。種類が増えると、同じ日付でも★2・★3の並びが変わる。これは構わない。
* **今の★2で見えること**: ★2は巨人と毒キノコの2種なので、巨人 → 毒キノコ → 巨人 → 毒キノコ… と必ず交互になる（2番目の★2がまた巨人になることはなくなる）。

### 要件2: 中断データ
* 並びは種とステージの番号から求めるので、中断データの形は変えない（版 10 のまま）を初期案とする。形を変える必要が出たら、理由と版の扱いを RES に書く。
* 袋を入れる前に保存した途中のゲームも読め、今の敵のまま続き、次のステージから新しい並びになる（07-09 の★の抽選のときと同じ扱い）。

### 要件3: DEBUG タブの先の並びの一覧（発注者の決定）
* ★2・★3の行に、袋の番号と、その袋の何番目かを出す（例: 「袋2の1番目」。文言・置き方は計画で決める）。袋の入れ直しの境目と、直前と同じ敵が続いていないことが、一覧で読める。
* ★1の行は今のまま。
* 今のステージの行（DEBUG で敵を切り替えた後の今の敵）の袋の番号の扱いは、計画で決めて RES に書く（並びの上での袋の位置を出すのでよい）。
* 一覧の行数（20 行）・ほかの DEBUG の項目は変えない。

### 要件4: 確かめ（一時スクリプトで行い、結果を RES に書く）
* **袋の決まり**: 10 年分の種 × ステージ 1〜500 ほどで、★2・★3のステージを順に並べ、次が成り立つ。
  * 袋の大きさごとの区切りの中に、その★の全種が1回ずつ出る。
  * 最初の★2は巨人、最初の★3はドラゴン。
  * 袋の境目で、直前と同じ敵が続かない（種類が1つの★を除く）。
  * 同じ種・同じステージで、何度求めても・ステージ 1 から順に求めても途中から求めても、同じ敵になる。
* **敵を足したとき**: 一時スクリプトの中で設定の写しに★2の敵を足して（3〜5種）、上の決まりが成り立つ（ゲームの設定ファイルには足さない）。
* **変わっていないこと**: 変更の前と比べて、同じ種・同じステージで、各ステージの★と、★1のステージの敵の種類が同じ。
* **中断データ**: 保存して戻したゲームで、先のステージの敵が保存の前と同じ。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. **★2の出方**: ふつうに遊ぶと、最初の★2は巨人で、その後の★2は毒キノコ → 巨人 → 毒キノコ… と交互に出る。
2. **★3**: ★3はいつもドラゴン（今と同じ）。
3. **DEBUG の並びの一覧**: `?debug` の先の並びの一覧で、★2・★3の行に袋の番号と何番目かが出て、袋の決まりどおりに並んでいる。★1の行は今のまま。
4. **同じ日付なら同じ並び**: 同じ日に「もう一度」で始め直しても、同じ並びになる。
5. **中断と再開**: 途中で閉じて「再開」しても、先の並びが変わらない。
6. **ほかは変わらない**: ★1の敵の並び（同じ日付で前と同じステージに同じ★1の敵）と、どのステージが強敵になるかは前と同じ。タイトルから負けまで通しで遊べる。

## 【計画書に必ず含めるべき固定タスク】

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: 各タスクの終わりで、起動とプレイが壊れない順・大きさに分ける。
    *   順の例: 袋の決まりの純粋関数（まだ使わない）→ 並びの選び方の切り替え（設定で★2・★3を袋に）→ DEBUG の並びの一覧の袋の番号。
    *   やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**:
    *   並びはルール層で決める。DEBUG の一覧は、ルール層の問い合わせ（袋の番号・何番目か）を読むだけにする。
    *   ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない。
*   **アーキテクチャの維持**:
    *   敵の種類の識別子・★の数字で分岐する if を足さない（設定・表で分ける）。
    *   1つのモジュールに責務を足しすぎない（憲法 3章）。袋の計算は、動きの組の計算（`motionOrder.js`）と別のファイルに置くことを検討する。
    *   ★1の並びの計算（`motionOrder.js`・`STREAM.member` などの使い方）は変えない。`STREAM` の既存の値は変えない。
*   **エンジンの使い方**:
    *   エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。
    *   必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **今回やらないこと**:
    *   ★2・★3の敵の追加（ネクロマンサー・ゴーレム・侵略軍・★3の敵）。
    *   ★1の並びの決まり・★の抽選の決まりと確率の変更。
    *   敵の数値・動き・見た目の変更。
    *   DEBUG の一覧の行数やほかの DEBUG の項目の変更。
    *   `README.md`・`_doc/` の資料の書き換え。
