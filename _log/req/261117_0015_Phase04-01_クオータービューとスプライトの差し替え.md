## 【実装要件】
戦闘の段（画面の最上段）を、斜め上から見下ろしたクオータービューの見た目にし、仮の図形を発注者が OZ Vector Editor で作ったスプライト（`assets/sprites/`）に差し替える。あわせて、スートの「薬」を「ハンマー」、「力こぶ」を「金貨」に見た目と名前だけ変える。**ルールは変えない。攻防の流れ・兵の動き・時間割・音は今のままで、描く絵と置き場所だけが変わる。** タイトルからクリア・負けまで、いまと同じく通しで遊べること。

*   **要件1: 戦闘の段の背景**
    *  戦闘の段に、背景のスプライト（`background.js`）を描く。段の上 60px が空、下 300px が地面（斜め上から見た地面）の絵になっている。いまの空と地面の塗りと地面の線は描かない。
    *  地面は回さない。左が自軍（城）、右が敵のまま。
    *  戦闘の段の高さ（`js/view/layout.js` の `BATTLE_H`）は 360 のまま変えない。背景は 720×360 で段と同じ大きさなので、拡大縮小せずに段全体に描く。
    *  フェーズ・城の HP・敵の名前と HP・予告・数え下ろしの枠は、今の位置のまま背景の上に描いてよい（重なり方は試遊で見る）。
*   **要件2: 城の位置とスプライト**
    *  城を、城のスプライト（`unit_castle.js`）で描く。いまの城の四角（狭間つき）は描かない。
    *  城の中心の x は、戦闘の段の左端から約 1/3（約 240px）に置く。城の左側（後ろ）は、後のサブフェイズで自軍の兵が並ぶ場所として空けておく（今回はそこに何も描かなくてよい）。この位置は、後の試遊で動かせるよう、配置の定数1か所で変えられること。
    *  城の見た目の高さは、戦闘の段に収まり、上の枠（フェーズの枠など）と大きく重ならない大きさ（目安 180〜200px）にする。大きさも定数1か所で変えられること。
    *  城の位置が変わるので、城に当たる位置・大工が現れる位置・兵が動く場の左端など、城の矩形から求めている配置は新しい城の位置から求め直す（兵の動きの流れは今のままでよい）。
*   **要件3: 敵のスプライト**
    *  巨人を `unit_giant.js`、ドラゴンを `unit_dragon.js` で描く。いまの巨人の緑の玉・ドラゴンの赤い玉は描かない。
    *  ゴブリンの軍勢の群れの兵1体1体を、ゴブリンのスプライト（`unit_goblin.js`、緑の丸）で描く。群れの数・並び方は今のままでよい（HP との連動は後のサブフェイズ）。
    *  巨人・ドラゴンは、地面に立って見える位置に、戦闘の段に収まる大きさ（目安 高さ 200px 前後）で描く。大きさは敵ごとに定数で変えられること。
    *  常時防御力のシールドマークは、盾のスートのスプライト（`suit_shield.js`）を縮小して描く。並べる先は、敵の絵の体の上に収まる矩形にする（並べ方は今の格子のままでよい。光り方も今のまま）。
    *  敵の回復の量（緑の「+20」）の浮き出しなど、敵の玉の位置から求めている表示は、新しい敵の絵の位置から求め直す。
    *  兵が敵・シールドマークに当たる位置（`armorHitX`・`enemyHitX`）は、今は敵の種類によらず同じ。今回は新しい敵の絵の位置に合わせた仮の値でよい（敵ごとに作り直すのは後のサブフェイズ）。
*   **要件4: 兵のスプライト（丸だけ）**
    *  自軍の兵（守備兵・兵士・大工）は、自軍の兵のスプライト（`unit_solder.js`、白い丸）で描く。
    *  敵の側の兵（敵兵・敵の守り・ゴブリン）は、ゴブリンのスプライト（`unit_goblin.js`、緑の丸）で描く。
    *  兵とゴブリンのスプライトは、絵が大きめ（直径約 200px）に作ってある。画面には大きく縮小して描く。小さな兵の見た目の大きさは、いまの小さな兵の大きさ（`TroopLayout` の `smallW`・`smallH` 程度）を目安にする。縮小の倍率は配置の定数から求め、1か所で変えられること。
    *  今回は持ち物（盾・槍・槌・旗）や色で役割を見分けられなくてよい。いまの人形の仮の図形（胴・頭・持ち物）は描かない。
    *  大きなユニット（10人分の1体）は、同じ丸のスプライトを大きく描く。人数の換算・群れの動き・位置・濃さは今のまま（`js/anim/` は変えない想定。変える必要があれば理由を計画に書く）。
*   **要件5: スプライトの扱い**
    *  スプライトは `oz/ENGINE_API.md` 23章のとおり、`import x from 'assets/sprites/xxx.js'` で読み、`ctx.save()`／`translate`／`scale` の後に `draw(ctx)` を呼んで `ctx.restore()` で戻す。`draw` 以外のキー（`bounds` など）は実行時に読まない。
    *  スプライトの import と「位置・大きさを合わせて `draw(ctx)` を呼ぶ」処理は、`js/view/` の中の1つのモジュール（新しく作る。名前は計画で決める）に集め、ほかの描画モジュールはそこを呼ぶ。後でエンジンに Canvas のキャッシュが入ったとき、呼ぶ側を変えずに中身だけを差し替えられるようにするため。スプライトごとの「基準点から見た絵の範囲」（下の表）は、このモジュールの凍結した定数の表として持つ。
    *  スプライトは回さず、エディタで描いた向きのまま描く。巨人・ドラゴンは左（城の方）を向いて描かれている。基準点（原点）は絵の足元ではなく体の中ほどにあるので、地面に立たせるには下の表の下端（`maxY`）を使う。
    *  スプライトの絵の範囲（発注者のファイルの `bounds` を、現場設計が確かめた値。単位 px、基準点 (0, 0)、y は下向き）:

| ファイル | 中身 | x の範囲 | y の範囲 |
| --- | --- | --- | --- |
| `background.js` | 背景（上 60 が空、下 300 が地面） | −360〜360 | −260〜100 |
| `unit_castle.js` | 城（クオータービューの城） | −115〜101 | −292〜150 |
| `unit_giant.js` | 巨人（左向き） | −113〜160 | −153〜243 |
| `unit_dragon.js` | ドラゴン（左向き） | −150〜168 | −196〜200 |
| `unit_solder.js` | 自軍の兵（白い丸） | −99〜99 | −98〜98 |
| `unit_goblin.js` | ゴブリン（緑の丸） | −99〜99 | −98〜98 |
| `suit_sword.js` | 剣 | −39.5〜40.5 | −100.5〜99.5 |
| `suit_shield.js` | 盾 | −80.5〜80.5 | −100.5〜100.5 |

*   **要件5の続き**
    *  背景は、基準点を戦闘の段の (360, 260) に置くと段にぴったり重なる。
    *  `effect_fire.js`（炎）は今回は使わない。
    *  `assets/sprites/` のファイルは書き換えない。足りない絵はない（つなぎのスプライトは作らない）。
*   **要件6: スートの絵と名前**
    *  盤面のカード（列・山札・捨て札・手札・動いているカード）の真ん中の絵文字を、スートのスプライト（剣 `suit_sword.js`・盾 `suit_shield.js`・薬 → ハンマー `suit_hammer.js`・力こぶ → 金貨 `suit_gold.js`）に差し替える。カードの数字・色・枠は今のままでよい。カードの効果は変わらない。
    *  ゲージの行の名前を「回復」→「修理」、「力こぶ」→「金貨」に変える（「攻撃」「防御」はそのまま）。数字の出し方・枠は変えない。
    *  画面のほかの文字も同じ名前にそろえる。少なくとも、結果の表示の「回復の合計」を「修理の合計」にする。ほかに自軍の回復・力こぶを指す画面の文字があれば同じく直す（計画で `js/view/` を探して列挙すること）。**敵（巨人）の回復**（緑の「+20」など）は敵が自分の HP を戻すことなので「回復」のままにする。
    *  コードの中の識別子（スートの `potion`・`muscle`、ゲージの `heal`・`muscle`、出来事の `heal` など）は変えない。画面に出る名前と絵だけを変える。識別子と画面の名前の対応（`potion` は画面ではハンマー、`muscle` は金貨、ゲージ `heal` は修理）は開発資料に書く。
*   **要件7: 開発資料**
    *  `PROJECT_ARCHITECTURE.md` の戦闘の段の記述を、クオータービュー（背景のスプライト、左が自軍・右が敵、城の位置）に直す。コードのコメントの「サイドビュー」（`js/view/layout.js` の戦闘の段の配置の JSDoc）も直す。
    *  スプライトの向きと基準点の決まり（回さずに描く・敵は左向き・基準点は体の中ほど）を開発資料に書く（`oz/ENGINE_API.md` 23章が「前方の向きはゲームの開発資料に書く」としているため）。
    *  スートとゲージの識別子と画面の名前の対応（要件6）を開発資料に書く。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する（戦闘の段のクオータービューの記述、スプライトの向きと基準点、スートとゲージの識別子と画面の名前の対応、新しく作るスプライトのモジュールと、責務の変わった `js/view/` のファイルの表の更新など）。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `PROJECT_CONSTITUTION.md` の絶対禁止事項に反する設計をしてはならない。描画（`js/view/`）は状態を変えず、ルール層（`js/rules/`）を実行時に import しない。配置（座標と大きさ）は `js/view/layout.js` に置き、描画モジュールに座標を直書きしない。
*   **ルールと演出を変えない** : ルール層（`js/rules/`）は変更しない。攻防の段の並び・時刻・兵の数と動き・早送り・スキップ・音のきっかけ（`js/anim/`・`js/scenes/soundCues.js`）は変えない。演出の途中・早送り・スキップのどれでも、ルールの結果は変わらない。
*   **スプライトの扱い** : `assets/sprites/` を変更しない。スプライトの `draw` 以外のキーを実行時に読まない。スプライトを描く処理を各描画モジュールに散らさず、要件5の1つのモジュールに集める。`ctx` の変換は必ず `save`／`restore` で囲む。
*   **先回り実装の禁止** : 兵を1人＝1体で描くこと、陣地（盾 → 城 → 剣 → 修理の並び）、兵が武器を持つ見た目、人数の表示、跳ねて落ちる消え方、光の玉、敵ごとの攻防の見せ方（ゴブリンの数と HP の連動・シールドが剥がれる・ヒットマーク・ブレスの炎）、エフェクト（ヒットストップ・揺れ・呼吸）、敵ごとの当たる位置の作り直し、デバッグモード、ゲージの行の作り替え、カードのデザイン全体の作り替え、Canvas のキャッシュは作らない。これらは後のサブフェイズ・Phase で扱う。
*   **使われなくなったものの片付け** : スプライトに置き換えて使われなくなる仮の図形の描画処理・色や大きさの定数・配置の項目（城の狭間、敵の玉の色、人形の胴・頭・持ち物、絵文字の表など）は、残さずに消す（呼び出し元と JSDoc も合わせる）。ただし、差し替えと無関係な箇所の「ついでの整理」はしない。
*   **エンジンの使い方** : `oz` は `import { … } from 'oz'` でだけ使う。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext`・`setTimeout`・`setInterval`・`performance.now()`・`Date.now()` を書かない。
*   **変更してよい範囲** : 変更してよいのは `js/view/` の中のファイル（新しいファイルを含む）とする（どのファイルを変えるかは計画に明記すること）。`js/rules/`・`js/anim/`・`js/scenes/`・`js/audio/`・`oz/`・`index.html`・`js/main.js`・`js/ui/`・`assets/` は変更しない。これら以外の変更が必要だと分かった場合は、計画の中で理由を書いて対象に加えるのではなく、RESの懸念事項に記して発注者の判断を仰ぐこと。
*   **1ファイル1責務** : `js/view/layout.js`・`js/view/battleStageView.js` を肥大化させない。スプライトを描く処理は新しいモジュールに分ける。
*   **テストプレイで確かめること（計画の最後に、発注者が見る点として書くこと）**
    *  戦闘の段に背景の絵（空と地面）が描かれ、左に城、右に敵がいる。城の左側に空きがある。
    *  城・ゴブリン・巨人・ドラゴン・自軍の兵がスプライトで描かれ、城の四角・巨人の緑の玉・ドラゴンの赤い玉・人形の兵が画面に残っていない。
    *  盤面のカードの絵が剣・盾・ハンマー・金貨の袋の絵になっている。ゲージの行が「攻撃・防御・修理・金貨」、結果の表示が「修理の合計」になっている。
    *  攻防の演出（兵の突撃・相殺・城や敵への当たり・修理・敵の回復・ブレスで札が燃える・敵を倒したときの案内・早送り・スキップ）が今と同じ流れで動き、タイトルからクリア・負けまで通しで遊べる。
