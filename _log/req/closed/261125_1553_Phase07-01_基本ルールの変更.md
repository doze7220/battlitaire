## 【実装要件】
戦闘の土台になるルールを変える。放った列に4スートがそろうと +1、敵は攻撃と防御を同時に予告できる、巨人・ドラゴンの毎回固定のシールドをやめてターンごとのランダムな防御にする、決まったターンに隙（防御 0）ができる、長引いた敵は疲弊して防御が減る、TURN の番号を戦闘ごとに数える。

* 数値はすべて `js/rules/config.js` に置き、下の値は初期値（試遊で変える）。
* 座標はすべて論理座標（画面 720×1280）で書く。画面の呼び名は TURN・ターン（内部の名前は phase）。
* 敵はいままでどおり ゴブリンの軍勢 → 巨人 → ドラゴン の順で、ドラゴンを倒すとクリア。城の HP・盤面・金貨の引き継ぎ、行動の回数、束の補正は変えない。

### 今の作り（現場設計で確かめたこと）
* 敵の予告（`enemy.intent`）は `{ kind, amount, variant?, burn?, sureHeal? }` の1つの量だけを持ち、攻撃と防御を同時に表せない。
* ゴブリンは攻撃（2〜5・重み 3）か防御（2〜5・重み 1）のどちらかを抽選する（`'weighted'` の決まり）。巨人は常時防御力 3、ドラゴンは 4 を毎ターン張る（`armor`）。
* 攻防の計算（`battle.js`）は、敵の防御と常時防御力を別々に引き、別の出来事（`enemyBlock`・`enemyArmorBlock`）にしている。
* TURN の番号は `game.phase`（ゲームを通した番号）。最上部の TURN・始まりの演出の TURN N・`boardFlow.js` の始まりを出したかの印（`introPhase`）が同じ値を使っている。
* 戦闘の画面に敵の名前は出ていない（出るのはステージの始まりのロゴだけ）。
* 敵の側の攻撃の兵（`enemy`）と守りの兵（`enemyGuard`）は同じ陣地（x 470〜550）に、種類ごとの番号から決まる位置で並ぶ。両方が同時に出ると、同じ番号の兵がぴったり重なる。

*   **要件1: 4スートそろい**
    *  放った列に、設定のすべてのスート（剣・盾・ハンマー・金貨）の札が1枚以上ずつあると、攻撃・防御・修理・金貨のそれぞれに +1 を足す。並びの順・続いた枚数は問わない。1回放つごとに1度だけ。
    *  足す量は設定（初期値 1）で、0 にすると効果がなくなる（切れる）。
    *  同じスートの区切りごとの合計・足す量・加算量（今の式）は変えない。+1 は区切りとは別に足し、放った結果（`ReleaseResult`）から、+1 があったことと量が分かるようにする。ゲージごとの加算量（`gains`）には +1 を含める。
    *  見せ方（発注者の決定）: いまの区切りの玉と式のあとに、放った列の上に「4スート +1」の文字を出し、4つのスートの色の小さい玉が1つずつ、攻撃・防御・修理の陣地と金貨のゲージへ飛ぶ。着くと兵が1人ずつ現れ、金貨のゲージが 1 増える。
        *  文字の数字は設定の量を出す。文字は縁取り付きで、スマホで読める大きさ。画面の端からはみ出さない。
        *  放つたびの待ちを目立って長くしない（いまの最後の区切りの玉が飛ぶのと重ねて見せてよい。時間は `animConfig.js` に置く）。
        *  人数の枠・金貨のゲージの表示は、いまと同じく、着くにつれて増える。陣地で待つ兵の数とルール層のゲージの値が食い違わないこと（食い違うと攻防の始めに Error になる）。
        *  準備終了は、+1 の玉と兵が全部着いてから出る。
*   **要件2: 敵の行動は「攻撃」と「防御」の2つの量を持つ**
    *  敵の予告は、1ターンに攻撃の量と防御の量の両方を同時に持てる。どちらか一方が 0 でもよい。振りかぶり・吸い込む（攻撃しない）のターンにも防御の量を持てる。
    *  防御の量は、敵の種類の設定「防御を張る確率」と「量の幅（最小〜最大）」で決める。3体とも同じ形の設定にする。
    *  敵の防御（ゴブリンの防御の兵、巨人・ドラゴンのシールド）は、見た目が違うだけで、そのターンだけの「防御の量」として同じに扱う。自軍の攻撃からその量を差し引き、余っても次のターンへ持ち越さない。
    *  常時防御力（`armor`）はなくす。攻防の計算と出来事では、敵の防御を1つに統合する（守りの兵で見せるかシールドで見せるかは、敵の種類の見せ方の表（`enemyShows.js` の `body`）で演出の側が決める。ルール層は見た目で分岐しない）。
    *  乱数の順: 今の行動の決まりの抽選（種類・攻撃の量）→ 防御を張るか（1回）→ 防御の量（1回）。隙のターンでないときは、張らない結果でも・疲弊していても、必ず2回呼ぶ。隙のターンは防御の乱数を呼ばない。予告は今と同じくターンの頭に決め、攻防は予告の量で行う。
    *  敵の種類の名前・識別子で分岐しない。隙のターンかどうかは、行動の決まりの設定か、行動の決まりの種類ごとの実装が決める。
*   **要件3: 敵ごとの行動と初期値**（発注者の決定）

    | 敵 | 攻撃 | 防御 | 隙（防御 0） | HP |
    |---|---|---|---|---|
    | ゴブリンの軍勢 | 毎ターン 1〜3 | 毎ターン 1〜2（確率 100%） | なし | 30 のまま |
    | 巨人 | 今のまま（4ターンに1回 18〜22、ほかは振りかぶり。攻撃の直後の回復も今のまま） | 75% で 2〜6 | 攻撃のターン | 60 のまま |
    | ドラゴン | 今のまま（爪 4〜6、吸い込む 30% → 次は必ずブレス 10〜13 と燃える札） | 75% で 3〜7 | 吸い込むのターン | 80 → 90 |

    *  ゴブリンは「攻撃と防御を毎ターン両方行う」新しい決まりにする。「どちらか一方を重みで抽選」の決まり（`'weighted'`）は使う敵がなくなるので消す（DEBUG タブの重みの項目・検証も）。
*   **要件4: 予告の表示**
    *  敵の頭の上の札に、攻撃の側（今の絵と量。振りかぶり・吸い込むは絵だけ）と、防御の側（防御の絵 `intent_defend` と量）を、横に並べて同時に出す。
    *  **防御が 0 のターンは、防御の絵も数字も出さない**（発注者の決定。防御の絵がないこと＝隙、と読む）。攻撃の側がない行動は今はないが、あれば防御だけを出す。
    *  ブレスの赤い札（目立たせ）は今のまま。
    *  札が長くなっても画面の右端（720）からはみ出さず、最上部のゲージ・人数の枠と重ならない（ゴブリンの札は今の中心 x 650 のままだとはみ出す見込み）。巨人の数え下ろし（「攻撃まで あとN」）は今のとおり札の下に読める。
    *  始まりの演出（TURN N）の予告の文字も両方を出す（「攻撃 3 ／ 防御 2」「振りかぶり ／ 防御 4」のように。防御 0 なら今と同じ「攻撃 20」）。幅を超えないこと。
    *  攻防の演出中の札も同じ。
*   **要件5: 攻防の演出**
    *  ゴブリンが攻撃と防御を同時に行う攻防を見せる。攻撃のゴブリンと守りのゴブリンが画面の外から現れ、攻撃の側が盾の兵・城へ、その後に自軍の剣の兵が守りのゴブリン・群れへ当たる。順番と結果は攻防の計算のとおり。
        *  攻撃のゴブリンと守りのゴブリンが、ぴったり重なって1体に見えないようにする。
        *  攻防の演出の長さが目立って伸びないようにする（両方が同時に現れる、など。計画で決める）。
        *  余った守りのゴブリンは今と同じく右へ帰る。城が落ちて負けたときも破綻しない。
    *  巨人・ドラゴンのシールドは、段取りの間からそのターンの防御の量の数だけ体に並び、攻撃の兵が当たるたびに1つずつ剥がれる（今の常時防御力のシールドと同じ見せ方）。0 なら並ばない。次のターンの始まりに、新しい量に変わる。
    *  ドラゴンのブレスと燃える札・巨人の回復・ための段・ヒットストップなど、ほかの演出は今のまま。
*   **要件6: 疲弊**
    *  1体との戦闘が 21 ターン目に入ると、その敵の防御の量が半分（端数切り捨て）になり、26 ターン目からは 0 になる。攻撃・行動の周期・確率・HP・回復は変えない。次の敵には持ち越さない。
    *  境目のターン（21・26）は設定に置く。
    *  減った後の量を予告・シールドの数・攻防に使う（半分になって 0 になれば、予告の防御は出ない）。
    *  画面右上の敵の HP ゲージの下（x 410〜700、y 30〜58 のあたり。金貨のゲージの反対側の空き）に、**敵の名前を左詰めでいつも出し、疲弊しているあいだ「疲弊」を同じ行の右詰めで出す**（発注者の決定）。
        *  ふつうの文字（スプライトのロゴではない）。縁取り付きで、空の背景の上でスマホで読める大きさ（目安 18px 以上）。「疲弊」は目立つ色にする。
        *  予告の札・TURN の区画と重ならない。段取りの間も攻防の演出中も同じ場所に出し、揺れでは揺らさない。敵が入ってくる前（ステージの始まり）の見え方は計画で決めてよいが、次の敵の名前が先に出てもよい。
*   **要件7: TURN の番号**
    *  最上部の TURN と、始まりの演出の TURN N は、その戦闘で何ターン目か（敵が替わると 1 に戻る）を出す。
    *  ゲームを通したターンの番号は別に持ち続ける（始まりの演出を出したかの印・結果の「かかったターン数」は今のまま通しの値）。
*   **要件8: DEBUG タブ**
    *  戦闘のターンの番号のスライダー（1〜30）を足す。動かすと TURN の番号が変わり、疲弊がその番号で決まり直す。いまの予告の防御の量も、抽選し直さずに、元の抽選の量から数え直す（21 にすれば半分、26 にすれば 0、20 に戻せば元の量）。通しのターンの番号・行動の回数・盤面・集計は触らない。段取りの間だけ効く（今のデバッグの操作と同じ）。
    *  「今の敵」を切り替えると、戦闘のターンの番号は 1 に戻る。
    *  ルールの値のスライダーを新しい値に合わせる: 常時防御力と重みの項目をなくし、3体それぞれに防御の確率・防御の量の最小と最大を足す（効く時期は「次の予告から」）。ゴブリンの攻撃の量は残す。最小 ≤ 最大の決まり、「元に戻す」は今のまま。項目の数は、城 1・ゴブリン 6・巨人 9・ドラゴン 11 の 27 になる見込み。
    *  防御の量のスライダーの最大は 20 とし、シールドの焼き付けの上限（`SHIELD_BAKE_MAX_COUNT` の 20。1〜20）と合わせる（コメントの説明も直す）。
    *  「次の行動」の選択肢を新しい行動に合わせる（ゴブリンは「攻撃と防御」の1つ、巨人・ドラゴンは今のまま）。選んだときの防御の量は、ふつうと同じ決まり（隙なら 0、それ以外は抽選、疲弊も効く）。
    *  兵の数のスライダーの上限（63）を、4スートそろいの +1 で見直す。現場設計の計算では 65（7 行動で2回放つ。7 枚の束 +34 と 5 枚を置いて放つ +29 に、それぞれ +1）。計画で確かめて決め、根拠のコメントを直す。
    *  デバッグのとき、新しい値も保存しない（今と同じ）。
*   **要件9: 遊び方の文章**（`js/view/howToText.js`）
    *  2ページ目（基本はソリティア！）に、4スートそろいを足す。文案: 「4つの絵柄を|1列に|混ぜて|放つと、|{key:すべて +1}の|おまけ付き！」
    *  4ページ目のゴブリンの説明を直す（今の「防御してるときが準備のチャンス！」はルールと合わなくなる）。文案: 「毎ターン、攻撃と|防御を|同時に|してくる。{key:防御の薄い}|ターンが|攻めどき！」
    *  ほかに食い違う所があれば直す（巨人の絵の予告の数字 20 は今のままでよい）。文章が区画からはみ出さず、読めること。絵は変えない。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. 4スートの混じった列を放つと「4スート +1」が出て、4つの玉が飛び、攻撃・防御・修理の兵が1人ずつ、金貨が 1 増える。1スートでも欠けた列では出ない。連続で放っても、最後に準備終了 → BATTLE! へ進める。
2. ゴブリン: 毎ターン、攻撃と防御の両方が予告に出る。攻防で攻撃のゴブリンと守りのゴブリンの両方が見え、予告の量どおりに減る。
3. 巨人: シールドの数がターンごとに変わり、予告の防御の数字と同じ。張らないターンもある。攻撃のターンは必ずシールドなし。
4. ドラゴン: 吸い込むのターンは必ずシールドなし。爪・ブレスのターンは張ることがある。HP 90 から始まる。
5. 予告の札が、どの敵・どの行動でも画面からはみ出さず、スマホで読める。防御 0 のターンは防御の絵が出ない。
6. 敵の HP ゲージの下に敵の名前が左詰めで出る。`?debug` でターンの番号を 21 にすると「疲弊」が右詰めで出て防御が半分に、26 で防御が出なくなる。20 に戻すと元の量に戻る。敵を切り替えると TURN 1 に戻り、疲弊が消える。
7. ふつうに敵を倒すと、次の敵で TURN が 1 から始まる。結果の「かかったターン数」は通しの数。
8. DEBUG タブの新しいスライダーが効き、「元に戻す」で初期値に戻る。
9. 遊び方の2ページ目・4ページ目が読める。
10. タイトルからクリア・負けまで、通しで遊べる（PC とスマホ）。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   「常時防御力」「重みによる抽選」「ルールの値 25 個」など、なくなった・変わった記述が資料に残らないこと。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: ルール層（敵の行動と攻防）→ 攻防の演出 → 予告・名前・疲弊の表示 → 4スートそろい（ルールと演出）→ TURN の番号 → DEBUG タブ → 遊び方 のように、各タスクの終わりで起動とプレイが壊れない順・大きさに分ける。やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**: 4スートそろいの判定、防御の量、隙、疲弊、戦闘のターン数はルール層で決め、画面・演出は結果と状態を読むだけにする。ルール層は `oz` も画面のモジュールも import しない。乱数は渡された関数だけを使う。
*   **量の計算は1か所**: 疲弊で減らした後の防御の量を求めるのは、ルール層の1か所だけにする。予告・シールドの数・攻防は同じ値を使う。
*   **アーキテクチャの維持**: 敵の種類の識別子で分岐する if を足さない（設定・行動の決まりの表・見せ方の表で分ける）。1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。
*   **1体＝1ポイント**: 1体が複数のポイントを持つ仕組みは作らない。
*   **スプライト**: 新しいスプライトは作らない。既存のスプライトは変更しない（防御の予告の絵は `intent_defend.js` を使う）。
*   **描画**: `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **今回やらないこと**:
    *   3体を倒した後も続く進行、敵の並び・★・ステージの加算、敵の名前のロゴをなくすこと（ステージの始まりの名前のロゴは今のまま）。
    *   新しい敵、敵の1体のポイント・大きさの変更。
    *   強化・3択・スコア・中断と再開。結果の板の項目の変更。
    *   乱数の作り（種・保存）の変更。
    *   疲弊の間に攻撃・周期・確率を変えること、疲弊の演出（音・画面の効果）を足すこと。
    *   4スートそろいの DEBUG タブの項目を足すこと。
    *   自軍の数値（城の HP・行動の回数・束の補正・金貨の換算）の変更。
