**本作業は調査のみを目的とする。いかなる理由があっても、ソースコードおよび資料ファイルの修正・作成を行ってはならない（RESファイルの出力を除く）。PHASEOUT（`D:\ozlab\phaseout`）と OZ Engine のリポジトリ（`D:\ozlab\ozengine-web`）にも、何も書かない（連絡票 `BRIDGE_FROM_*.md` も作らない）。**

1. ルール（`PROJECT_CONSTITUTION.md`）を熟読・把握すること。エンジンの使い方は `oz/ENGINE_API.md` だけを読むこと（`oz/src/` は読まない）。OZ Engine のリポジトリでも `oz/src/` は読まず、資料（`*.md`）・`oz/VERSION`・`oz/FINGERPRINTS.txt`・git の履歴（`git log` など読むだけのコマンド）だけを見ること。
2. 本REQの【関連する責務】を把握すること。作業に必要な責務情報はすべてここに記載されている。開発資料（`PROJECT_ARCHITECTURE.md`）は、記載外の責務を確認する必要が生じた場合にのみ参照すること。
3. 調査対象のコードを読み、【関連する責務】の記述と実コードに相違がある場合は、その相違点を調査結果に必ず含めること（作業は中断しない）。記述にない事項の存在は相違とみなさない。
4. 【調査要件】に従って調査を行い、実コード・資料から読み取れる事実のみを抽出すること。要件1・2では推測・改善提案は求めていない。推測を含める必要がある場合（要件1-7・要件3など）は、どこまでが実コード・資料の記述でどこからが推測かを明示すること。事実には、ファイルと行（資料なら章）を添えること。
5. 調査が完了したら、この時点までにソースコードおよび資料ファイルを一切変更していないこと（このプロジェクトの `git status` がクリーンであること、PHASEOUT と OZ Engine のリポジトリで何も書いていないこと）を確認したうえで、Survey作業レポートテンプレート（`./_log/TEMPLATE_RES_Survey.md`）を元に、作業レポート（`./_log/res/YYMMDD_HHMM_RES_Survey_エンジンへの要望の材料集め.md`）を新規作成して出力すること。RES冒頭の参照元REQには本ファイル `./_log/req/261121_1834_Survey_エンジンへの要望の材料集め.md` を記載すること。
6. すべての調査が完了したら、チャットにて「調査が完了しました。RESの確認をお願いします」と報告すること。

## 【調査の背景】
次の Phase で、バトリティアにデバッグの仕組み（開発用の調整パネル）を作り、OZ Engine を今の版に載せ替える予定である。その前に、OZ Engine への要望をまとめる材料を集める。発注者はコードを読まないため、結論は画面・操作・挙動の言葉でも書くこと。

* PHASEOUT（`D:\ozlab\phaseout`）は、発注者が以前作ったゲームで、デバッグ機能（`js/core/DebugConfig.js`・`js/render/DebugManager.js`・`js/scene/ConfigScene.js`・`js/render/UIComponents.js` など）を持つ。参考にする作りとして調べる。
  * REQ 作成時の確認では、PHASEOUT は OZ Engine を取り込んでいない（`oz/` フォルダと import map がなく、自前の `SceneManager`・`SpriteCacheManager` と Matter.js を使う）ように見えた。要件2-0で確かめること。そのため、要件1の「ゲーム側にあるかエンジン側にあるか」は、「そのゲームに固有のコードか、ゲームによらない部品として分けて作られているか」として調べる。
* バトリティアが取り込んでいる OZ Engine は `oz/VERSION` が `0.1.0`。OZ Engine のリポジトリ（`D:\ozlab\ozengine-web`）の `oz/VERSION` も `0.1.0` のままだが、`oz/ENGINE_API.md` には 25章「キャンバスキャッシュ」が足されている（REQ 作成時の確認）。版の番号が同じでも中身が違う前提で比べること。
* 発注者が考えている要望の候補（このほかに調査で見つかったものも足す）:
  * サブウィンドウの UI の部品（タブ・ボタン・チェックボックス・スライダー）。見た目をゲーム側で差し替えられる形。開発用の調整パネルと、遊ぶ人向けの設定画面の両方に使う。
  * 部品の値を、ゲームの設定の値につなぐ口。
  * キャンバスキャッシュを実行中に使う・使わないで切り替えられること（描画の重さを比べて計測するため）。
  * FPS の表示を実行中に出し入れできること（今の `oz/ENGINE_API.md` 14章では「実行中には切り替えられない」）。
* バトリティアの開発資料にある、デバッグモードの予定（`_doc/PROJECT_MILESTONE.md` の「演出と UI の磨き込み」節。読むだけ）: タイトル画面に「デバッグモードスタート」を置き、1つの定数で、そのボタンとエンジンの FPS 表示（`debug: true`）をいっしょに入り切りしてリリースのときに消す。`addButton` は消せないので、操作は専用のシーン（`pushScene`）にまとめる。
* 同じ資料の「エンジンへの要望」節（読むだけ）に、スプライトの Canvas キャッシュの要望と、連絡票で詰める論点（焼く範囲、原点、解像度、焼くときの色の差し替え、ウィンドウの大きさが変わったときの焼き直し）が書いてある。

## 【調査要件】
*   **要件1: PHASEOUT のデバッグ機能の作り**（`D:\ozlab\phaseout`。読むだけ）
    *  **1-1 入口とリリースでの消し方**: デバッグ機能にどこから入るか（画面のどこに何があり、何を押すと開くか。PC のキー操作があればそれも）。リリースのときに消す方法（`DebugConfig.js` の `ENABLE_DEBUG_OVERLAY` など）。定数1つで全部が消えるか、消えずに残るもの（`index.html` の `#debug-overlay` の要素、読み込まれるだけのファイル、デバッグ用の値が本番の値に混ざる経路など）があるかを示す。
    *  **1-2 UI の部品の有無と作り**: サブウィンドウ（重ねて開く窓）・タブ・ボタン・チェックボックス（入り切り）・スライダー・選択肢の切り替え・数値の表示などの部品ごとに、有無と作りを表にする。作りには、Canvas に描くか DOM か、どのファイルのどのクラス・関数か、見た目（色・大きさ・文字）をどこで決めているか、押した判定のしかた、部品がそのゲームに固有のコードか、ゲームによらない部品として分けられているかを含める。
    *  **1-3 部品の値と設定の値のつなぎ方**: 部品の値（例: `DEBUG_VALUES` の選択肢）が、どの経路でゲームの設定の値（`config.js`・`effectConfig.js` など）に届くか。その場で値が変わって画面に効くか、シーンのやり直し・再起動が要るか。値を保存するか（`localStorage` など）、次に開いたときにどうなるか。
    *  **1-4 スマホでの操作**: デバッグの画面での、タッチとマウスの扱い、ドラッグ・スクロール（長い一覧を指でずらす、スライダーを指で動かすなど）の有無と作り、タップとスクロールの区別、デバッグの画面を開いている間にゲーム本体へ入力が通り抜けない作りかどうか。
    *  **1-5 FPS などの計測の表示**: FPS・描画時間・物の数などを表示する仕組みの有無と作り。実行中に出し入れできるか。
    *  **1-6 キャッシュ**: `SpriteCacheManager` などのキャッシュの仕組みの有無と作り（何を焼くか、いつ焼き直すか）。実行中に使う・使わないを切り替えられるか、切り替えて比べる仕組みがあるか。
    *  **1-7 ゲームによらず使えそうな部分の仕分け**: 1-1〜1-6 の部品・仕組みごとに、「ゲームによらず使えそう（エンジンに移せそう）」「そのゲームに固有」「分けられるが手直しが要る」を表にし、根拠（そのコードが何に依存しているか: ゲームの設定・Matter.js・DOM など）を書く。この仕分けは推測を含むので、事実と分けて書くこと。
*   **要件2: OZ Engine の版と機能**（資料だけで調べる。エンジンのソースは読まない）
    *  **2-0 PHASEOUT と OZ Engine の関係**: PHASEOUT が OZ Engine を取り込んでいるか（`oz/` フォルダ・import map・`from 'oz'` の有無）。取り込んでいなければ、その事実と、エンジンにあたる仕組み（シーン・ループ・入力・キャッシュ）を自前で持っていることを示す。PHASEOUT の資料（`PROJECT_ARCHITECTURE.md`・`_docs/`）に OZ Engine との関係の記述があれば添える。
    *  **2-1 版の比べ**: このプロジェクトの `oz/VERSION`・`oz/FINGERPRINTS.txt` と、OZ Engine のリポジトリの `oz/VERSION`・`oz/FINGERPRINTS.txt` を見比べ、ファイルごとに「同じ」「違う」「片方にだけある」を表にする（2つのファイルの記載を見比べるだけで、ハッシュの計算による照合はしない）。OZ Engine のリポジトリの git の履歴と資料（`_doc/COWORK_STATUS.md`・`_doc/COWORK_STATUS_CLOSED.md`・`_doc/PROJECT_MILESTONE.md` など）から、バトリティアが取り込んだ後にエンジンで何が変わったかを並べる。版の番号が上がっていない理由・版の番号の付け方が資料にあれば示す。
    *  **2-2 ENGINE_API.md の違い**: 2つの `oz/ENGINE_API.md` を章ごとに見比べ、足された章・書き換わった記述を表にする（25章以外も含めて）。
    *  **2-3 観点ごとの今のエンジンの機能**: OZ Engine のリポジトリの `oz/ENGINE_API.md` で、次の観点ごとに、できること・できないこと・書かれていないことを章を添えて示す。
        *  キャンバスキャッシュの使い方（作り方、描き方、焼き直し、捨て方、作れる時期、注意）。
        *  キャンバスキャッシュを実行中に使う・使わないで切り替えられるか（エンジンに入り切りの口があるか。ない場合、焼き付けと元のスプライトを描き分ければ同じことができるかを、資料の記述から分かる範囲で）。
        *  FPS の表示を実行中に出し入れできるか。FPS の値をゲーム側で読めるか。
        *  UI の部品（ボタン・タブ・チェックボックス・スライダー・窓など）の有無。ボタン（18章）を消せるか・隠せるか、シーンを積んだときのボタンと入力の扱い。
        *  ドラッグ・スクロールに使えるポインタ入力（16章）の機能（押したまま動かす、離す、複数の指）。
        *  OZ Engine のリポジトリの `_doc/PROJECT_MILESTONE.md`・`_doc/COWORK_STATUS.md` に、上の要望の候補（UI の部品、値をつなぐ口、キャッシュの入り切り、FPS の出し入れ）が予定や懸念として載っているか。
    *  **2-4 載せ替えで直す必要がありそうな所**: このプロジェクトの `js/` で `from 'oz'` から使っている機能（`Engine`・`Scene`・`Assets`・`Sound` など）と使い方を挙げ、2-2 の違いのうち、載せ替えで書き方・振る舞いが変わるものがあるかを示す。OZ Engine のリポジトリの `_doc/newgame/NEW_GAME_GUIDE.md` 9章「エンジンの更新」の手順の要点（誰が何をするか）も示す。
*   **要件3: エンジンへの要望の下書き**
    *  要件1・2を踏まえて、OZ Engine への要望の下書きを、項目の一覧として RES に書く。項目ごとに次を書く。
        *  要望の内容（画面・操作・挙動の言葉で）。
        *  要る理由（バトリティアでの使い道: 開発用の調整パネル、遊ぶ人向けの設定画面、描画の重さの計測と比べ、など）。
        *  今のエンジンですでにできるか（要件2-3 の根拠）。できるなら要望から外し、「今の版でできる」として残す。
        *  PHASEOUT の作りで参考になること（要件1 の根拠）。
        *  連絡票で詰める論点（決めなければならないこと）。
    *  【調査の背景】の要望の候補4つは必ず項目にする。調査で見つかった要望の候補（例: ボタンを消す・隠す口）があれば足す。`_doc/PROJECT_MILESTONE.md`「エンジンへの要望」節の Canvas キャッシュの論点が、今のエンジンでどこまで決着しているかも照らして書く。
    *  書き方は OZ Engine のリポジトリの `_doc/newgame/NEW_GAME_GUIDE.md` 10章（読むだけ）の連絡票の書式に寄せてよいが、連絡票のファイルには書かない（書くのは発注者の承認の後）。要望の下書きは推測・提案を含むので、その旨を明示すること。
