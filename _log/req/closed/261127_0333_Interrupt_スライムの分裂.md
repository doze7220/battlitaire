## 【実装要件】
★1の敵「スライム」（`slime`）を、**ダメージを受けると「子スライム」が生まれ、次のターンのふつうの攻撃に上乗せして襲ってくる敵** に作り直す。名前・識別子は今のまま（「スライム」・`slime`）で、★1は6種のまま。
* **狙い**: 防御の準備がないときに大攻撃をぶちかますと、次のターンに痛い目にあう。盾を寝かせておくか、寝かせた束で一気に倒しきるのが上手い遊び方になる。

**決まりごと**
* **数値の置き場所**: 数値はすべて設定に置く（ルールは `js/rules/config.js`、動き・大きさは `js/anim/battleAnimConfig.js` や配置の定数など）。下の値は初期値で、試遊で変える。
* **座標**: すべて論理座標（画面 720×1280）で書く。
* **呼び名**: 画面の呼び名は TURN・ターン（内部の名前は phase）。
* **変えないもの**: ほかの7種の敵、自軍、ステージ、1ターンの流れ、ほかの機能。
  * ほかの7種の敵（猪の親子を含む）: 数値・動き・見た目・乱数を呼ぶ順と回数・攻防の計算と出来事・時間割。
  * 自軍: 数値。
  * ステージ: 加算の量・疲弊の決まり。
  * ほかの機能: スコアの項目・精鋭・強化。

### 今の作り（現場設計で確かめたこと）
* **スライムの設定**: `config.js` の `enemies.slime`。
  * 名前「スライム」・★1・最大 HP 40。防御の設定（`defense`）は持たない。
  * 行動の決まり `either`:
    * 40% で攻撃（2〜3）。
    * 外れれば防御だけのターン（2〜4。そのうち 20% は大防御 5〜7）。
* **見た目**: 絵の敵（`enemyShows.js` の `body: 'figure'`、攻撃の見せ方 `dashBounce`、`dents: true`）。
  * 絵は `enemyFigures.js` の `ENEMY_FIGURES.slime`（高さ 120・シールドあり・`minScale` 0.5＝HP が減ると体が縮む）。
  * スプライトは `assets/sprites/unit_slime.js`。
  * BGM は `stage`（`soundConfig.js`）。攻撃の始まりの音はない（`soundCues.js` の `ENEMY_ATTACK_SE` に行がない）。
* **攻防の計算**: `battle.js` の `computeBattle` が合計の引き算で求める。順序は次のとおり。
  1. 敵の攻撃
  2. 盾の兵との相殺（`block`）
  3. 城の被害（`castleDamage`）
  4. 敵の回復
  5. 敵の防御での相殺（`enemyBlock`）
  6. 敵への攻撃（`enemyDamage`。残りの HP で頭打ち）
  7. 倒した（`enemyDefeat`）
  8. 修理
  * 敵の攻撃が先なので、敵を倒すターンでも敵の攻撃は城に届く。
* **ターンをまたいで持つ敵の状態**: 敵の状態は `combatants.js` の `createEnemy`（`hp`・`maxHp`・`parts`・`intent`・`behaviorState`）。
  * Interrupt 猪の親子で、親と子の HP `parts` を足した（親子でない敵は `null`）。
  * 次のターンに持ち越す攻撃のユニットは、まだない。
* **群れの攻撃の兵**: 画面の外から陣地へ出て城へ向かい、盾の兵と1対1で相打ちになる（ゴブリンの攻撃の見せ方 `march`）。
  * Interrupt 猪の親子で、「絵と群れを両方持つ体」（`body: 'brood'`）ができた。この体の群れは HP を持ち、剣が当たる。
* **★1の並び**: 敵の並びは動きの組ごとに決まる。組の鍵は `enemyTypes.js` の `motionKeyOf(spec)` = `spec.motion ?? spec.behavior.type`（Interrupt 猪の親子で作った）。
  * 今の組は3つある。
    * 攻防を同時に: ゴブリン・オーガ
    * 溜めて大攻撃: 狼・猪の親子
    * 攻撃か防御: 骸骨・スライム
* **予告の札**: 攻撃の側（剣の絵と量）と防御の側を出す（`intentView.js`・`intentParts.js`）。
* **中断データ**: 版 7（`suspendData.js` の `SUSPEND_VERSION`）。
* **DEBUG タブ**: 次がある。
  * 敵の切り替え
  * 敵の次の行動（`debugIntents.js`。`either` は攻撃・防御・大防御）
  * ルールの値のスライダー（`debugRuleItems.js`）
  * 「HP を 1 にする」「子を 0 にする」「親を 0 にする」

### 要件1: スライムの数値と行動（発注者の決定。ステージの加算の前。★1）
* **HP**: 40（今のまま）。HP を持つのはスライムだけ（子スライムは HP を持たない）。
* **行動**: 毎ターン、ふつうの攻撃を行う（2〜3。今の攻撃の幅のまま。ステージの加算（攻撃）が足される）。
  * 防御はしない（防御だけのターン・大防御はなくなる。防御はいつも 0）。
* **並び**: 並びの組は、骸骨と同じ「攻撃か防御」の組のままにする（発注者の決定）。
  * 同じ日付・同じステージで出る敵の並びは、今と同じになる。
  * 行動の決まりの種類を変えるなら、設定の `motion` で組を今のままにする。ほかの7種の組と並びは変えない。

### 要件2: 子スライム（攻防の結果はルール層で決める）
**生まれ方**
* 自軍の攻撃でスライムがダメージを受けると、与えたダメージの割合の数だけ子スライムが生まれる。
  * 割合の初期値: 30%（設定に置く）。
  * 数は切り上げ（発注者の決定）。1 でも当てれば最低1匹生まれる。例: 1 → 1匹、10 → 3匹、11 → 4匹。
  * 与えたダメージは、そのターンの敵へのダメージ（`enemyDamage`。残りの HP で頭打ちの、実際に減った量）。0 なら生まれない。
  * 数に上限は付けない（発注者の決定）。
  * 数にステージの加算は足さない。疲弊も効かない。

**襲い方**
* 子スライムは次のターンに持ち越す敵の攻撃のユニット。
  * 次のターンのふつうの攻撃に、子スライムの数だけ上乗せされる。
  * 1匹1ポイントで、盾の兵と1対1で相打ちになり、越えた分が城に当たる（ふつうの攻撃と合わせて今の相殺・城の被害の式のまま）。
  * 襲いかかった後は消える（そのターンの攻防で生まれた子スライムだけが、次のターンに残る）。
  * 剣では消せない（剣はスライムにだけ当たる）。
* スライムを倒すターンの扱い（発注者の決定）:
  * 前のターンに生まれた子スライムは、今の順（敵の攻撃が先）のまま、そのターンもスライムの攻撃と一緒に襲う。
  * 倒した一撃で生まれる子スライムは出ない（戦闘が終わるので、次のターンには持ち越さない）。
* 子スライムが盾の兵・城にどれだけ当たり、ふつうの攻撃がどれだけ当たったかは、ルール層の攻防の計算が出来事として出す。
  * 演出は出来事を読むだけで、計算し直さない。
  * 盾の兵に当たる順（子スライムが先か、スライムの攻撃が先か）は計画で決めて RES に書く。
  * 合計の量（`block`・`castleDamage`）は今の計算の式と合う。
  * 最大の一撃の数え方・城の被害の記録（スコアの「無傷」）は今のまま（子スライムの城の被害も城の被害に入る）。
  * ほかの敵の出来事の並び・量は変えない。
* 子スライムの数は、敵の状態として持つ（ほかの敵は持たない、または 0）。

**予告**
* 次のターンの予告に、ふつうの攻撃と子スライムの数が並んで出る（例: 攻撃4 +子スライム8）。
* 予告の札の形（発注者の決定）: 今の攻撃の札（剣の絵と量）の横に、子スライムの絵と数の札をもう1つ並べる。
  * 子スライムが 0 匹なら、子スライムの札は出さない。
  * ターンの始まりの文字（予告の始まりの表示）も、同じ中身が分かるようにする。

**中断データ**
* 子スライムの数を持たせ、版を上げる（8）。
* どのターンでも保存して戻せる。版 7 のデータは捨てられる。

### 要件5: 確かめ（一時スクリプトで行い、結果を RES に書く）
* **生まれる数**: 与えたダメージ 0・1・3・4・10・11・残りの HP を越える量などで、生まれる数が切り上げの 30% になる（頭打ちの量で数える）。
* **予告**: スライムを多数のターン進め、毎ターンふつうの攻撃（2〜3＋加算）と、前のターンに生まれた子スライムの数が予告に出る。防御はいつも 0。
* **攻防の場合分け**: 攻防の計算が次の場合でエラーなく出来事を出す。量の合計（盾の兵での相殺・城の被害）と子スライムの残りが要件2のとおりになる。
  * 子スライム 0 匹・盾の兵より少ない・同じ・多い。
  * スライムを倒すターン（前のターンの子スライムは襲う。倒した一撃の子は持ち越さない）。
  * 城が落ちるとき。
* **攻防の時間割**: 上の場合（精鋭を含む）で時間割がエラーなく作れる。消える体・盾の兵での相殺・城の被害の合計が、出来事の量と合う。
* **変わっていないこと**: 同じ乱数の状態から比べて、次が変更の前と同じになる。
  * ほかの7種の予告・最大 HP・乱数の呼び出し・攻防の出来事・時間割・見た目。
  * ★1 の並び（10 年分の種 × ステージ 1〜500 ほど。同じ日付・ステージで同じ敵の種類）。
* **中断データ**: 子スライムがいるターン・いないターンで保存して戻し、同じ操作で同じ結果になる。版 7 のデータは捨てられる。
* **描く体の数**: ステージ 30・100 で、大きな一撃の次のターンを数える（目安 500 体）。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. **出たとき**: `?debug` でスライムに切り替えると、今と同じスライムが出る。予告はふつうの攻撃（2〜3）だけで、防御のターンはない。
2. **子スライムが生まれる**: 剣でスライムを削ると、スライムから子スライムが生まれ、そばに並んで待つ。数は与えたダメージの3割（切り上げ）。
3. **次のターンの予告**: 予告の札に、攻撃の札の横に子スライムの絵と数の札が並ぶ（例: 攻撃4 +子スライム8）。0匹なら出ない。
4. **襲いかかる**: 次のターン、子スライムが盾の兵へ向かって1対1で相打ちになり、越えた分が城に当たって消える。スライム自身の攻撃もいつもどおり来る。
5. **剣では消せない**: 剣の兵は子スライムに向かわず、スライムにだけ当たる。
6. **倒すターン**: 前のターンの子スライムは倒すターンにも襲う。倒した一撃で子スライムは出ず、「〜を倒した！」になる。
7. **狙いどおりか**: 盾がないときに大攻撃を当てると、次のターンに痛い。盾を寝かせておくか、一気に倒しきると楽になる。
8. **DEBUG**: 子スライムの数の操作・ルールの値のスライダー（子スライムが生まれる割合を含む）と「元に戻す」が効く。
9. **崩れないこと**:
   * スライム・子スライムの群れ・攻撃の子スライム・予告の札・HP の表示が重なりすぎない。
   * ステージ 20〜30 のスライムで大きな一撃を当てても、崩れない・重くならない。
10. **中断と再開**: 子スライムが待っている途中で閉じて「再開」しても、子スライムの数が同じように残り、続きから遊べる。
11. **ほかの敵と通しのプレイ**:
    * ほかの敵（ゴブリン・オーガ・狼・猪の親子・骸骨・巨人・ドラゴン）の見た目と動きは前と変わらない。
    * 同じ日付なら、前と同じステージにスライムが出る。
    * タイトルから負けまで、PC とスマホで通しで遊べる。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   2章「敵の種類を足すときに書き足す所」に、次のターンに持ち越す攻撃のユニット（子スライム）を持つ敵を書き足す所が分かる形にする。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: 各タスクの終わりで、起動とプレイが壊れない順・大きさに分ける。
    *   順の例: ルール層（子スライムの数・予告への上乗せ・攻防の計算。まだスライムの設定は今のまま）→ 演出の「持ち越す攻撃のユニット」の仕組み（ほかの敵の時間割が変わらないことを確かめる）→ 子スライムのスプライトのコピーと見た目・並ぶ場所・予告の札 → 中断データ → スライムの設定の切り替え → DEBUG タブ。
    *   スライムの設定を替えるのは、見せる表と中断データがそろってからにする（途中で Error にならないように）。
    *   やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**:
    *   子スライムの数・予告の量・攻防の結果は、ルール層で決める。演出は結果と状態を読むだけにする。
    *   ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない。
*   **アーキテクチャの維持**:
    *   敵の種類の識別子で分岐する if を足さない（設定・表で分ける）。
    *   1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`battle.js`・`Game.js`・`layout.js`・`battleTimeline.js`・`troopRoster.js` は大きいので、足す処理は分けて置けないか先に検討する。
    *   ほかの敵の攻防の計算は、今の `computeBattle` の結果と同じになるようにする。
    *   猪の親子の仕組み（`enemyParts.js`・`body: 'brood'`）は、使える所は使ってよいが、猪の親子の動き・見た目・出来事を変えない。
*   **動きの時間**:
    *   動きの時間は `dt`・演出の時計だけで決め、状態は時計から求められる形にする（今の演出と同じ）。
    *   演出の速さ（普通・速い）とヒットストップが、新しい動きにも同じように効く。
*   **描画**:
    *   `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。
    *   `js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。
    *   描く体の数は、敵と兵を合わせて 500 体を目安とする。
*   **エンジンの使い方**:
    *   エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。
    *   必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **今回やらないこと**:
    *   ほかの7種の敵（猪の親子を含む）の数値と見せ方の変更。
    *   ステージの加算・疲弊の値の変更。
    *   新しい音・曲・予告の絵（子スライムの札の絵は子スライムのスプライトを使う）。
    *   子スライムの本番の絵（発注者が後で描く）。
    *   敵の絵（`enemyPortrait.js`）の変更。
    *   遊び方の4ページ目に敵を足すこと。
    *   スコアの項目・強化・精鋭の仕組みの変更。
    *   `README.md`・`_doc/` の資料の書き換え。
