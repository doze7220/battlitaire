## 【実装要件】
いまは種類のない敵1体を倒すか、城が落ちるかで決着する。今回は、敵に種類（名前・最大 HP・常時防御力・行動の決まり）を持たせ、ゴブリンの軍勢 → 巨人 → ドラゴンの順に戦い、ドラゴンを倒すとゲームクリアになる進行に作り変える。巨人・ドラゴンの固有の行動（数え下ろし・回復・ブレスチャージ・札を燃やす）は 03-02・03-03 で作るので、今回は仮の行動で通しで遊べればよい。結果の画面・集計（フェーズ数・総ダメージなど）は 03-04 で作るので、今回は作らない。

*   **要件1: 敵の種類と設定**
    *  敵は種類ごとに、名前・最大 HP・常時防御力・行動の決まり（予告する行動の種類ごとの量と重み）を持つ。これらの値と、敵の順番は、ルール層の設定のファイル（`js/rules/config.js`）にまとまっていて、そこを書き換えるだけで変えられる。いまの `enemyMaxHp`・`enemyActions`（種類のない敵の設定）は、敵の種類ごとの設定に置き換える。
    *  敵の順番は ゴブリンの軍勢 → 巨人 → ドラゴン で固定。
    *  初期値（仮。03-05 で調整する）:
        *  ゴブリンの軍勢: 名前「ゴブリンの軍勢」、最大 HP 50、常時防御力 0。行動は 攻撃 10（重み 3）・防御のスタンス 15（重み 1）。基本は毎フェーズ攻撃を予告し、ときどき防御のスタンスを予告する。
        *  巨人（仮の行動）: 名前「巨人」、最大 HP 80、常時防御力 8。行動は 攻撃 15（重み 2）・防御のスタンス 15（重み 1）。
        *  ドラゴン（仮の行動）: 名前「ドラゴン」、最大 HP 120、常時防御力 15。行動は 攻撃 20（重み 2）・防御のスタンス 15（重み 1）。
    *  敵の行動の決まりは、03-02（周期の数え下ろし・攻撃後の回復）・03-03（ブレスチャージの蓄積・満ちたら確率でブレス・ブレスで札を燃やす）で、敵ごとに状態を持つ決まりを足せる形にしておく（今回は重みによる抽選の決まり1種類だけを作る。足す形の想定を計画に書くこと）。

*   **要件2: 常時防御力とフェーズごとの壁**
    *  敵の防御は、いまと同じくフェーズごとの壁として働く（そのフェーズの攻撃の合計から引き、残りが敵へのダメージになる。余りはフェーズの終わりに消える）。壁の量は「常時防御力」＋「そのフェーズに防御のスタンスを取っていればスタンスの量」。
    *  常時防御力が 0 でない敵では、防御のスタンスを取らないフェーズでも、攻撃が常時防御力の分だけ減る。
    *  防御のスタンスの分と常時防御力の分は、攻防の出来事の並びで別の出来事として分かれる（演出で見分けるため。要件4）。自軍の攻撃は、先に防御のスタンス（敵の前に並ぶ敵の守り）で、次に常時防御力で減る。

*   **要件3: 敵の入れ替わりと決着**
    *  敵の HP を 0 にすると、その敵を倒したことになる。
    *  **途中の敵（ゴブリンの軍勢・巨人）を倒したフェーズ**: 攻防はそこで止まらず、回復ゲージによる城の回復はいつもどおり起きる。攻防の演出の終わりに、戦闘の段に大きく「（倒した敵の名前）を倒した！」と「次は（次の敵の名前）」、「タップで次へ」の案内が出る（早送り・スキップのボタンは消える）。画面のどこかをタップすると、次のフェーズへ進み、次の敵（HP が最大）と戦う。案内が出ている間、戦闘の段の敵は倒した敵のまま（HP 0）でよい。
    *  **最後の敵（ドラゴン）の HP を 0 にしたとき**: ゲームクリアとして決着する。いまの勝ちと同じく、回復の前で攻防が終わり、いまの「勝ち」の表示と「タップでタイトルへ」を出す（表示の文字を「クリア」にするかは計画で決めてよい）。
    *  **城の HP が 0 になったとき**: ゲームオーバーとして決着する（いまの負けの表示のまま）。
    *  敵が替わっても、城の HP と盤面（列・山札・捨て札・手札）はそのまま引き継ぐ。ゲージ・行動回数・力こぶの換算は、いまのフェーズの進み方（`startNextPhase`）どおりに動く。フェーズ数は通しで数え続ける（敵ごとに 1 に戻さない）。
    *  次の敵の最初の予告は、次の敵の行動の決まりで、次のフェーズに入るときに決まる。

*   **要件4: 戦闘の段の表示**
    *  戦闘の段の敵の HP の表示は、いま戦っている敵の名前と HP（例: 「ゴブリンの軍勢 30 / 50」）になる。文字が枠からはみ出さないこと（必要なら枠や文字の大きさを調整してよい）。
    *  **ゴブリンの軍勢の見た目**: 戦闘の段の敵の位置に、小さな兵の群れ（仮の図形。攻防の演出の敵兵と色か形で見分けられるとよい）が、段取りの間も最初から並んで見える。兵の数は HP と連動させない固定の数で、描画の側の定数で変えられる。
    *  **巨人・ドラゴンの見た目（仮）**: いまの敵の玉（丸）でよい。巨人とドラゴンで色を変えてもよい（03-02・03-03 で作り込む）。
    *  **常時防御力のシールドマーク**: 常時防御力が 0 でない敵は、敵の図形（玉）に重ねて、常時防御力の数だけのシールドマーク（盾の形の仮の図形）が、段取りの間も攻防の演出の間も見える（巨人なら8個、ドラゴンなら15個）。敵の図形からはみ出しすぎず、数えられる程度に並ぶこと（並べ方は計画で決めてよい）。
    *  **攻防の演出での常時防御力**: 自軍の突撃で、防御のスタンスの敵の守りとの相殺（いまの「敵の防御での相殺」）の後に、残った兵士がシールドマークに当たり、常時防御力の分だけ兵士が消える段が入る（量が 0 なら段を飛ばす）。シールドマークは常時のものなので消えない（当たったことが分かる見た目、例えば一瞬光る程度はあってよい）。その後、残った兵士が敵に当たる（いまの「敵へのダメージ」）。効果音は、いまの「敵の防御での相殺」と同じ音を当ててよい。

*   **要件5: 攻防の演出・段取りは他は変えない**
    *  上に書いたこと以外の、段取り（カードの操作と動き）・攻防の演出（兵の動き・早送り・スキップ・速さ）・音の挙動は変えない。決着していない、敵も倒していないフェーズは、いまどおり演出の後に自動で次のフェーズへ進む。
    *  ルール層の攻防は、いまどおり「行動終了」の時点で一度に結果を決め、演出はその結果を後から見せるだけにする。次のフェーズへ進む操作（次の敵への入れ替わりを含む）は、演出（と要件3の案内のタップ）が終わってから行う。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する（敵の種類と進行のルール、攻防の出来事・段の追加、戦闘の段の表示、作成済みのファイルの表の更新など）。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `PROJECT_CONSTITUTION.md` の絶対禁止事項に反する設計をしてはならない。敵の種類・順番・入れ替わり・決着・攻防の計算はルール層（`js/rules/`）に置き、画面・エンジンに触れない。乱数はいまどおり外から渡されたもの（`Game` の `random`）を使う。描画の側（`js/view/`）・演出（`js/anim/`）・シーン（`js/scenes/`）は、ルール層の状態と攻防の結果を読むだけで、書き換えない。
*   **行動の決まりの拡張性** : 敵の行動の決まりは、敵の種類ごとの設定から選ばれる形にし、03-02・03-03 で「敵ごとの状態（数え下ろし・チャージ）」と「新しい行動の種類」を、既存の決まりを壊さずに足せる形にする。ただし、03-02 以降の行動・状態そのものは作らない（先回り実装の禁止）。
*   **配置は `layout.js` から読む** : ゴブリンの兵の群れ、シールドマークの並ぶ位置、敵を倒したときの案内の位置は、`js/view/layout.js` の戦闘の段の配置から求める（必要なら `layout.js` に足す）。描画・演出・シーンのファイルに座標の数値を直書きしない。
*   **時刻の式の二重化に注意** : 攻防の当たり・修理の時刻の式が `js/anim/battleCues.js` と `js/anim/battleTimeline.js` の2か所にある（`_doc/COWORK_STATUS.md`）。常時防御力の段を足すときは、両方を合わせて直す計画にする（または1か所にまとめる計画にしてもよい。その場合は理由を書く）。
*   **先回り実装の禁止** : 巨人の数え下ろし・回復、ドラゴンのブレスチャージ・ブレス・札を燃やすこと、巨人・ドラゴンの作り込んだ見た目、結果の画面と集計、タイトル画面（TITLE）の分離、最高記録の保存、敵ごとの演出の変化（兵が減って見える等）、BGM は作らない。
*   **エンジンの使い方** : 動きは `Scene` の `update(dt)` で進め、`draw` の中でシーンの状態を変えない（`oz/ENGINE_API.md`）。シーンの操作と `Engine.timeScale` の変更は `update`・`onPointer` の中で行う。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext`・`setTimeout`・`setInterval` を書かない。必要な機能がエンジンにないときは、回避策を書かずにRESに記録して作業を止める。
*   **変更してよい範囲** : 変更・追加してよいのは `js/rules/`・`js/anim/`・`js/view/`・`js/scenes/` の中のファイルとする（どのファイルを変えるかは計画に明記すること）。`oz/`・`index.html`・`js/main.js`・`js/ui/`・`js/audio/`・`assets/` は変更しない。変更が必要だと分かった場合は、計画の中で理由を書いて対象に加えるのではなく、RESの懸念事項に記して発注者の判断を仰ぐこと。
*   **1ファイル1責務** : 敵の種類の定義と行動の決まり、敵の進行（今の敵・次の敵・入れ替わり）、攻防の計算を、1つのファイルに詰め込みすぎない（`js/rules/Game.js` を肥大化させない）。新しいファイルを作る場合は、先頭に責務定義を書く。
