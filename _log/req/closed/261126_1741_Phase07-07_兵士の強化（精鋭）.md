## 【実装要件】
3択の強化に兵士の枠を足し、放った兵に強い兵（精鋭）が混じるようにする。

* 数値はすべて設定（ルールは `js/rules/config.js`、動きの時間は `js/anim/` の設定、配置は `js/view/` の配置の定数）に置き、下の値は初期値（試遊で変える）。
* 座標はすべて論理座標（画面 720×1280）で書く。画面の呼び名は TURN・ターン（内部の名前は phase）。スートの画面の呼び名は 剣（`sword`）・盾（`shield`）・ハンマー（`potion`）・金貨（`muscle`）。
* 敵・ステージの加算・疲弊・1ターンの流れ・3択の画面の流れ・ほかの枠の強化は変えない。**攻防の結果は「合計の引き算」のまま**（`battle.js` の `computeBattle` は変えない）。**強化を取らないゲームでは、放つ量・攻防の結果・予告・乱数の呼び出し（3択の抽選の分を除く）が変更の前と同じ**であること。

### 今の作り（現場設計で確かめたこと）
* **強化の仕組み**: 強化の一覧は `config.js` の `upgrades`（種類 → `{ slot, weight, effect, … }`）、枠は `upgradeSlots`（`castle: 1, troop: 1, card: 1, special: 0.5`）。兵士の枠（`troop`）にはまだ強化がなく、3択はいつも城・カード・特別から1つずつになっている。効き方の表 `upgradeEffects.js` の `UPGRADE_EFFECTS` は、どの行も全部の口（`canOffer`・`roll`・`fixedValue`・`take`・`untake`・`preview`・`cardBonus`・`comboSteps`・`allSuitsExtra`・`actionChance`・`isCapped`・`handSlots` など）を持つ。全種類の合計は `upgradeBoosts.js` が求める。設定には上限の回数 `maxCount`、上限に着いた後だけ出す `after` がある。アクションポイント（`actionChance`）は「5〜10% の整数・上限 50%・上限の手前では実際に増える分（`min(抽選, 上限 − 今の率)`）を出す・上限で出さない・率 0 では乱数を呼ばない」を実装済みで、精鋭の確率はこの形を参考にできる。文字は `upgradeText.js` の `UPGRADE_TEXTS`。
* **放つ**: `Game.release` が `computeRelease` の結果のゲージごとの量（札の数字 + 札の +◯ + 束の補正、4スートそろいの量）をゲージに足し、その後に山札の補充（乱数を呼ぶことがある）をする。演出は `releaseShow.js` が区切りの玉と4スートそろいの玉（`allSuitsTrack.js`）を飛ばし、着いた後の処理（`addArrival`）で陣地に兵（1人 = 1体 = 1ポイント）を出す。自動兵士はターンの始まりに `landAuto` で現れ、名簿で印（`TroopUnit.auto`・`markAutoTroops`）を持ち、薄いオレンジで描かれる（`troopView.js` の `autoTint`・`drawAutoFigure`・`:auto` の焼き付け）。ゲージ（攻撃・防御・修理）はターンの頭に 0 に戻る（金貨は残る）。
* **1体が複数のポイントを持つ仕組み（07-04b）**: 敵の側に作ってある。ルールの `unitPoints.js`、消し合いの組 `pointMatch.js` の `matchPoints`、体の割り振り `bodyPoints.js`、傷ついた姿（傾いて暗い）と当たりの「-N」。ただし `troopRoster.js` の `clashPairs` は組を丸ごと選ぶので、自軍の兵が複数のポイントを持つと、消し合う合計が出来事の量を超えうる（今は自軍が全員1ポイントなので起きない）。`battleFxView.js` の先頭のコメントに「-1」と決め打ちした言い回しが残っている。
* **人数の表示**: `troopCountView.js` が画面左上の枠（`layout.js` の `troopCounter`。x 20・幅 168・高さ 40）に、剣・盾・ハンマーの絵と数（`bold 20px`）を並べる。項目の幅は 52px で、数の欄は 24px しかなく、**今でも 100 以上で崩れる**（攻撃・防御の数が次の絵に約 9px 重なり、修理の数は枠から約 3px はみ出す）。敵の予告の札は画面の右寄り（敵の絵の中心 x 620 の上）にある。
* **山札**: 山札は4つで、スートごとに1つ（`createDecks`。並びは剣・盾・ハンマー・金貨）。`deckView.js` の `drawDeck` が描く。
* DEBUG タブの兵の数のスライダー（`debugTab.js` の `TROOP_SLIDER`。上限 99）は、その種類の兵の数（ゲージの値）を決める。説明の「理論上の最大 65」はカードの強化で古くなっている。`debugLayout.js` の説明（32・71・91・128 行目付近）と `upgrades.js` の JSDoc に「強化の +1」の古い言い方が残る。DEBUG の強化の「取る」のボタンは2列（`debugLayout.js` の `UPGRADE_COLS`）で、長い名前は 0.42 倍ほどまで横に縮む。

### 要件1: 兵士の強化（枠「兵士」）
* 種類と重み（`config.upgrades` に1行ずつ）:
    * **精鋭の確率**（剣・盾・ハンマーの各 2）: その種類の兵が精鋭になる確率。スートごとに持ち、初め 0%、1回取るごとに 5〜10%（整数。3択が出たときに決める）増え、上限 50%。上限の手前では実際に増える分を選択肢に出し、上限に着いたスートの確率は出さない。
    * **精鋭の能力 +1**（剣・盾・ハンマーの各 1）: その種類の精鋭のポイントが 1 増える。上限なし。そのスートの確率が 0% の間は出さない。
* 能力の初めの値は +1（取る前でも、精鋭は2ポイント）で、「精鋭の能力 +1」を取るごとに 1 増える。精鋭1体のポイント = 1 + 能力。
* 兵士の枠に強化が入るので、3択は4つの枠から重みで3つを選ぶ形になる（特別の枠は ≈54%、ほかの枠は ≈82% で出る。07-05 の枠の抽選の式のまま）。
* 選択肢の文字の目安（前後の値はルール層の `preview` が返したものを並べるだけ。文言は計画で整えてよい）:
    * 確率: 見出し「剣の精鋭 +7%」・説明「剣の兵が精鋭になる確率 10% → 17%」。**抽選の値が 9〜10 のときは、見出しの数字（「+9%」「+10%」）を金色にする**（上限の手前で実際に増える分が 9 未満になったときは金色にしない）。
    * 能力: 見出し「剣の精鋭の能力 +1」・説明「剣の精鋭 2ポイント → 3ポイント」。
    * 盾・ハンマーも同じ書き方。メニューの「強化」タブの行の目安:「剣の精鋭 17%・能力 +2」のように、スートごとに1行。

### 要件2: 精鋭の抽選（ルール）
* 精鋭は、放った時点で兵1人ずつ抽選で決まる。対象はカードから出る剣・盾・ハンマーの兵（札の数字・+◯・束の補正の分）と、4スートそろいで足された剣・盾・ハンマーの兵。**金貨・自動兵士は対象外。**
* 抽選は `Game.release` の中で、その種類の確率が **0 より大きいときだけ**、その種類の兵1人につきプレイ用の乱数を1回呼ぶ（確率 0 では呼ばない。強化なしのゲームの乱数の並びを変えないため）。呼ぶ順は決まった順（区切りの順 → 4スートそろいの順など。計画で決めて資料に書く）にし、放つ量が決まった後・山札の補充の前に呼ぶ。
* ゲージは「人数 + 精鋭の上振れ（精鋭の数 × 能力）」のポイントの合計にする（攻防の計算はこの合計で今のまま）。ゲームの状態として、ゲージごとの精鋭の数（または上振れ）を持ち、ターンの頭にゲージと一緒に 0 に戻す。放った結果（`release` の戻り値）に、区切り・4スートそろいごとに精鋭の数が分かる形で入れる（演出が使う）。
* 再開しても、精鋭の抽選は同じ結果になる（放つのは段取りの間で、中断データはターンの始まりと3択の段階に保存する。足した状態があれば中断データの扱いを見直し、形が変わるなら版を上げる）。

### 要件3: 精鋭の見た目と攻防の演出
* **見た目（発注者の決定）**: 精鋭は、ふつうの兵と同じ大きさ・同じ動きで、体の円の内側を青く塗る（自動兵士の薄いオレンジと同じ描き方。色は試遊で決め直す）。焼き付けも作る。自動兵士は精鋭にならないので、両方の色が重なることはない。
* 放った玉が陣地で兵に変わるとき、その区切り・4スートそろいの精鋭の数だけ精鋭（青）が現れる。
* **攻防**: ふつうの兵が先に、精鋭が後に当たる。精鋭は1回の当たりで、自分のポイントを、シールド・敵の守り → 敵の順に使う。盾の精鋭はそのポイントの分だけ敵兵を止め、ハンマーの精鋭はその分だけ直す。精鋭が敵に当たると「-2」のように当てたポイントが出る。攻防の結果（城・敵の HP、決着）は合計の引き算のままで、演出は見せ方だけを変える。
* 1体が複数のポイントを持つ仕組みは、07-04b のオーガで作ったもの（`matchPoints`・`bodyPoints.js`・当たりの「-N」）を使う。自軍が複数のポイントを持つので、`clashPairs` の最後の組を量で切るように見直す（消し合う合計が出来事の量を超えない）。精鋭とオーガ（2ポイント）がぶつかるときも、消し合う量が出来事の量と合う。
* 描く体の数は敵と兵を合わせて 500 体を目安とする（精鋭は1体なので、体の数は人数のまま）。

### 要件4: 人数の表示
* 数は「人数 + 上振れ」（ゲージの値）。精鋭による上振れがあるときは、数をオレンジにし、右下に「+◯」（上振れ）を数の約半分の大きさで出す（例「35」+ 小さな「+5」）。上振れがなければ今の見た目。攻防の間は、どちらも残りに合わせて減る（上振れは残っている精鋭の分）。
* **枠の広げ方（発注者の決定）**: 人数の表示の枠を右へ広げ（幅 168 → 約 290 を目安）、3つの項目それぞれに3桁の数と「+◯」（2桁）が収まるようにする。敵の予告の札・数え下ろし・最上部のゲージと重ならないこと（計画で配置を確かめる）。3択の画面の間は今どおり描かない。

### 要件5: 山札の角の表示
* 精鋭の確率が 0% より大きいスートの山札は、左下の角に「◯20%」（◯は青い丸）を出す。能力が +2 以上なら「◯20% +2」。確率が上限（50%）のとき、% の部分をオレンジにする。カードがめくれても（めくれの動きの間も）動かず、山札が空でも出る。金貨の山札には出ない。

### 要件6: DEBUG タブ
* 強化の「取る」ボタンは一覧から組み立てる（今のまま。兵士の強化の6種が増える）。上限に着いた確率は押しても何も起きない。
* **兵の数のスライダー（発注者の決定）**: スライダーで数を変えると、その種類の精鋭はなくなり、すべてふつうの兵になる（ゲージの値 = スライダーの値）。上限 99 はそのまま。`TROOP_SLIDER` の説明の「理論上の最大 65」を、今の扱い（上限は目安の値で、強化で超えうる）に直す。
* ボタンの数が増えるので、「取る」ボタンの文字が読めるか見直す（2列のままで縮みすぎるなら1列にする。`debugLayout.js` の `UPGRADE_COLS`）。`debugLayout.js` の説明と `upgrades.js` の JSDoc の「強化の +1」の古い言い方を、今のボタンの文字（「{名前} を取る（今 N 回）」）に合わせて直す。

### 要件7: 確かめ
* 確かめは一時スクリプト（スクラッチのフォルダ。リポジトリの外。終わったら消す）で行い、結果を各タスクの詳細作業内容に書く。`oz` は代用、`assets/` だけ解く `module.register` のローダーを使う（07-06 と同じ要領）。変更前のコードは `git archive`（本 REQ のコミット）をスクラッチへ展開して比べる（リポジトリの状態を変える git 操作はしない）。
* 強化を取らないゲームを変更前と並べて、毎手の結果・状態（予告・乱数の状態まで）が一致すること。
* 抽選の割合の目安（列挙で求めた期待値と比べる）: 4つの枠の重み 1・1・1・0.5 から3つで、特別の枠 ≈54.3%、ほかの枠 ≈81.9%。精鋭の抽選の割合が確率どおりであること（金貨・自動兵士が精鋭にならないこと）。
* 精鋭のいる攻防の時間割が Error なく作れ、当たりで消し合う合計が出来事の量（シールド・敵の守り・敵の HP・敵兵を止めた量・直した量）と一致すること（オーガが相手のときを含む）。精鋭のポイント・ゲージ・人数の表示の値が式どおりであること。
* ターンの始まりと3択の段階の保存・復元で、続けた結果が一致すること。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. 3択に兵士の枠（「剣の精鋭 +◯%」など）が出る。4つの枠のうち3つが出て、特別の枠はほかより出にくい。9〜10% の値は金色。確率が 0% のスートの「能力 +1」は出ない。
2. 精鋭の確率を取ったスートの山札の左下に「◯◯%」が出る（能力 +2 以上なら「+2」も）。上限 50% でオレンジになる。札がめくれても動かない。
3. そのスートの札を放つと、ときどき青い精鋭が陣地に現れる。金貨・自動兵士は精鋭にならない。4スートそろいで足された兵も精鋭になることがある。
4. 精鋭がいると、人数の表示の数がオレンジになり、右下に小さな「+◯」が出る。3桁になっても枠に収まり、予告の札と重ならない。
5. 攻防で、ふつうの兵が先に、精鋭が後に当たる。精鋭が敵に当たると「-2」のように出る。盾の精鋭はその分だけ敵兵を止め、ハンマーの精鋭はその分だけ直す。攻防の間、人数の表示の数と「+◯」が残りに合わせて減る。オーガが相手でも見た目と結果が合う。
6. 「精鋭の能力 +1」を取ると、精鋭のポイントが増える（当たりの「-3」など）。
7. メニューの「強化」タブで、精鋭の確率と能力が見られる。
8. 強化を取った後に閉じて開き直しても（ふつうのターン・3択の段階のどちらでも）、同じ状態で続けられる。
9. `?debug` の DEBUG タブで、兵士の強化を付けられ・すべて外せる。兵の数のスライダーで数を変えると、その種類はふつうの兵だけになる。ボタンの文字が読める。
10. スマホで、人数の表示・山札の角の文字が読める。終盤（兵と敵が多い状態）でも重くならない。PC とスマホで、タイトルから負けまで通しで遊べる。

AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   精鋭の抽選の乱数の順、自軍の複数ポイントの兵の消し合いの作り、強化の種類を足すときに書き足す所（兵士の枠を含む）が、資料から分かる形になっていること。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: ルール層（兵士の強化の一覧と効き方 → 精鋭の抽選とゲージ）→ 中断データ → 3択・「強化」タブの文字 → 人数の表示（枠の広げ方と「+◯」）→ 山札の角の表示 → 精鋭の見た目（青・焼き付け）→ 陣地に現れる精鋭 → 攻防の演出（消し合いの見直し・当たりの「-N」）→ DEBUG タブ のように、各タスクの終わりで起動とプレイが壊れない順・大きさに分ける。攻防の演出は大きいので、さらに分けられないか検討する。やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**: 精鋭の確率・能力・抽選・精鋭の数・ゲージの値はルール層で決め、画面と演出は状態と結果を読むだけにする（画面の側で足し算して値を作らない）。ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない（乱数は `game.random` だけ）。演出（精鋭の当たる順・「-N」・青）は結果を見せるだけで、結果を変えない。
*   **アーキテクチャの維持**: 強化の種類の識別子・スートの識別子で分岐する if を足さない（一覧の表と効き方の表で分ける）。新しい効き方は `UPGRADE_EFFECTS` に行を足し、表の口が足りなければ口を足す（今の効き方の行にも同じ口を足す）。強化で変わる値は `config.js` の値を書き換えず、ゲームの状態から求める。1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`Game.js`・`layout.js`・`BoardScene.js`・`troopRoster.js`・`battleTimeline.js` は大きいので、足す処理は分けて置けないか先に検討する。
*   **動きの時間**: 動きの時間は `dt`・時計だけで決め、状態は時計から求められる形にする。
*   **描画**: `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。新しいスプライトは作らない（精鋭の青・山札の角の青い丸はコードで塗る）。描く体の数は敵と兵を合わせて 500 体を目安とする。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **触るファイルの古い説明**: `battleFxView.js` の先頭のコメントの「-1」の決め打ち、`soundCues.js`・`bgmCues.js` の「はじめる」の古い説明が残っている（動作に影響なし）。同じファイルを触るなら一緒に直す。
*   **今回やらないこと**:
    *   スコア・ボーナス・結果の画面の作り直し、ベストの保存。
    *   メニューの「敵情報」タブ、3択の画面に次の敵の強さを出すこと。
    *   ほかの枠の強化（城・カード・特別）の値・重みの変更、ジョーカー・最大値の解放。
    *   金貨・自動兵士を精鋭にすること、精鋭の大きさを変えること。
    *   敵・ステージの加算・疲弊の値の変更、新しい音・曲、遊び方の文章の変更。
    *   `README.md`・`_doc/` の資料の書き換え。
