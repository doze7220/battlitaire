## 【実装要件】
倒した敵の数と、倒すのに使ったターン数を軸にしたスコアを入れ、負けたときの結果の画面を作り直す。

* 数値はすべて設定（ルールは `js/rules/config.js`、動きの時間は `js/anim/` の設定、配置は `js/view/` の配置の定数）に置き、下の値は初期値（試遊で変える）。
* 座標はすべて論理座標（画面 720×1280）で書く。画面の呼び名は TURN・ターン（内部の名前は phase）。スートの画面の呼び名は 剣（`sword`）・盾（`shield`）・ハンマー（`potion`）・金貨（`muscle`）。
* 攻防の計算・敵・ステージの加算・疲弊・強化・1ターンの流れ（段取り → 攻防）・3択の画面は変えない。**ゲームの進み方（放つ量・攻防の結果・予告・3択の候補・乱数の呼び出し）は変更の前と同じ**であること。スコアは数えて見せるだけで、乱数を呼ばない。

### 今の作り（現場設計で確かめたこと）
* **結果の集計（07-02）**: `gameStats.js` の `GameStats` は `{ enemiesDefeated, phases, damageDealt, damageTaken, healed }`。`Game.resolveBattle` が攻防の出来事の並びで `tallyBattle` を呼んで足す（`phases` は攻防の回数＝総ターン数）。`game.gameStats()` が写しを返し、中断データの項目 `stats` に入る。
* **攻防の出来事（`battle.js`）**: `enemyBlock`（敵の守りで止めた量 `min(攻撃, 敵の守り)`）、`enemyDamage`（敵の HP を減らした量。残りの HP で止まる）、`enemyDefeat`、`castleDamage`（城が受けたダメージ。0 より大きいときだけ出る）、`heal` など。攻撃の量は `resolveBattle` が渡すゲージの値 `gauges.attack`（07-07 から精鋭の上振れを含む）。修理（`heal`）は `castleDamage` の後に計算される。
* **戦闘のターン**: `game.battleTurn` は今の敵との戦闘で何ターン目か（`spawnEnemy` で 1 に戻り、`advancePhase` で敵が替わらなければ 1 足す）。敵を倒した攻防の中では、倒したターンの番号（倒したターンを含む、その戦闘で使ったターン数）。敵の★は `config.enemies[typeId].star`（1〜3）、ステージの番号は `game.stageNumber`。
* **放つ**: `release.js` の区切り（`ReleaseSegment`）は同じスートが続く束で、`count` が枚数。束は前の敵の間に列へ積んだものでも、放つのは今の敵の段取りの中（放った時点の `game.enemy` がその戦闘の敵）。
* **敵を倒したとき**: `resolveBattle` の結果の `defeat` は `{ enemyName }`。攻防の演出が終わると、戦闘の段に「（名前）を倒した！」とタップの案内が出る（`battleShowView.js` の `drawDefeat`。位置は `layout.js` の攻防の配置）。終わった後のタップで `BattleShowScene.goToUpgradeChoice` が `game.beginUpgradeChoice()` → 中断データの保存（3択の段階）→ 3択の画面（`UpgradeChoiceScene`）を積む。演出の途中のタップでは何も起きない。
* **負けたとき**: 攻防の演出が終わると、`BattleShowScene.draw` が結果の表示（`resultView.js` の `drawResult`。暗幕・板 600×696（`layout.js` の `RESULT_PANEL_*`）・「負け」・集計の5行・案内）を重ね、終わったときに中断データを消す。どこをタップしてもタイトルへ切り替わる（`Engine.changeScene(createTitle())`）。
* **保存**: `main.js` で1つの `Storage`（`key: 'battlitaire'`、`version: 1`）に、設定（`settingsStore.js`）と中断データ（`suspendStore.js` の `SUSPEND_DEFAULTS`）の名前を合わせて開く。`defaults` に名前を足すだけなら版を上げなくてよく、足した名前は既定値で始まる（ENGINE_API 22章）。**版を上げると設定も全部既定値に戻る**ので上げない。中断データは `suspendStore.js` だけが読み書きし、デバッグ（`Engine.debug`）では保存も読み込みもしない。中断データの版は `suspendData.js` の `SUSPEND_VERSION`（今は 5）。
* **日付**: 敵の並びの種 `game.seed` は、ゲームを始めた日の端末の日付（`dateSeed.js` の `todaySeed()`。年×10000＋月×100＋日。例 20261126）で、中断データに入り、再開しても変わらない。日付を読むのは `dateSeed.js` だけ。
* **取った強化の一覧**: メニューの「強化」タブは `game.takenUpgradeRows()` と `upgradeText.js` の `takenUpgradeLines(rows, anyTaken)` で行を作る（精鋭は確率の行に能力を並べる）。
* **敵の絵**: 3択の画面は次の敵の絵を `upgradeChoiceView.js` の `drawNextEnemy` で描く（群れの敵は体の絵3体、絵の敵はその絵のスプライト）。名前と Lv は `upgradeText.js` の `nextEnemyText(name, stageNumber)`。

### 要件1: スコア（ルール）
* 敵を倒したとき、その敵の点を次の合計で出し、スコアに足す。負けた敵（倒せなかった敵）の分は入らない。

    | 項目 | 点（初期値） |
    |---|---|
    | 討伐 | 500 ＋（ステージ番号 − 1）× 20 |
    | 強敵 | ★1: 0、★2: +200、★3: +400 |
    | ターン | 500 − 25 × その戦闘で使ったターン数（倒したターンを含む）。下限 0 |
    | コンボ | その戦闘で、同じスートが5枚以上続いた束を1回でも放っていれば +50 |
    | 無傷 | その戦闘で、城が1度も被害を受けていなければ +25 |

* コンボは、前の敵の間に積んだ束でも、その戦闘で放てば数える。同じ戦闘で何回放っても +50。枚数は区切り（`ReleaseSegment.count`）で数える（札の +◯ や束の補正の強化とは関係ない）。
* 無傷は、同じターンに修理で戻しても、城が被害（`castleDamage`）を受けていれば数えない。3択の「城を修理」は関係しない。
* 点の値（討伐の基本・ステージごとの足し分・★ごとの足し分・ターンの基本・1ターンごとの引き分・ターンの下限・コンボの枚数・コンボの点・無傷の点）は `config.js` に置く（ターンの下限は初め 0。試遊で −250 などに下げることがある）。
* **項目の一覧**: 点の項目（討伐・強敵・ターン・コンボ・無傷）は「戦闘の記録から点を出す」一覧（設定の表と、計算の表）で持ち、項目を1つ足すときは1行ずつ足す形にする。項目の識別子で分岐する if は書かない。敵を倒したときの内訳・結果の画面の内訳の並びもこの一覧の順から作る。
* **戦闘の記録**: 敵ごとに 0 から数える記録（その戦闘で使ったターン数・城が被害を受けたか・5枚以上の束を放ったか）を、ルール層のゲームの状態に持つ。敵が替わると（`enterStage`）新しい記録になる。点は敵を倒した攻防（`resolveBattle`）の中で記録から求め、スコアと内訳の合計に足す（3択の段階の保存より前）。
* **結果の記録**: 結果の集計を次の形に置き換える（いまの `damageDealt`・`damageTaken`・`healed` は使わなくなるので外す）。
    * 倒した数、総ターン数（攻防の回数。今の `phases`）、スコア
    * 内訳: 項目ごとの合計点と、取った回数（結果の画面ではコンボ・無傷の回数を出す）
    * 倒した敵の並び（倒した順に、敵の種類とステージの番号）
    * 最大の一撃: 1回の攻防で、攻撃の量から敵の守りで止めた量を引いた量（`gauges.attack − enemyBlock の量`）の最大。とどめのターンで敵の残りの HP を超えた分も含む。点にはしない
    * 一番長いコンボ: 放った区切りの枚数（`count`）の最大（ゲーム全体。敵をまたぐ）。点にはしない
* 結果の記録とスコアは、ルール層の問い合わせ（写しを返す）で画面へ渡す。画面の側で点を足し算しない。

### 要件2: 中断と再開
* スコア・内訳・倒した敵の並び・最大の一撃・一番長いコンボ・今の戦闘の記録を中断データに入れ、ターンの始まりと3択の段階のどちらから再開しても、同じスコア・記録で続く。
* 状態の形が変わるので、`suspendData.js` の `FIELDS` を直し（足す・形を確かめる）、`SUSPEND_VERSION` を 6 に上げる（版 5 のデータは読み捨てて新しいゲームから始まる）。

### 要件3: 敵を倒したときの内訳
* 敵を倒した攻防の演出が終わると、戦闘の段の「（名前）を倒した！」の下に、その敵の点の内訳を「討伐 500／ターン +400／コンボ +50／無傷 +25」のように出す。取れなかった項目（0 点の項目。★1 の強敵、下限に着いたターンなど）は出さない。続けて、その敵の点の合計と、今のスコアの合計を出す（例「+975　SCORE 3,250」。並べ方・文字は計画で決めてよい）。
* 項目は1つずつ順に出てくる（1つの間の目安 200ms。`js/anim/` の設定。演出の速さの設定に合わせてよい）。出そろう前のタップでは何も起きず、出そろった後のタップで今と同じく3択へ進む（タップの回数は今と同じ1回）。タップの案内は出そろった後に出す。
* 戦闘の段（高さ 360）の中で、「倒した！」・内訳・合計・タップの案内が重ならず、スマホで読める大きさにする（配置は `layout.js`、文字は `battleText.js` などの view の文字の表）。
* 内訳の値は、ルール層が倒した攻防の結果（`defeat` に足す、または問い合わせ）として渡し、画面はそれを読んで文字にするだけ。
* 3択の段階から再開したときは、内訳は出さない（3択の画面から始まる。今と同じ）。

### 要件4: 結果の画面
* 城が落ちて攻防の演出が終わると、結果の画面が出る。今の結果の表示（`drawResult`・集計の5行・どこを押してもタイトルへ）は、この形に置き換わる。中断データを消す時期は今と同じ。
* 画面全体を暗くし、その上に板を出す。**板の高さは画面の高さの約 8 割（1280 × 0.8 ≈ 1024）**に広げる（幅は今の 600 を目安に計画で決めてよい）。中身が板に収まらないときは、中身の部分を指で縦にスクロールして見られる（項目は減らさない）。「もう一度」「タイトルへ」の2つのボタンは板の下に固定し、スクロールしなくても押せる。スクロールはエンジンの窓のスクロールする領域（26章）を使っても、ゲームの側で作ってもよい（計画で決め、理由を書く。エンジンの機能で足りないことがあれば、回避策を書かずに止めて RES に記録する）。
* 中身は上から次の順に並べる。
    1. 倒した数とスコア（一番大きく）。今の「負け」の見出しは残してよいが、倒した数とスコアより目立たせない。
    2. 内訳: 討伐・強敵・ターン・コンボ・無傷の合計点（コンボ・無傷は取った回数も。例「コンボ ×3　+150」）と、総ターン数。
    3. 倒した敵の絵の並び（倒した順に小さな絵を並べ、多いときは折り返す）と、最後に負けた敵（絵・名前・Lv。倒した敵と区別できるように）。絵の描き方は3択の画面の次の敵の絵（群れの敵は体の絵、絵の敵はそのスプライト）を使う。新しいスプライトは作らない。
    4. 取った強化の一覧（`takenUpgradeRows` と `takenUpgradeLines` から。1つも取っていなければ、そのことが分かる1行）。
    5. 最大の一撃・一番長いコンボ（点にはしない、と分かる見せ方でなくてよい）。
    6. 今日のベストと自己ベスト（スコア）。今回のスコアで更新したら、その行に「NEW」を出す。
* 「もう一度」を押すと、タイトルの「はじめる」と同じく新しいゲーム（その日の日付の種）が始まる。「タイトルへ」を押すとタイトルへ戻る。ボタンは押して離したときに反応する（今のタイトルのボタン・メニューの窓と同じ）。板の外や中身を押しても何も起きない。
* 結果の画面の文字は view の文字の表（`battleText.js` か新しい文字のファイル）に置く。配置・色・フォントは view の定数。ルール層は import しない（型の参照だけ）。

### 要件5: 今日のベストと自己ベスト
* 自己ベスト（これまでで一番高いスコア）と今日のベスト（日付と、その日のゲームで一番高いスコア）を保存し、ページを開き直しても残る。
* 「今日」は**ゲームを始めた日の日付**（`game.seed`）。日をまたいで遊んでも、始めた日のベストとして数える。保存してある今日のベストの日付がそのゲームの日付と違えば、その日のベストはまだない（0）とみなして比べ、そのゲームの日付で書き換える。
* 負けて結果が決まったとき（中断データを消すのと同じ時期に1回）、今回のスコアがベストより高ければ書き換え、その行を NEW にする（同じ点は更新しない・NEW にしない）。
* 保存は新しい名前を今の `Storage` の `defaults` に足して行う（`Storage` の版は上げない。設定が既定に戻らない）。読み書きは1つのファイル（新しい `js/scenes/` のモジュール。`suspendStore.js` と同じ形）だけが行い、形が壊れた値は「ベストなし」として扱う。
* **デバッグ（`?debug`）では保存も読み込みもしない。** 結果の画面のベストの欄は、デバッグでは記録しないことが分かる1行にする（現場設計の決定）。

### 要件6: 確かめ
* 確かめは一時スクリプト（スクラッチのフォルダ。リポジトリの外。終わったら消す）で行い、結果を各タスクの詳細作業内容に書く。`oz` は代用（`Engine`・`Scene`・`Storage`・`Ui` などの最小の代わり）、`assets/` だけ解く `module.register` のローダーで `js/` を読む（07-07 と同じ要領）。変更前のコードは `git archive`（本 REQ のコミット）をスクラッチへ展開して比べる（リポジトリの状態を変える git 操作はしない）。
* 変更前と並べて、ランダムな操作のゲーム（強化を取るものを含む）で毎手の結果・状態（予告・乱数の状態・3択の候補まで）が一致すること（結果に足した項目と、結果の記録は比べない）。
* 点の計算: 手で作った戦闘（ステージ 1・★2・★3、ターン数 1・20・21 以上、5枚の束を前の敵の間に積んで次の敵で放つ、4枚の束だけ、城が被害を受けて修理で戻したターンあり）で、点と内訳が表のとおりであること。負けた敵の分が入らないこと。最大の一撃・一番長いコンボが式どおりであること。
* ターンの始まりと3択の段階の保存・復元で、続けたスコアと記録が一致すること。版 5 のデータが読み捨てられること。
* ベスト: 代用の `Storage` で、初めて・更新・同点・別の日・壊れた値・デバッグ（読み書きしない）の場合を確かめる。
* 起動とプレイが壊れないことの確かめ（画面に関わるタスクの終わりに行う）: 代用の `oz` のローダーで `js/main.js` から辿るモジュールがすべて読み込めることと、`BoardScene` から攻防・敵を倒したときの内訳・3択・負け・結果の画面（スクロール・2つのボタン）までを数ゲーム Error なく進められ、代用の `ctx` で `draw` が Error なく `save`/`restore` が釣り合うこと。倒した敵が多い（30 体など）ときに結果の画面の中身がスクロールで全部見られること。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. 敵を倒すと、「〜を倒した！」の下に、取れた項目だけの内訳（「討伐 500／ターン +400／コンボ +50／無傷 +25」など）が1つずつ出て、その敵の点と今のスコアが出る。出そろってからタップすると3択になる。
2. 5枚以上の同じスートの束を放った戦闘ではコンボ +50、城が1度も被害を受けなかった戦闘では無傷 +25 が出る。被害を受けて修理で戻した戦闘では無傷が出ない。★2・★3 の敵では強敵の点が出る。
3. 3択の段階やふつうのターンで閉じて開き直しても、スコアが続いている（倒した後の内訳は出ない）。
4. 城が落ちると、結果の画面が出る。倒した数とスコアが一番大きく、内訳・総ターン数・倒した敵の絵の並びと負けた敵・取った強化・最大の一撃・一番長いコンボ・今日のベストと自己ベストが見られる。
5. 板は画面の高さの約 8 割で、収まらないときは指で縦にスクロールできる。「もう一度」「タイトルへ」はいつも押せる。
6. 「もう一度」で新しいゲームが始まり、「タイトルへ」でタイトルに戻る。
7. ベストを更新すると「NEW」が出る。開き直しても今日のベストと自己ベストが残っている。設定（音量・演出の速さ）が既定に戻っていない。
8. `?debug` では、ベストが保存されず、結果の画面にデバッグでは記録しないことが出る。
9. スマホで、内訳と結果の画面の文字が読め、スクロールとボタンが使える。PC とスマホで、タイトルから負けまで通しで遊べる。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   点の項目を足すときに書き足す所と、ベストの保存の置き場所が資料から分かる形になっていること。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: ルール層（戦闘の記録と点・結果の記録）→ 中断データ → 敵を倒したときの内訳 → ベストの保存 → 結果の画面（配置と中身 → スクロールとボタン）のように、各タスクの終わりで起動とプレイが壊れない順・大きさに分ける。やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**: 点・内訳・結果の記録・最大の一撃・一番長いコンボはルール層で決め、画面は状態を読むだけにする。ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない（「今日」はゲームの種 `game.seed` で表す）。ベストの読み書き（`Storage`）は `js/scenes/` の1つのファイルだけ。
*   **アーキテクチャの維持**: 点の項目の識別子・敵の種類の識別子で分岐する if を足さない（一覧の表で分ける）。1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`Game.js`・`layout.js`・`BoardScene.js`・`BattleShowScene.js` は大きいので、足す処理は分けて置けないか先に検討する（戦闘の記録と点の計算は新しいルールのファイルに置くなど）。
*   **動きの時間**: 内訳が順に出る動きの時間は `dt`・時計だけで決め、状態は時計から求められる形にする。
*   **描画**: `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。新しいスプライトは作らない。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **保存**: `Storage` の `key`・`version` は変えない（版を上げると設定が既定に戻る）。ベストは `defaults` に名前を足して持つ。
*   **今回やらないこと**:
    *   段取りの画面（盤面）やメニューに今のスコアを出すこと（発注者の決定。スコアは倒したときの内訳と結果の画面だけで見せる）。
    *   点の値・ターンの下限の調整（07-09 の試遊で行う）。
    *   スコアのランキング・送信、過去のゲームの履歴の一覧。
    *   メニューの「敵情報」タブ、3択の画面に次の敵の強さを出すこと。
    *   強化・精鋭・敵・ステージの加算・疲弊の値や動きの変更、新しい音・曲、遊び方の文章の変更。
    *   `README.md`・`_doc/` の資料の書き換え。
