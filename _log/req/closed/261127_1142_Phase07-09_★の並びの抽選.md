## 【実装要件】
ステージの★（1〜3）を、ステージの番号の倍数で決めるのをやめ、**ステージごとの抽選で決める**。強敵（★2・★3）の間隔を 2〜4 ステージほどに縮め、ときどき強敵が2連続する並びにする。
* **狙い**: 発注者の試遊で「ザコ（★1）が続きすぎて間延びする」と分かった。強敵が今より多く、間隔が読めない並びにする。

**決まりごと**
* **数値の置き場所**: 数値はすべて設定（`js/rules/config.js`）に置く。下の値は初期値で、試遊で変える。
* **呼び名**: 画面の呼び名は TURN・ターン（内部の名前は phase）。
* **変えないもの**: 敵の数値・動き・見た目、ステージの加算と疲弊、攻防、強化、スコア、1ターンの流れ、ほかの機能。

### 今の作り（現場設計で確かめたこと）
* **★の決め方**: `stageOrder.js` の `starOfStage` が、設定 `config.stageStars`（`base: 1`・`multiples: [{ of: 10, star: 3 }, { of: 5, star: 2 }]`）から、ステージの番号の倍数で★を決める。
  * 10 の倍数は★3、それ以外の 5 の倍数は★2、残りは★1。
* **同じ★の何番目か**: `starPositionOfStage` が、倍数の周期から「同じ★のステージの中で何番目か」を、前のステージを計算せずに求める。
* **敵の種類**: `enemyTypeIdOfStage(config, seed, stageNumber)`。
  1. ★を決める。
  2. 同じ★の動きの組（`enemyMotionsOfStar`）から、何番目かと種で動きを選ぶ（`motionIndexAt`）。同じ★の中で同じ動きが隣り合わない。
  3. 動きの中の敵を、種とステージの番号で選ぶ（`seededIndex` の `STREAM.member`）。
* **種**: ゲームを始めた日付の種（`Game.seed`。`dateSeed.js`）。同じ日なら、誰が何度始めても同じステージには同じ敵が出る。
* **★の敵**: ★1 は6種（ゴブリンの軍勢・オーガの軍勢・狼・猪の親子・骸骨の軍勢・スライム）。★2 は巨人、★3 はドラゴンの1種ずつ。
* **並びを使う所**:
  * `Game.enterStage`（ステージの敵を出す）。
  * `Game.nextStageEnemy`（3択の画面の「次の敵」）。
  * DEBUG のステージ移動（`debugControls.js` の `moveStage`。−5・−1・+1・+5）。
* **中断データ**: 版 8。`seed`・`stageNumber`・今の敵を持つ（並びそのものは持たない）。

### 要件1: ★の抽選（ルール）
* ★は、ステージごとの抽選で決める（07-02 の倍数の決まりを置き換える）。
  * 先に★3を抽選し、外れたら★2を抽選する。どちらも外れたら★1。
* **★3の確率**:
  * ★3が出た次のステージは 0%。
  * その後、1ステージごとに 8% ずつ上がる。
  * ★3が出たら 0% に戻る。
* **★2の確率**:
  * ★2が出た次のステージは 0%。
  * その後、1ステージごとに 30% ずつ上がる（100% で頭打ち）。
  * ★2が出たときと、★3が出たときに 0% に戻る。★2が出ても、★3の確率は戻さない。
* **ゲームの始まり**: ★2・★3が出た直後とみなす。
  * ステージ 1 はかならず★1。
  * ステージ 2 は★3が 8%・★2が 30%。
* **上がる量**: ★3の 8%・★2の 30% は設定で変えられる。
  * 確率は百分率の整数で持ち、抽選も整数で比べるなど、浮動小数の誤差で並びが変わらない形にする。
  * 設定の形（★の数の並び、上がる量、どの★で戻るか）は計画で決める。★の識別子で分岐する if は書かない。
* **抽選の乱数**: 日付の種から求める（プレイ用の乱数は使わない）。
  * 同じ日付なら、誰が何度始めても同じ並びになる。
  * DEBUG で途中のステージへ移っても、中断から再開しても、同じ並びになる。
  * 新しい抽選は前のステージの結果で確率が変わるので、ステージ 1 から順に抽選して求める形になる。ステージ 1000 ほどまで、ゲームが重くならない速さで求められること（求め方・覚えておき方は計画で決める。ルール層は純粋なまま、同じ種と番号には同じ★を返す）。
  * 抽選に使う用途の鍵は、今の `STREAM`（`member`・`last`・`first`・`middle`）と別にする。

### 要件2: ★の中の敵の並び
* 同じ★の中の動き・敵の選び方（07-04a の「同じ敵・同じ動きを続けない」決まり）は、そのまま使う。
  * 同じ★の中の何番目かは、抽選で決まった★の並びから数える（ステージ 1 から、同じ★のステージを数える）。
  * 今と同じく、同じ★の敵は、間に別の★を挟んでも続いているとみなす（★1の動きは、巨人・ドラゴンを挟んでも隣り合わない）。
* **最初の強敵**: 毎回のプレイで、最初に出る★2は巨人、最初に出る★3はドラゴンにする。
  * P7 では★2・★3が1種ずつなので、何もしなくてもこのとおりになる。
  * P8 で★2・★3の種類を増やしても守られる決まりとして作る（例: ★ごとに「最初の1体」を設定に持つ）。
  * 敵の識別子で分岐する if は書かない（設定・表で持つ）。
* ★1・★2・★3のどれかの敵がいない設定では、今と同じく Error にする。

### 要件3: 使う所と中断データ
* 並びを使う所（ステージの敵・3択の「次の敵」・DEBUG のステージ移動）は、新しい並びを使う。呼び方は今と同じ `enemyTypeIdOfStage` でよい。
* **中断データ**（発注者の決定）: 形は変えず、版は上げない。
  * 抽選の前に始めた途中のゲームは、そのまま続けられる。今の敵はそのままで、次のステージから新しい並びになる。
  * 計画で中断データの形を変える必要が出たときは、版を上げて（9）RES に理由を書く。
* ステージの加算（`stageBonus.js`）は今のままステージの番号で決まる（★の並びが変わっても加算は変わらない）。
* スコアの「強敵」の点は、今のまま敵の★で決まる。

### 要件4: DEBUG タブ
* **先の並びの一覧**（発注者の決定）: DEBUG タブに、今のステージから先の 20 ステージほどの並びを出す。
  * 1行に、ステージの番号・★・敵の名前。
  * 今のステージが分かるようにする（例: 色を変える）。
  * ステージを移ると一覧も合わせて変わる。
  * 置き場所・文字の大きさ・行の数は計画で決めて RES に書く。DEBUG タブのほかの部品が使いにくくならないようにする。
* **ルールの値**: ★3・★2の上がる量を、ルールの値のスライダーに出す（「元に戻す」で戻る）。
  * 値を変えると、先の並び（一覧・次のステージ以降）が変わる。今の敵は変えない。
  * 変えた値の効く時期の表示は、今のルールの値の決まり（`debugRules.js` の `ruleTiming`）に合わせる。

### 要件5: 確かめ（一時スクリプトで行い、結果を RES に書く）
* **割合と間隔**: 多くの種で 30 万ステージほど並べ、次が DIR の試算と合う。
  * ★1 約 60%・★2 約 21%・★3 約 19%。
  * 強敵の間隔: 1ステージ（2連続）約 15%・2ステージ約 37%・3ステージ約 33%・4ステージ約 13%。
  * ★3は平均で約 5 ステージに1回。
* **決まりどおりか**: どの種でも次が守られる。
  * ステージ 1 は★1。
  * ★3の確率・★2の確率が、要件1のとおりに上がり、戻る（数え直して比べる）。
  * 最初の★2は巨人、最初の★3はドラゴン。
  * ★1の動きが隣り合わない（★2・★3を挟んでも）。
* **同じ並び**: 次で、同じ種なら同じ並びになる。
  * ステージ 1 から順に求めた並び。
  * 途中のステージだけを求めた並び（順を変えて求めても同じ）。
  * DEBUG のステージ移動。
  * 中断データから戻したゲーム。
* **速さ**: ステージ 1000 の敵を求める時間を測って書く。
* **変わっていないこと**: 同じ乱数の状態から比べて、並び以外（敵の数値・予告・攻防・強化・スコア）が変更の前と同じになる（同じ敵が出たステージで比べる）。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. **強敵の間隔**: `?debug` を付けずに遊ぶと、強敵（巨人・ドラゴン）が 2〜4 ステージほどの間隔で出て、ときどき2連続する。ザコが長く続かない。
2. **始まり**: ステージ 1 はかならずザコ。最初の強敵は、★2なら巨人、★3ならドラゴン。
3. **同じ並び**: 同じ日に何度始めても、同じステージには同じ敵が出る。
4. **3択の「次の敵」**: 3択の画面に出る次の敵が、実際に次のステージで出る敵と同じ。
5. **DEBUG の一覧**: DEBUG タブに、先の 20 ステージほどの★と敵の名前が並ぶ。ステージを移ると一覧も変わり、移った先の敵が一覧と同じ。
6. **DEBUG のスライダー**: ★3・★2の上がる量を変えると、先の一覧が変わる。「元に戻す」で戻る。
7. **中断と再開**: 途中で閉じて「再開」しても、続きのステージの敵が一覧と同じ。抽選の前に保存していた途中のゲームも、続けて遊べる。
8. **ほかの機能**: 敵の強さ・攻防・強化・スコア・結果の画面は前と同じように動き、タイトルから負けまで、PC とスマホで通しで遊べる。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: 各タスクの終わりで、起動とプレイが壊れない順・大きさに分ける。
    *   順の例: ルール層（★の抽選と何番目か。まだ使う所は今のまま）→ 並びの切り替え（`enemyTypeIdOfStage`）→ DEBUG のルールの値 → DEBUG の先の並びの一覧。
    *   やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**:
    *   ★の抽選・並びはルール層の純粋な計算で決める。画面（DEBUG の一覧）はルール層の関数の結果を読むだけにする。
    *   ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない（種は今と同じく引数で受け取る）。
*   **アーキテクチャの維持**:
    *   敵の種類・★の識別子で分岐する if を足さない（設定・表で分ける）。
    *   1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`Game.js`・`layout.js`・`debugTab.js` は大きいので、足す処理は分けて置けないか先に検討する。
    *   使わなくなる関数・設定（`starOfStage` の倍数の決まり・`starPositionOfStage` の周期の計算・`stageStars.multiples`）は、残さず整理する（ほかから使われていないことを確かめる）。
*   **描画**:
    *   `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。
    *   `js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。
*   **エンジンの使い方**:
    *   エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。
    *   必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **今回やらないこと**:
    *   ★2・★3の敵の追加と、種類が増えたときの出し分け（最初の1体を固定するほかは P8）。
    *   序盤の歯止め（序盤にドラゴンが出ないようにすること。発注者の判断で入れない）。
    *   敵の数値・ステージの加算・疲弊・強化・スコアの値の調整（07-10 で行う）。
    *   古いままの説明コメントの直し（07-10 で行う）。
    *   遊び方の4ページ目に敵を足すこと。
    *   `README.md`・`_doc/` の資料の書き換え。
