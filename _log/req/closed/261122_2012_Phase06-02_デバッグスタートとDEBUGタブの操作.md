## 【実装要件】
1つの定数で入り切りできるデバッグの入口（タイトル画面の「デバッグスタート」）を作り、デバッグスタートから始めたゲームでだけ、メニューの窓に DEBUG タブを出す。DEBUG タブから、兵の数・敵・敵の次の行動・城と敵の HP を操作でき、FPS の表示を出し入れできるようにする。

* 座標はすべて論理座標（画面 720×1280）で書く。部品の大きさや位置は定数に置き、試遊で決め直す値と書く。
* タイトルからクリア・負けまで、通しで遊べること（定数が ON でも OFF でも）。スマホの縦画面を優先し、PC でも同じように使えること（タップ（クリック）だけで使え、ホバーに頼らない）。
* ルールの数値（`js/rules/config.js`）は変えない。

*   **要件1: デバッグを有効にする定数**
    *  デバッグを有効にする定数を**1つ**、1か所に置く（置き場所・名前は計画で決める。ルールの設定ファイル `config.js` ではない）。
    *  **コミットするときの値は ON**（発注者の決定。Phase 06 の間は ON のまま、試遊でそのまま使う。OFF にするのは後のサブフェイズ）。
    *  定数が **OFF** のとき: タイトル画面に「デバッグスタート」が出ない（描かれず、その位置を押しても何も起きない）。DEBUG タブはどこにも出ない。FPS の表示は出ない（起動設定 `debug` は使わず、`Engine.fpsVisible` は既定の `false` のまま）。デバッグの操作はどこからも呼ばれない。OFF のときのタイトル画面・メニューの窓・盤面は、今（06-01 の後）と同じ見た目と動きになる。
    *  OFF のとき、デバッグ用のファイルを読み込まないところまでは求めない（動的 `import` にしなくてよい。静的 `import` で読み込んでも、入口が出ず操作が呼ばれなければよい）。ただし、OFF にしたときに消し忘れが起きないよう、定数を読む場所を少なくまとめる。
*   **要件2: タイトル画面の「デバッグスタート」**
    *  定数が ON のとき、タイトル画面の「設定」ボタンの下に「デバッグスタート」ボタンを出す。見た目は「遊び方」「設定」と同じ縁だけのボタンにする（文字は「デバッグスタート」。文字は `js/view/titleText.js` に置く）。配置（`createTitleLayout`）と当たり判定（`titleHitTest`）に足す。画面の下にはみ出さず、ほかのボタンと重ならないこと。
    *  押して同じボタンの中で離したとき（「はじめる」と同じ押し方）に、「はじめる」と同じゲームが始まる（同じ盤面・同じ最初の敵・タイトルの曲の止め方も同じ）。違いは、そのゲームで開くメニューの窓に DEBUG タブが出ることだけである。
    *  ふつうに「はじめる」から始めたゲームでは、DEBUG タブは出ない。タイトル画面の「設定」から開いたメニューの窓にも、DEBUG タブは出ない。
    *  デバッグスタートから始めたゲームが決着してタイトルに戻ったら、次のゲームはまた「はじめる」か「デバッグスタート」のどちらで始めたかで決まる。
*   **要件3: DEBUG タブ**
    *  デバッグスタートから始めたゲームで、盤面の TURN の区画からメニューの窓を開いたとき（段取りの間）に、タブの列の**一番右**に「DEBUG」を出す（並びは「設定」「クレジット」「DEBUG」）。窓は今と同じく毎回「設定」から始まる。
        *  06-01 の作り: メニューの窓は `js/scenes/MenuScene.js`（窓だけを持つ）、標準のタブの一覧は `js/scenes/menuTabs.js` の `createMenuTabs()`、窓は `js/main.js` の `createMenu()` で作っている。DEBUG タブは、タブの一覧の後ろに足す形にすれば、窓（`MenuScene.js`）と標準のタブの一覧（`menuTabs.js`）を書き直さずに済む（06-01 の申し送り）。デバッグスタートかどうかを盤面のシーンからメニューを作る関数へどう伝えるかは計画で決める。
    *  項目が窓に収まらないので、DEBUG タブの中は**スクロールする領域**（`addScroll`）にまとめてよい。並び順・大きさは計画で決め、定数に置く（試遊で決め直す値）。スクロールする領域の中のスライダーの受け方（26章。縦に動かすとスクロール、横に動かすと値が変わる）に注意する。
    *  DEBUG タブで操作した結果は、窓を閉じた後の盤面にそのまま出る（窓を開いている間は背面の動きが止まっているので、閉じた後に見えてよい）。
    *  DEBUG タブの操作は、行動の回数を使わない。TURN の番号・山札・捨て札・列・手札・金貨のゲージは変えない（下の各要件で変えると書いたものだけを変える）。
    *  DEBUG タブで操作した後も、ゲームはそのまま続けて遊べる。攻防の結果・決着・次の敵への進み方は、ふつうのルールのとおり（操作した値から、ふつうに計算される）。
*   **要件4: 兵の数**
    *  攻撃・防御・修理の兵の数を、種類ごとに**スライダー**（`addSlider`）で決める（発注者の決定）。範囲は **0〜63**、刻みは 1。値の文字は数（例: 「63」）。
    *  兵の数はゲージの値（攻撃＝`attack`、防御＝`defense`、修理＝`heal`）である。スライダーで決めた数が、その種類のゲージの値になり、次の攻防でその数の兵として使われる。
    *  決めた数の兵が、**その場で陣地に並ぶ**（玉は飛ばない。減らしたときは、その種類の兵が減る）。並び方・大きさは、ふつうに放って兵が着いたときと同じ決まり（数によって大きさが変わる、など）に従う。
    *  **兵の数の上限（63）の根拠**（DIR の「理論上の最大まで」をルールの値から求めた）: 各スートの札は 1〜7 の 7 枚で、1回に放つ同じスートの区切りの加算量は最大 28 + 補正 6 = 34。攻撃・防御・修理のゲージはフェーズの終わりに 0 に戻るので、1フェーズの中で決まる。行動は最大 7（基本 5 + 金貨の換算で最大 +2）。前のフェーズまでに 1 つの列に同じスートの 7 枚（7〜1）を積んでおき、放つ（行動 1、+34）→ 補充された山札から 5 枚（7・6・5・4・3）を置く（行動 5）→ 放つ（行動 1、25 + 4 = +29）で、1種類あたり最大 **63**。3種類の合計の理論上の最大は **131**（28 枚を列に積んでおき、攻撃・防御・修理の区切りを 1 回で放つ（+34×3）→ 5 枚を置いて放つ（+29））。スライダーは種類ごとに 63 まで動かせるので、3つを最大にすると合計 189 になり、理論上の最大より多くなる（重さを測る Phase 06-04 では、それで足りる）。
    *  **玉が飛んでいる途中・兵が陣地へ向かっている途中**に窓を開いて兵の数を変えた場合も、窓を閉じて動きが終わった後に、**画面の兵の数と、攻防で使われる数（ゲージの値）が食い違わない**こと。どう合わせるか（例: 動いている間は兵の数を変えられないようにし、そのことが分かる表示にする、など）は計画で決める。
*   **要件5: 敵の切り替え**
    *  今の敵を、選択肢の列（`addChoices`。横に並べる）で「ゴブリンの軍勢」「巨人」「ドラゴン」から選んで切り替える（`config.js` の `enemyOrder` の順。名前は敵の種類の設定の `name`）。今の敵が選ばれている見た目になる。
    *  切り替えると、**その場で敵が入れ替わる**（発注者の決定。ステージの始まりの演出（敵が入ってくる・STAGE と名前）は出さない）。
        *  新しい敵は HP が満タンで、行動の決まりの状態は初期値。次の行動の予告は、新しい敵の決まりでふつうに決める（巨人なら数え下ろしも表示される）。
        *  新しい敵の段取りの間の見た目（ゴブリンの群れ・巨人・ドラゴンの待機の動き、予告の札、HP のゲージ）に、窓を閉じたときには変わっている。
        *  BGM は新しい敵のステージの曲にする（`bgmCues.js` の `playStageBgm`。ゴブリンと巨人は同じ曲なので、その間の切り替えでは曲が流れたままでよい）。
        *  敵の順番は、切り替えた敵から続く（巨人に切り替えて倒すと次はドラゴン、ドラゴンを倒すとクリア）。TURN の番号・城の HP・盤面・兵の数はそのまま。結果の集計（フェーズ数・総ダメージなど）は変えない。
    *  今の敵と同じ敵を選んでも何も起きない（選択肢の列は同じ値では `write` を呼ばない）。
*   **要件6: 敵の次の行動の指定**
    *  今の敵の**次の行動**（予告）を、選択肢の列で指定する。選択肢は、そのときの敵が取る行動だけにする。
        *  ゴブリンの軍勢: 「攻撃」「防御」
        *  巨人: 「振りかぶり」「攻撃」「攻撃して回復」（発注者の決定。「攻撃して回復」は、その攻撃の直後に必ず回復する。回復の量は `config.js` の巨人の回復の量で、最大 HP で頭打ちになるのはふつうと同じ。「攻撃」は、回復するかをふつうどおり抽選する）
        *  ドラゴン: 「爪」「吸い込む」「ブレス」
    *  指定すると、予告がその行動に変わり、敵の頭の上の予告の札にすぐ出る（窓を閉じたときには変わっている）。行動の量（攻撃・防御の値、ブレスで燃やす札の枚数）は、ふつうに予告を決めるときと同じく、`config.js` の幅から抽選する。
    *  指定した行動の**後の続き方**は、その行動をふつうに選んだときと同じにする。
        *  ドラゴン: 「吸い込む」の次は必ずブレス、「ブレス」の次は爪、「爪」の次はふつうの抽選。
        *  巨人: 「攻撃」「攻撃して回復」を指定したら、数え下ろしは 0（このフェーズで攻撃する）になり、攻撃の後は周期の頭（振りかぶり）から始まる。「振りかぶり」を指定したら、周期の頭（攻撃まで残り 周期 − 1）からやり直す。数え下ろしの表示もそれに合う。
    *  今の予告と同じ行動を選んでも何も起きない（量の抽選もやり直さない）。今の予告に当たる選択肢が選ばれている見た目にする（巨人の「攻撃」と「攻撃して回復」のどちらが選ばれて見えるかは、指定したかどうかで分かるようにする）。
    *  窓を開いたまま要件5で敵を切り替えたときも、次の行動の選択肢が新しい敵のものになる（窓の部品は足した後に消せないので、作り方は計画で決める。例: 敵ごとの選択肢の列を並べて今の敵の分だけ効かせる、選択肢の `label` を関数にする、など）。
*   **要件7: 城と敵の HP**
    *  城の HP と敵の HP を、それぞれ今の値（例: 「32 / 50」）で表示し、「1 にする」「満タンにする」のボタンで変える（`addValue`・`addButton`）。
    *  HP を 1 にしても、その場では決着しない。次の攻防で、ふつうのルールのとおりに決着する（城が 1 なら敵の攻撃で負け、敵が 1 なら攻撃が通れば倒れる）。
    *  窓を閉じたとき、最上部の HP のゲージと数字が新しい値を示している（変わるときに動いて見えるか、すぐ変わるかは計画で決めてよい）。
*   **要件8: FPS の表示**
    *  DEBUG タブに、FPS の表示を出し入れするチェックボックス（`addCheckbox`。文字は例えば「FPS を表示」）と、いまの FPS の値（`addValue`。`Engine.fps`。`null` の間は「--」）を置く。値は窓を開いている間も約1秒ごとに変わる。
    *  表示の出し入れは `Engine.fpsVisible`、位置は `Engine.fpsPosition` で行う（14章。`draw` の中で代入しない）。位置は、四隅のうち最上部のゲージ（HP・金貨・TURN の区画）と重ならない隅にする。下の隅は放つボタンと重なるので、どの隅にするかは計画で決めて定数に置く（試遊で決め直す値）。表示は文字だけで、押しても何も起きない（盤面の操作の邪魔にならない）。
    *  起動したときは表示が消えている。出した後にタイトルへ戻っても、表示は出したままでよい（定数が ON のときにだけ起こる）。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   開発資料の冒頭の「FPS の表示（14章）はまだ使っていない」の記述、3章の画面の流れ（タイトル画面のボタン・デバッグスタート・メニューの窓のタブ）、4章の責務の表（ルール層のデバッグ用の操作・デバッグの定数の置き場所）を、実際に合わせて直す。エンジンの使い方は書き写さず、章の番号と機能の名前だけを挙げる。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **ルールに触る操作はルール層に作る**（憲法 3章）: 兵の数（ゲージの値）・敵の切り替え・次の行動の指定・城と敵の HP は、ルール層にデバッグ用の操作を作り、DEBUG タブはそれを呼ぶだけにする。画面・シーン・窓の部品の `write`・`onPress` が、ルールの状態（`game.gauges`・`game.enemy`・`game.castle` など）を直接書き換えない。ルール層のデバッグ用の操作は、エンジン・画面に依存せず、乱数は今と同じく `Game` が持つ乱数の関数だけを使う。デバッグ用の操作を `Game.js` に足すか、別のファイルに分けるかは計画で決める（`Game.js` が肥大しないようにする）。
*   **見た目は anim・view の口で合わせる**: 兵の数・敵・HP を変えたとき、段取りの間の見た目（陣地の兵・敵の待機・予告・HP のゲージ）を合わせる処理は、シーンが anim の口を呼ぶ形にする。描画層（`js/view/`）にデータ・状態を持たせない。
*   **窓と入力**: 窓（`Ui`）はシーンが持つ（26章「シーンへの置き方」）。`Engine.addButton` を窓と重なる位置に登録しない。`read`・`format`・`label`・`enabled` は `draw` の中から呼ばれるので、状態を変えない。`write`・`onPress` の中で、ルール層のデバッグ用の操作を呼ぶ。
*   **音の決まりを守る**: `Sound` を呼ぶのは `js/scenes/soundCues.js`・`js/scenes/bgmCues.js` の中だけ。敵を切り替えたときの BGM も `bgmCues.js` の口で流す。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **時間**: 時間は `update(dt)` の `dt` と `draw` の `time` だけを使う。`draw` の中で状態を変えない。
*   **今回やらないこと**:

    *   キャンバスキャッシュ（`oz/ENGINE_API.md` 25章）を使うこと、描画の重さを測ること（Phase 06-04 で行う）。
    *   行動の回数・金貨のゲージ・山札・列・手札を DEBUG タブから変えること。スロー・一時停止など時間の操作。乱数の種の表示とやり直し。
    *   攻防の演出の途中・「準備終了」が出ている間に DEBUG タブを開くこと（メニューの窓を開ける間は 06-01 のまま）。
