## 【実装要件】
3択の強化に、カードの枠（札の人数を伸ばす強化）と特別の枠（行動・手札を増やす強化）を足す。

* 数値はすべて設定（ルールは `js/rules/config.js`、動きの時間は `js/anim/` の設定、配置は `js/view/` の配置の定数）に置き、下の値は初期値（試遊で変える）。
* 座標はすべて論理座標（画面 720×1280）で書く。画面の呼び名は TURN・ターン（内部の名前は phase）。スートの画面の呼び名は 剣（`sword`）・盾（`shield`）・ハンマー（`potion`）・金貨（`muscle`）。
* 攻防の計算・敵・ステージの加算・疲弊・1ターンの流れ（段取り → 攻防）・3択の画面の流れは変えない。**強化を取らないゲームでは、放つ量・行動の数・攻防の結果・予告・乱数の呼び出し（3択の抽選の分を除く）が変更の前と同じ**であること。

### 今の作り（現場設計で確かめたこと）
* **強化の仕組み（07-05）**: 強化の一覧は `config.js` の `upgrades`（種類 → `{ slot, weight, effect, … }`）、枠は `upgradeSlots`（`castle: 1, troop: 1, card: 1, special: 0.5`）。効き方は `upgradeEffects.js` の `UPGRADE_EFFECTS`（効き方の種類 → `canOffer`・`roll`・`fixedValue`・`take`・`untake`・`castleMaxHpBonus`・`turnGains`・`preview`）、文字は `upgradeText.js` の `UPGRADE_TEXTS`（種類 → `name`・`choice`・`taken`）と `UPGRADE_SLOT_TEXT`。抽選は `upgradeOffer.js` の `drawUpgradeChoices`（枠を重みで選ぶ → 枠の中で強化を重みで選ぶ → 足りなければ埋める → 値の抽選）。取った強化の状態は `game.upgrades`＝種類 → `{ count, amount }` で、中断データ（`suspendData.js`。版 3）は `isUpgradeState` でこの形を確かめる。DEBUG タブの強化の「+1」のボタンとメニューの「強化」タブの行は一覧から組み立てる。いまの強化は城の枠の4種（最大 HP・自動兵士3種）だけで、残りは「埋める」で選ばれている。
* **放つ計算**: `release.js` の `computeRelease(cards, config)` が、同じスートが続く区切りごとに `sum`（数字の合計）・`count`（枚数）・`bonus`（束の補正 `min(max, perCard × (count − 1))`。`releaseBonus` は `{ perCard: 1, max: 6 }`）・`amount`（`sum + bonus`）を出し、全スートがそろえば各ゲージに `allSuitsBonus`（1）を足す。区切りの式は `battleText.js` が「18 +2 = 20」（足す量 0 は「4」）、4スートそろいは「4スート +1」と文字にする。金貨のゲージ（`muscle`）は5たまるごとに次のターンの行動 +1（最大 +2。`muscleConversion`）。
* **札の描き方**: `cardView.js` の `drawCardFace(ctx, x, y, w, h, card)` が表の枠・左上の数字（`bold 24px`、左から 8・上から 6）・中央のスートの絵を描く。呼び元は `boardView.js`・`columnView.js`・`deckView.js`・`handView.js`・`orbView.js`・`howToArt.js`（`drawCardFlip` を含む）。列の重ねた札の見える帯は 36px（`layout.js` の `COLUMN_STEP_DEFAULT`）。
* **手札と配置**: 手札は `game.hand`（`createHand(config.handSize)`。`handSize` は 1）。`layout.js` の `createLayout` は上の行（山札4・捨て札・手札の枠）を横幅に並べてカードの大きさを決める（1枠でカード 100×140）。`BoardScene.init` が `handSize: this.game.hand.length` で配置を1回だけ作る。中断データは手札の長さを `config.handSize` と比べて確かめる。
* **行動**: `phase.js` の `computePhaseStart` が基本の行動（`baseActions` 5）に金貨の換算の分を足し、`Game.advancePhase` が `actionsMax`・`actionsLeft` に入れた後、敵が倒れていれば `enterStage`、続けて `planIntent`（予告の抽選）を呼ぶ。行動のゲージ（`actionGaugeView.js`）はブロック5つで、5を超えた分をオレンジで重ねる（10 まで出せる）。帯の上の「ACTION POINT」のラベルは x 20・y 356・`bold 14px`（`layout.js` の `actionGauge.label`）。
* 兵の数のスライダー（DEBUG）の上限は 99（`debugTab.js` の `TROOP_SLIDER`）。人数の表示（`troopCountView.js`）は `bold 20px`。

### 要件1: カードの強化（枠「カード」）
* 種類と重み（`config.upgrades` に1行ずつ）:
    * **スートを強化**（剣・盾・ハンマー・金貨の各 0.5）: そのスートのすべての札が +1。上限なし。
    * **数字を強化**（1〜7 の各 1）: その数字のすべての札が +1。上限なし。
    * **4スートそろいを強化**（0.5。1プレイに3回まで）: 4スートそろいで4つのゲージそれぞれに足す量が 1 増える（基本 +1 から、3回で +4）。
    * **コンボを強化**（1。1プレイに3回まで）: 束の補正の1枚ごとに足す量と上限が、取った回数に応じて伸びる。1枚ごと `perCard × (1 + 回数)`、上限 `max × (1 + 回数)`（強化なしの5枚 +4 が、1回で +8、3回で +16。上限 +6 は +12・+18・+24）。
    * 「3回まで」の強化は、上限に着いたら3択に出さない（効き方の `canOffer` で止める）。
* 札の「+◯」（その札の強化の量）= そのスートの強化の回数 + その数字の強化の回数。強化は山札・手札・列・捨て札のどこにある札にも効く（札そのものは書き換えず、ゲームの強化の状態から求める）。
* 放つと、各札は「数字 + +◯」の人数（金貨なら貯まる量）になる。**並べるための数字と、束の補正の枚数は変わらない。** 区切りの式の「合計」は +◯ を含めた値にし、式の形は今のまま（例: 数字の合計 15・札の +3・束の +2 なら「18 +2 = 20」）。束の補正と4スートそろいの量は強化後の値で式・文字に出る。
* **「+◯」の見た目**: 強化された札（+◯ が 1 以上）には、左上の数字の右下に「+◯」をオレンジで出す。文字の大きさは数字の約 2/3（数字 24px に対して 16px を目安。試遊で決め直す）。重ねた札の見える帯（36px）に収める。0 なら出さない。札の表を描く所すべて（山札の見える札・捨て札・列・手札・動いている札・玉に変わる前の札・燃える札）に出す。遊び方の絵（`howToArt.js`）には出さない。

### 要件2: 特別の強化（枠「特別」）
* **アクションポイント**（重み 2）: ターンの始まりに、発動率で行動 +1。発動率は初め 0%、1回取るごとに 5〜10%（整数。3択が出たときに決める）増え、上限 50%。上限の手前では、実際に増える分（`min(抽選の値, 50 − 今の率)`）を選択肢に出す。上限に着いたら出さない。
    * 発動の抽選は、ターンの始まり（`advancePhase` の中。中断データの保存より前）に、**率が 0 より大きいときだけ**プレイ用の乱数を1回呼ぶ（率 0 では呼ばない。強化なしのゲームの乱数の並びを変えないため）。予告の抽選（`planIntent`）の後に呼ぶ。発動すれば、そのターンの行動が +1。金貨で増える行動とは別に数える。
    * 行動のゲージの「ACTION POINT」の右に「+1(10%)」のように率を出す。上限（50%）に着くと % の部分がオレンジになる。率 0% の間は出さない。
* **次の戦闘の間、毎ターン行動 +1**（重み 2）: アクションポイントが上限に着いた後だけ、アクションポイントの代わりに出る。取った後のターンの始まりから、次に敵を倒すまで、毎ターン行動 +1（3択で取れば、次のステージの戦闘の間）。敵を倒すと消える。効いている間は、「ACTION POINT」の右の表示の後ろに「・この戦闘 +1」を足す。
* **手札の枠**（重み 1。1プレイに1回だけ）: 手札が2枠になる（取った後は出さない）。手札の枠の数はゲームの状態で持つ（`config.handSize` は書き換えない）。
    * **2枠の配置（発注者の決定）**: 上の行の並び・カードの大きさ（100×140）は変えず、今の手札の枠1つ分の場所に、手札の枠を 60〜70%（65% を目安。試遊で決め直す）に縮めて2つ斜めに重ねる。1枠目を左上（奥）、2枠目を右下（手前）に置き、2つ合わせて今の枠の矩形に収める。奥の枠は、手前の枠に隠れていない所で押せる（多少押しにくくてよい）。両方の札の数字と「+◯」が見える。「手札」の見出しは今の位置のまま。札が手札へ動く・手札から動くときは、縮めた枠の大きさに合わせる。
    * 取るまでは今の1枠の見た目のまま。取ったとき（3択で選んだ後・DEBUG）に配置が2枠に切り替わる。

### 要件3: 3択の選択肢と「強化」タブの文字
* 枠の名前は今の `UPGRADE_SLOT_TEXT`（カード・特別）を使う。選択肢の文字（見出し・説明）の目安（`◯` は値。前後の値はルール層の `preview` が返したものを並べるだけにする。文言は計画で整えてよい）:
    * スート: 見出し「剣の札 +1」・説明「剣の札すべて +0 → +1」（盾・ハンマー・金貨も同じ書き方）。
    * 数字: 見出し「数字 3 の札 +1」・説明「3 の札すべて +0 → +1」。
    * 4スートそろい: 見出し「4スートそろいを強化」・説明「4スート +1 → +2（あと 2 回）」。
    * コンボ: 見出し「コンボを強化」・説明「5枚の束 +4 → +8（あと 2 回）」。
    * アクションポイント: 見出し「アクションポイント +7%」・説明「行動 +1 の発動率 10% → 17%」。
    * 次の戦闘の間: 見出し「次の戦闘の間 行動 +1」・説明「次の敵を倒すまで、毎ターン行動 +1」。
    * 手札の枠: 見出し「手札の枠 +1」・説明「手札 1枠 → 2枠」。
* メニューの「強化」タブの行の目安: 「剣の札 +2」「数字 3 の札 +1」「4スートそろい +3（2回）」「コンボ 1枚ごと +3・上限 +18（2回）」「アクションポイント 25%」「この戦闘の間 行動 +1」（効いている間だけ）「手札の枠 2枠」。
* 3択の札・「強化」タブの行が、長い文字でも枠に収まる（はみ出すなら縮める）。

### 要件4: 中断と再開
* 中断データの版を 4 に上げ、足した状態（アクションポイントの率、「次の戦闘の間」が効いているか、手札の枠の数など）をすべて保存・確かめ・戻す。手札の長さの確かめは、設定ではなくゲームの状態（取った手札の枠）と比べる。
* アクションポイントの発動はターンの始まりの保存より前に決まるので、再開しても同じターンの行動の数になる。同じ手順なら、再開しても同じ結果になる。

### 要件5: DEBUG タブ
* 強化の「+1」のボタンは一覧から組み立てる（今のまま。カード・特別の強化のボタンが増える）。上限のある強化は、上限に着いていれば押しても何も起きない。手札の枠を DEBUG で取ると、その場で手札が2枠になる。「次の戦闘の間」を DEBUG で取ると、次のターンの始まりから、次に敵を倒すまで効く。
* 「強化をすべて外す」では、手札は1枠に戻る（2枠目に札があれば捨て札へ移す。DEBUG だけの扱い）。
* ボタンの文字を「{強化の名前} を取る（今 N 回）」の形に直す（今の「城の最大 HP +1（今 N）」は、1回で +5 増えるのに「+1」と出て紛らわしいため。名前に数字の入る強化が増えるので一緒に直す。`debugText.js` の `upgradeAddText`）。
* 兵の数のスライダーの上限（99）は変えない。

### 要件6: 確かめ
* 確かめは一時スクリプト（スクラッチのフォルダ。リポジトリの外。終わったら消す）で行い、結果を各タスクの詳細作業内容に書く。`oz` は代用、`assets/` だけ解く `module.register` のローダーを使う（07-05 と同じ要領）。変更前のコードは `git archive`（本 REQ のコミット）をスクラッチへ展開して比べる（リポジトリの状態を変える git 操作はしない）。
* 強化を取らないゲームを変更前と並べて、毎手の結果・状態（予告・乱数の状態まで）が一致すること。
* 抽選の割合の目安（列挙で求めた期待値と比べる）: 今は兵士の枠に強化がないので、候補の枠は城・カード・特別の3つになり、**3択はいつも城・カード・特別から1つずつ**になる（07-07 で兵士の枠が入るまで）。カードの枠の中は、スート 4種 × 0.5・数字 7種 × 1・4スートそろい 0.5・コンボ 1（合計 10.5）の重みで選ばれる。
* 強化を取ったゲームで、放つ量・4スートそろいの量・束の補正・行動の数・アクションポイントの発動率が式どおりであること。ターンの始まりと3択の段階の保存・復元で、続けた結果が一致すること。
* 人数が3桁（100 以上）になっても、人数の表示（`troopCountView.js`）が崩れないかを確かめる。崩れるなら RES の懸念事項に書く（07-07 で人数の枠を見直す）。

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. 3択に、城・カード・特別の枠から1つずつ選択肢が出る（「城を修理」もいつもある）。
2. スート・数字の強化を取ると、その札すべての数字の右下にオレンジの「+◯」が出る（山札・捨て札・列・手札・動いている札）。重ねた札でも見え、スマホで読める。
3. 強化された札を放つと、式の合計に +◯ が含まれ、その分だけ兵（金貨なら貯まる量）が増える。並べられる数字は変わらない。
4. 4スートそろい・コンボを強化すると、放ったときの「4スート +◯」と式の束の補正が強化後の値になる。3回取ると、もう出ない。
5. アクションポイントを取ると、「ACTION POINT」の右に「+1(◯%)」が出て、ときどきターンの行動が1つ増える。上限 50% で % がオレンジになり、その後は「次の戦闘の間 行動 +1」が出る。取ると次の戦闘の間ずっと行動が1つ多く、「・この戦闘 +1」が出て、敵を倒すと消える。
6. 手札の枠を取ると、手札の場所に縮んだ2枠が斜めに重なって出て、両方に札を入れて使える。奥の枠も押せる。ほかのカードの大きさは変わらない。1回取ると、もう出ない。
7. メニューの「強化」タブで、取った強化が見られる。
8. 強化を取った後に閉じて開き直しても（ふつうのターン・3択の段階のどちらでも）、同じ状態で続けられる。
9. `?debug` の DEBUG タブで、新しい強化を付けられ・すべて外せる（手札は1枠に戻る）。ボタンの文字が「◯◯ を取る（今 N 回）」になっている。
10. スマホで、2枠の手札と札の「+◯」が押せて読める。PC とスマホで、タイトルから負けまで通しで遊べる。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   強化の種類を足すときに書き足す所が、新しい効き方（札の +◯・束の補正・4スートそろい・行動・手札の枠）を含めて資料から分かる形になっていること。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: ルール層（カードの強化と放つ計算 → 特別の強化と行動・手札の枠）→ 中断データ → 札の「+◯」の見た目 → 行動のゲージの表示 → 手札2枠の配置 → 3択・「強化」タブの文字 → DEBUG タブ のように、各タスクの終わりで起動とプレイが壊れない順・大きさに分ける。やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**: 札の +◯・放つ量・束の補正・4スートそろいの量・行動の数・発動の抽選・手札の枠の数はルール層で決め、画面は状態を読んで操作の口を呼ぶだけにする（画面の側で足し算して値を作らない）。ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない（乱数は `game.random` だけ）。
*   **アーキテクチャの維持**: 強化の種類の識別子で分岐する if を足さない（一覧の表と効き方の表で分ける）。新しい効き方は `UPGRADE_EFFECTS` に行を足し、表の口が足りなければ口を足す（今の効き方の行にも同じ口を足す）。強化で変わる値は `config.js` の値を書き換えず、ゲームの状態から求める。1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`Game.js`・`layout.js`・`BoardScene.js` は大きいので、足す処理は分けて置けないか先に検討する。
*   **動きの時間**: 動きの時間は `dt`・時計だけで決め、状態は時計から求められる形にする。
*   **描画**: `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。新しいスプライトは作らない（「+◯」・率の表示は文字で描く）。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **触るファイルの古い説明**: `soundCues.js`・`bgmCues.js` の「はじめる」の古い説明が残っている（動作に影響なし）。同じファイルを触るなら一緒に直す。
*   **今回やらないこと**:
    *   兵士の枠の強化（精鋭の確率・能力）、精鋭の見た目、人数の表示の「△（＋◯）」。
    *   スコア・ボーナス・結果の画面の作り直し、ベストの保存。
    *   メニューの「敵情報」タブ、3択の画面に次の敵の強さを出すこと。
    *   ジョーカー・最大値の解放、手札の枠の3枠目以降。
    *   敵・ステージの加算・疲弊・城の強化の値の変更、新しい音・曲、遊び方の文章の変更。
    *   `README.md`・`_doc/` の資料の書き換え。
