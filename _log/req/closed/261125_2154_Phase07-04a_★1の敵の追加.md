## 【実装要件】
★1の敵に、狼・猪・骸骨・スライムの4種を足す。敵の並びに「同じ敵・同じ動きを続けない」決まりを入れる。

* 数値はすべて設定（ルールは `js/rules/config.js`、動きの時間・大きさは `js/anim/battleAnimConfig.js` や配置の定数）に置き、下の値は初期値（試遊で変える）。
* 座標はすべて論理座標（画面 720×1280）で書く。画面の呼び名は TURN・ターン（内部の名前は phase）。
* ゴブリン・巨人・ドラゴンの数値・動き・見た目、1ターンの流れ、攻防の計算の順、自軍の数値、ステージの加算の量、疲弊の決まりは変えない。

### 今の作り（現場設計で確かめたこと）
* 敵の種類は `config.enemies` の1行ずつ（名前・★・最大 HP・防御（張る確率と量の幅）・行動の決まり）。★ごとの候補は、そこから集める。行動の決まりは `enemyBehaviors.js` の表（`steady`・`cycle`・`inhale`）で、状態の初期値・状態の形の確かめ（`isState`。中断データ用）・次の行動・数え下ろし・隙かを持つ。デバッグの `debugIntents.js`・`debugRuleItems.js` にも決まりごとの表がある。
* 予告（`createIntent`）は、行動に、攻撃の加算（行動の種類が `attack` のとき、量が 0 でも足す）と、防御の量（`spec.defense` の抽選＋防御の加算）と、疲弊を付ける。行動の種類は `attack` と `windup` だけで、`battle.js`・`suspendData.js` の確かめ（`isIntentShape`）もこの2つだけを知っている。
* 予告の札・文字は、攻撃の量 0・中の種類なし・防御ありのときに攻撃の側を出さない（`intentParts.js`）。赤い札は行動の中の種類 `breath` だけ（`EMPHASIZED_VARIANTS`）。
* 敵の種類の識別子で引く表・集合は、次の所にある（足し忘れると Error か、表示の抜けになる）: `enemyShows.js` の `ENEMY_SHOWS`、`layout.js` の `ENEMY_FIGURES`、`enemyView.js` の `HORDE_ENEMIES`、`soundConfig.js` の `STAGE_BGM`、`soundCues.js` の `ENEMY_ATTACK_SE`。
* 群れの敵（ゴブリン）の体・攻撃の兵・守りの兵は、兵の種類 `goblin`・`enemy`・`enemyGuard` で、どれもゴブリンの絵（`troopView.js` の `TROOP_LOOKS`）に決め打ちである。焼き付けも種類と大きさごとに `init` で作る。
* 絵の敵（巨人・ドラゴン）は、攻撃のとき絵は動かず、打撃の印だけが出る（`strike`）。攻防中の絵の見た目は、倒れる動きの縦のずれと姿勢（傾き・伸び縮み）だけで、横には動かない。シールドは絵の体に並ぶ（`shieldArea`）。
* DEBUG タブの「敵」は、横1列（幅 580）の選択肢で、敵の種類の数だけ等分される。敵の最大 HP のスライダーは 5 刻み。

*   **要件1: 敵の種類と数値**（発注者の決定。ステージの加算の前。どれも★1）

    | 敵 | 名前 | 体 | HP | 攻撃 | 溜め／防御 |
    |---|---|---|---|---|---|
    | 狼 | 狼 | 絵 | 36 | 1〜3 | 30% で溜め1ターン → 大攻撃 7〜9 |
    | 猪 | 猪 | 絵 | 44 | 1〜2 | 30% で溜め2ターン → 大攻撃 13〜16 |
    | 骸骨 | 骸骨の軍勢 | 群れ | 24 | 4〜6（40%） | 60% で防御 3〜5（うち 20% は大防御 7〜9） |
    | スライム | スライム | 絵 | 40 | 2〜3（40%） | 60% で防御 2〜4（うち 20% は大防御 5〜7） |

    *  **動き A「溜めて大攻撃。防御しない」**（狼・猪。決まりは1つで、数値だけが違う）: ふつうは毎ターン攻撃する。溜めていないとき、大攻撃の次のターンを除いて、溜める確率で溜めに入る。溜めのターンは決めた数だけ続き、その間は攻撃しない。次のターンに大攻撃する。大攻撃の次のターンは必ずふつうの攻撃。防御はいつも 0（シールドを張らない）。
    *  **動き B「攻撃か防御のどちらか」**（骸骨・スライム。決まりは1つ）: 毎ターン、攻撃する確率で攻撃だけ（防御 0。隙）、そうでなければ防御だけ（攻撃しない）を行う。防御のうち、大防御の確率で大防御の量になる。
        *  **防御だけのターンは、ステージの加算が進んでも攻撃しない**（攻撃の加算が乗らない）。攻撃だけのターンは防御 0 のまま。
    *  ステージの加算は今と同じ決まり（攻撃・大攻撃の量に攻撃の加算、防御・大防御の量に防御の加算、HP は割合）。加算・疲弊を計算する所は今の1か所ずつのまま。疲弊は、動き B の防御にも掛かる。
    *  抽選はすべてプレイ用の乱数。ゴブリン・巨人・ドラゴンの乱数を呼ぶ順と回数は変えない。
    *  中断データ: 新しい決まりの状態の確かめを足し、予告の形が変わるなら確かめも直す。版番号（`SUSPEND_VERSION`）を 2 に上げる（前の中断データは捨てられてよい。設定は残る）。
*   **要件2: 敵の並び**
    *  「動き」は行動の決まりの組（攻防を同時に行う＝ゴブリン／溜めて大攻撃＝狼・猪／攻撃か防御＝骸骨・スライム）。
    *  ★1 のステージだけを順に並べたとき、同じ敵も同じ動きも隣り合わない（間に巨人・ドラゴンのステージが入っても、続いているとみなす。例: ステージ 4 と 6）。
    *  ステージ 1〜3 には、3つの動きが1回ずつ出る（順番は日付で決まる）。同じ動きの中のどの敵かも、日付とステージの番号で決まる。
    *  種とステージの番号から、前のステージを順に計算せずに求められる純粋な関数のままにする（今と同じ）。乱数は呼ばない。3つの動きは長い目で見て偏らず、同じ動きの2種も偏らない。日付が変われば並びが変わる。
        *  （考え方の例。採用は計画に任せる）★1 の並びを3ステージずつの組に分け、組ごとに動きの順を種から決める。組の境目は、隣の組の端の動きを種から直接決めておけば、順に計算しなくても続かない形にできる。
    *  ★2・★3 は候補が1種なので、今のまま同じ敵が続いてよい。敵の種類（07-04b のオーガを含む）を設定に1行足すだけで並びに加わる。
*   **要件3: 予告**（発注者の決定）
    *  大攻撃: ブレスと同じ赤い札で、文字は「大攻撃 8」。絵は今の攻撃の絵（新しい予告の絵は作らない）。
    *  溜め: 今の振りかぶりの絵・文字「溜める」。溜めが2ターン以上の敵（猪）は、今の数え下ろしの文字と同じ見せ方で、大攻撃まであと何ターンか（「攻撃まで あと2」「攻撃まで あと1」）を添える。1ターンの敵（狼）と、溜めていないターン・大攻撃のターンには添えない。
    *  防御だけのターン: 防御の札だけ。大防御もふつうの防御の札のまま（数字が大きいだけ）。始まりの文字は「防御 4」のように出る。
*   **要件4: 見た目と動き**
    *  **狼・猪・スライム（絵）の攻撃**（発注者の決定）: 絵が城の前（防御の兵がいれば、その前）まで駆け寄り、打撃（今の打撃の見せ方。印・防御の兵が跳ねる・城の HP が減る）を行い、元の場所へ戻る。自軍の突撃が始まる前に戻り終える。狼は速く、猪は一直線に、スライムは跳ねながら進む。進む時間・戻る時間・跳ねの高さは、敵ごとの設定の値（「動きの速さ」）にする。城・兵の手前と奥の重なりが不自然でない。予告の札は動かさなくてよい。
        *  攻防のタイミング（HP が減る時刻・音・当たりのエフェクト）は、絵が着いた後の打撃に合う。負けるときは、打ったまま戻らなくてもよい。
        *  狼・猪の大攻撃は「大きな一撃」（今の揺れ・止めの大きい見せ方）。溜めのターンは、今のため動き（後ろへ反る・膨らむ）を見せる。
    *  **スライム**: 剣の兵が当たるたびに短くへこむ（足元を軸に縮んで戻る。続けて当たっても震えて見えない）。HP が減るほど体が小さくなる（満タンで 1 倍、0 に近いとき半分まで。段取りの間も攻防の間も、表示中の HP に合わせる）。小さくなっても、兵の当たる位置・シールドの並ぶ位置・予告の札が、体から離れて見えない。倒れ方は今の絵の敵と同じ。
    *  **骸骨（群れ）**: 群れ・攻撃の兵・守りの兵が骸骨の絵になる。並び方・動き・演出はゴブリンの軍勢と同じ（守りの兵が現れて剣の兵を止める）。群れの絵を敵の種類ごとに決められる形にし、ゴブリンの見た目は変えない。焼き付けも、その絵で作られる。
    *  ステージの始まりの敵の入り・待機の伸び縮みは、今の絵の敵・群れの敵と同じ。
    *  スプライト: 次の4枚を手で書いた仮のスプライトとして新しく作る（**この4枚の作成だけ、本 REQ で明示的に認める。** ほかのスプライトは変えない）。`unit_wolf.js`・`unit_boar.js`・`unit_skeleton.js`・`unit_slime.js`。既存の仮のスプライトと同じ形（`source` を持ち、OZ Vector Editor の「開く」で開ける。線・塗りの調子を既存の敵に合わせる）。狼・猪・スライムは左（城の方）を向く。骸骨はゴブリンと同じ大きさ・枠（体の中心が原点、x・y とも約 ±105）。見て何の敵か分かること。発注者が後でエディタで描き直して同じ名前で差し替える（大きさの基準になる表の値を `spriteView.js` に持つ）。
    *  絵の高さ: 狼 110・猪 130・スライム 120 を目安に、ほかの要素（予告の札・人数の枠・HP ゲージ）と重ならない。
*   **要件5: 音**

## 【テストプレイで確かめること（実装セッションが発注者に依頼するときに示す）】
1. はじめから遊ぶ（または `?debug` の HP を 1 にして早送り）と、ステージ 1〜3 に3つの動きが1回ずつ出て、★1 で同じ敵・同じ動きが続かない（巨人・ドラゴンを挟んでも）。5 は巨人、10 はドラゴン。
2. 狼: ふつうの攻撃、ときどき溜め、次のターンに赤い札の「大攻撃」。絵が速く駆け寄って打ち、戻る。シールドは出ない。
3. 猪: 溜めが2ターンで「攻撃まで あと2」「あと1」が出て、重い大攻撃。一直線に突進する。
4. 骸骨: 攻撃だけのターンと防御だけのターンがあり、攻撃のターンは守りがいない。ときどき大きく防御する。絵が骸骨になっている。
5. スライム: 骸骨と同じ動き。シールドの出るターンと出ないターンがある。剣の兵が当たるとへこみ、HP が減るほど小さくなる。跳ねて打つ。
6. 予告の札（防御だけ・赤い札・数え下ろし）と、ターンの始まりの文字が読める。
7. 狼・猪・スライムの攻撃で、防御の兵がいるとき・いないとき・負けるときの見え方が自然である。音と打撃のタイミングが合う。
8. `?debug` の「敵」で7種に切り替えられ、名前が読める。「敵の次の行動」で各行動を選べる。ルールの値のスライダーで 36・44・24 が正しく出て、変えられ、「元に戻す」で戻る。一番下までスクロールできる。
9. ステージ 20〜30 の骸骨（群れ）とスライム（シールド）で、崩れない・重くならない。防御だけのターンに攻撃が 0 のまま。
10. ゴブリン・巨人・ドラゴンの見た目と動きが、前と変わらない。
11. 途中で閉じて「再開」しても、新しい敵の予告・溜めの残りターンが同じで、続きから遊べる。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（新しいファイルの先頭には責務を3行以内で書く）。
*   変更した .js ファイルの構文チェック（憲法 1章の検証コマンド）を行う。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。
    *   あわせて、資料に抜けている WEB アイコン（`assets/icon/` の4枚と `index.html` のアイコンの指定。発注者が追加済み）を書き足す（コードと素材は変えない）。
    *   敵の種類を足すときに書き足す所（表・設定・絵）の一覧が、資料から分かる形になっていること。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **タスクの分け方**: ルール層（行動の決まり・設定・中断データ）→ 並び → 予告の表示 → 仮のスプライトと表への登録 → 群れの絵の差し替え（骸骨）→ 駆け寄る攻撃（狼・猪・スライム）→ スライムのへこみ・縮み → DEBUG タブ のように、各タスクの終わりで起動とプレイが壊れない順・大きさに分ける。敵の種類を `config.enemies` に足すのは、その敵を見せる表がそろってからにする（途中で Error にならないように）。やむを得ず途中で壊れる区切りがあれば、計画に明記する。
*   **ルールと画面の分離**: 行動・量・並びはルール層で決め、画面・演出は結果と状態を読むだけにする。ルール層は `oz` も画面のモジュールも import せず、`Math.random`・日付を読まない。
*   **アーキテクチャの維持**: 敵の種類の識別子で分岐する if を足さない（設定・表で分ける）。狼と猪・骸骨とスライムの違いは数値と表だけで表す。1つのモジュールに責務を足しすぎない（憲法 3章。合わない処理は新しいファイルに分ける）。`layout.js`・`battleTimeline.js`・`troopRoster.js` は大きいので、足す処理は分けて置けないか先に検討する。
*   **動きの時間**: 動きの時間は `dt`・演出の時計だけで決め、状態は時計から求められる形にする（今の演出と同じ）。演出の速さ（普通・速い）とヒットストップが、新しい動きにも同じように効く。
*   **描画**: `draw` の中では状態を変えない。`ctx` の状態は `save`・`restore` で囲む。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext` を書かない。描く体の数は敵と兵を合わせて 500 体を目安とする。
*   **エンジンの使い方**: エンジンは `import { … } from 'oz'` でだけ使い、`oz/` は編集しない。`oz/src/` は読まない。必要な機能が `oz/ENGINE_API.md` にない、または書かれたとおりに動かないときは、ゲーム側に回避策を書かず、作業を止めて RES に記録する（憲法 3章「エンジンの不足への対応」）。
*   **今回やらないこと**:
    *   オーガ、1体が2ポイント以上を受け持つ仕組み、大きさの違う群れ（07-04b で行う）。
    *   ★2・★3 の敵の追加、★の並びの決まりを広げること、★・次の敵の表示。
    *   属性、札への妨害、3択・強化、スコア。
    *   ゴブリン・巨人・ドラゴンの数値と見せ方の変更、ステージの加算・疲弊の値の変更、新しい音・曲、新しい予告の絵。
    *   遊び方の4ページ目に敵を足すこと。
    *   `README.md`・`_doc/` の資料の書き換え。
