## 【実装要件】
いまの巨人は、03-01 で入れた仮の行動（攻撃・防御のスタンスの重みによる抽選）と仮の玉で出ている。今回は、巨人を「決まった周期で1回だけ重い攻撃をし、攻撃の直後にまれに HP を回復する」敵に作り変える。ゴブリンの軍勢・ドラゴンの行動と見た目は変えない（ドラゴンは 03-03 で作るので、今回は 03-01 の仮のまま）。

*   **要件1: 巨人の行動の決まり（周期の攻撃と振りかぶり）**
    *  巨人は決まった数のフェーズを1周期として、周期の最後のフェーズに1回攻撃する。周期のほかのフェーズは「振りかぶり」で、敵の行動をしない（攻撃も防御のスタンスも取らない）。振りかぶりのフェーズでも常時防御力は働く（自軍の攻撃は常時防御力の分だけ減る）。周期はランダムにしない。
    *  巨人が出た最初のフェーズは、周期の最初の振りかぶりから始める。攻撃したフェーズの次のフェーズは、また周期の最初の振りかぶりから始める（回復したかどうかに関係なく）。
    *  初期値（仮。03-05 で調整する。`js/rules/config.js` の巨人の設定に置き、そこを書き換えるだけで変えられる）: 周期 4 フェーズ（振りかぶり 3 回 → 攻撃）、攻撃力 40、常時防御力 8（いまのまま）、最大 HP 80（いまのまま）。巨人の仮の行動の設定（重みつきの攻撃・防御のスタンス）は、この決まりの設定に置き換える。
    *  巨人の行動の決まりは、`js/rules/enemyBehaviors.js` の表に新しい決まりの種類として足す（決まりの状態の初期値と次の行動の決め方）。ゴブリンの軍勢・ドラゴンの重みによる抽選の決まりは変えない。乱数は外から渡されたもの（`Game` の `random`）だけを使う。
*   **要件2: 数え下ろしと予告の表示**
    *  戦闘の段に、巨人と戦っている間は常に、攻撃までの残りフェーズ数（数え下ろし）が出る。周期 4 なら、巨人が出た最初のフェーズから「攻撃まで あと3」「あと2」「あと1」と減り、4つ目のフェーズ（攻撃するフェーズ）では、段取りの間、いつもどおり予告の枠に攻撃（量つき）が予告され、数え下ろしは攻撃するフェーズであることが分かる表示（例:「攻撃！」）になる。表示の文言・位置は計画で決めてよい（文字が枠からはみ出さないこと。位置は `js/view/layout.js` から求める）。
    *  振りかぶりのフェーズの予告の枠は、振りかぶりであること（例:「振りかぶり」）が分かる表示にする（「なし」ではなく）。
    *  ゴブリンの軍勢・ドラゴンと戦っている間は、数え下ろしは出ない。
*   **要件3: 攻撃の直後の回復**
    *  巨人が攻撃したフェーズの攻防で、巨人の攻撃が城に当たった直後（自軍の攻撃より前）に、低い確率で巨人が HP を回復する。回復は最大 HP を超えない（HP が最大のときは回復の量が 0 で、回復は起きなかったものとして扱ってよい）。抽選は攻撃したフェーズの攻防ごとに1回、外から渡された乱数で行う。
    *  初期値（仮。03-05 で調整する。`js/rules/config.js` の巨人の設定に置く）: 確率 25%、回復の量 20。
    *  巨人の攻撃で城の HP が 0 になったときは、そこでゲームオーバーとして決着し、巨人の回復は起きない。
    *  回復した後の自軍の攻撃は、回復した後の巨人の HP に当たる（同じフェーズで巨人を倒すことはできる。倒したときは 03-01 の敵の入れ替わりの流れのまま）。
    *  ルール層の攻防は、いまどおり「行動終了」の時点で一度に結果を決める。巨人の回復は、攻防の出来事の並びに独立した出来事として入る（量が 0 なら入らない）。
*   **要件4: 回復の見せ方と、振りかぶりの攻防の演出**
    *  攻防の演出で、巨人の攻撃（城への被害）の段の後、自軍の突撃の前に、巨人の回復の段が入る。戦闘の段の巨人の HP が回復の分だけ増えて表示され、巨人の近くに緑の「+20」のような回復の量が出て、回復したことが分かる。効果音は、いまの城の回復と同じ音を当ててよい。早送り・スキップでもいまの段と同じように扱われる。
    *  振りかぶりのフェーズの攻防の演出は、敵の攻撃も敵の防御のスタンスもない段の並び（自軍の攻撃が常時防御力で減り、残りが巨人に当たる、など）として、いまの段の仕組みで自然に見えること。振りかぶりそのものの特別な演出は作らない。
*   **要件5: 巨人の見た目**
    *  戦闘の段の巨人は、大きな緑の玉（仮の図形）で描かれる。いまの巨人の玉より大きくし、色を緑にする（ドラゴンの玉は 03-01 のまま）。常時防御力のシールドマーク（8個）は、いまどおり玉に重ねて見える（大きくなった玉に合わせて並べ直してよい）。
*   **要件6: ほかは変えない**
    *  上に書いたこと以外の、段取り（カードの操作と動き）・攻防の演出（兵の動き・早送り・スキップ・速さ）・敵の入れ替わり・決着・音の挙動は変えない。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する（巨人の行動の決まり・数え下ろし・回復のルール、攻防の出来事・段の追加、戦闘の段の表示、作成済みのファイルの表の更新など）。開発資料に影響を与えない場合は、このタスクは不要とする。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `PROJECT_CONSTITUTION.md` の絶対禁止事項に反する設計をしてはならない。巨人の行動の決まり・数え下ろしの状態・回復の抽選と計算はルール層（`js/rules/`）に置き、画面・エンジンに触れない。描画の側（`js/view/`）・演出（`js/anim/`）・シーン（`js/scenes/`）は、ルール層の状態（数え下ろしの残りを含む）と攻防の結果を読むだけで、書き換えない。数え下ろしの残りは、描画の側で周期から計算し直すのではなく、ルール層から読める形にする。
*   **行動の決まりの拡張性** : 巨人の決まりは `js/rules/enemyBehaviors.js` の表に、既存の重みによる抽選の決まりを壊さずに足す。03-03 のドラゴン（ブレスチャージの蓄積・満ちたら確率でブレス・ブレスで札を燃やす）も同じ形で足せることを確かめ、その想定を計画に書くこと。ただし 03-03 の行動・状態・見た目そのものは作らない（先回り実装の禁止）。「攻撃の直後の回復」を、巨人専用の分岐として `js/rules/battle.js` や `js/rules/Game.js` に直書きせず、敵の種類の設定（または決まり）から読み取る形にすること。
*   **配置は `layout.js` から読む** : 数え下ろしの表示の位置、回復の量の表示の位置、巨人の玉の大きさは、`js/view/layout.js` の戦闘の段の配置から求める（必要なら `layout.js` に足す）。描画・演出・シーンのファイルに座標の数値を直書きしない。
*   **時刻の式の二重化に注意** : 攻防の当たり・修理の時刻の式が `js/anim/battleCues.js` と `js/anim/battleTimeline.js` の2か所にある（`_doc/COWORK_STATUS.md`、03-01 RES 5章）。巨人の回復の段を足すときは、両方を合わせて直す計画にする（または1か所にまとめる計画にしてもよい。その場合は理由を書く）。
*   **先回り実装の禁止** : ドラゴンの行動（爪・ブレス・チャージ・札を燃やすこと）とドラゴンの見た目、結果の画面と集計、タイトル画面（TITLE）の分離、最高記録の保存、振りかぶりの特別な演出、敵ごとの演出の変化、BGM は作らない。
*   **エンジンの使い方** : 動きは `Scene` の `update(dt)` で進め、`draw` の中でシーンの状態を変えない（`oz/ENGINE_API.md`）。シーンの操作と `Engine.timeScale` の変更は `update`・`onPointer` の中で行う。`js/` に `addEventListener`・`requestAnimationFrame`・`getContext`・`setTimeout`・`setInterval` を書かない。必要な機能がエンジンにないときは、回避策を書かずにRESに記録して作業を止める。
*   **変更してよい範囲** : 変更・追加してよいのは `js/rules/`・`js/anim/`・`js/view/`・`js/scenes/` の中のファイルとする（どのファイルを変えるかは計画に明記すること）。`oz/`・`index.html`・`js/main.js`・`js/ui/`・`js/audio/`・`assets/` は変更しない。変更が必要だと分かった場合は、計画の中で理由を書いて対象に加えるのではなく、RESの懸念事項に記して発注者の判断を仰ぐこと。
*   **1ファイル1責務** : 行動の決まり、攻防の計算、敵の進行を、1つのファイルに詰め込みすぎない（`js/rules/Game.js` を肥大化させない）。新しいファイルを作る場合は、先頭に責務定義を書く。
