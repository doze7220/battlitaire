# 設計指針書 DIR: Phase 06 : デバッグとエンジンの載せ替え
* ルール: `./PROJECT_CONSTITUTION.md`
* 開発資料: `./PROJECT_ARCHITECTURE.md`

## 1. 大ゴール
P6 の前の Interrupt（261122）で、OZ Engine を次の機能の入った版に載せ替えた。ゲームはまだ、どれも使っていない。
* キャンバスキャッシュ（`oz/ENGINE_API.md` 25章）
* FPS の表示の出し入れと値の読み取り（14章）
* UI 部品（26章）

P6 では、エンジンの UI 部品を使って、次のものを作る。
* 遊ぶ人向けのメニュー（設定・クレジット）
* 開発用のデバッグの窓（DEBUG タブ）
* 兵が数百体のときの描画の重さを測る仕組み

そのうえで重さを測り、キャンバスキャッシュを使って、スマホで兵が最大の数でも 60fps 付近を保てるようにする。インゲーム強化（Phase 7）では敵と数値が増えるので、その前に、数値を試す道具と描画の余裕を用意しておく。

* **完了の目安**: ゴール型。次の状態になっている。
  * タイトルの「設定」と、段取りの間の TURN の区画から、同じメニューの窓が開く。
  * メニューでは、BGM と効果音の音量、攻防の演出の速さを変えられ、次の起動でも残る。クレジットに音の素材の出典が出ている。
  * URL に `?debug` を付けて開いたときだけ、デバッグのゲームになる。メニューの一番右に DEBUG タブが出て、画面の右下に「DEBUG MODE」と出る。デバッグのときは何も保存しない。（261124 の方針変更。初めは「デバッグを有効にする定数」と「デバッグスタート」のボタンだった）
  * DEBUG タブで、兵の数・敵・次の行動・HP・ルールの値を変えられる。FPS の表示を出し入れでき、キャッシュありとなしを切り替えられる。
  * 兵が最大の数のときに、スマホで 60fps 付近が出ている。
  * `?debug` を付けずに開くと、DEBUG タブ・FPS の表示・「DEBUG MODE」がすべて出ず、ふつうに遊べる。

## 2. やらないこと（Non-goals）
* ルールの変更 → しない。DEBUG タブで値を変えるのは、開発中の試しに限る。ルールの値の本番の調整は、P7 以降に `js/rules/config.js` で行う
* スロー・一時停止など時間の操作、演出の設定の値（速さ・大きさ・エフェクト）を DEBUG タブで動かすこと → 作らない（発注者の選択）
* 攻防の演出の途中・「準備終了」の間にメニューを開くこと → しない。メニューは段取りの間だけ開く
* メニューの「設定」「クレジット」以外のタブ（更新履歴など）→ 未定。設定の中身もこの Phase の項目（音量・演出の速さ）だけにする
* タイトル画面の作り直し → 未定（`_doc/PROJECT_MILESTONE.md`）。この Phase で足すのは、タイトルに「設定」を置くことだけ（「デバッグスタート」は 06-02 で置き、06-05 で消す）
* 兵が理論上の最大を超えたときの描き方 → Phase 7 以降（強化で数値が伸びたとき）
* エンジンの土台にある開発用パネルの雛形と名前の置き場所の取り込み → しない。DEBUG タブがあり、雛形の速度の操作は上の「時間の操作」に当たる
* インゲーム強化・メタ強化 → Phase 7・Phase 8
* エンジンへの新しい要望 → 必要になったら、発注者の承認を得て連絡票で頼む（ゲーム側に回避策を書かない）

## 4. サブフェイズごとの実装要件

### Phase 06-01: メニューの窓と設定
* **目的**: エンジンの UI 部品で、タイトルとプレイ中に同じメニューの窓を開けるようにし、設定とクレジットを入れる。
* **実装要件**:
  * タイトル画面に「設定」がある。押すとメニューの窓が開く。
  * 盤面の TURN の表示（最上部の中央）が、区画で囲まれたボタンになっている。押せることが見て分かる。
  * TURN の区画は、段取りの間だけ押せる。押すとメニューの窓が開く。攻防の演出の間と「準備終了」が出ている間は、押しても何も起きない。「準備終了」の「画面のどこかをタップで攻防へ」は今のまま。
  * メニューの窓は、タイトルとプレイ中で同じ窓である。タブで「設定」「クレジット」を切り替える。
  * 「設定」タブ:
    * BGM の音量と効果音の音量を、それぞれスライダーで変えられる。動かすと、その場で音量が変わる。
    * 攻防の演出の速さを、選択肢（例: 普通・速い）で変えられる。次の攻防から効く。
    * 設定は保存され、ブラウザを閉じて開き直しても残る。
  * 「クレジット」タブに、音の素材の出典（BGM: 魔王魂、効果音: Springin' Sound Stock）が出る。文面は発注者が決める。
  * 窓は閉じるボタンと、窓の外のタップで閉じる。閉じると、開く前の画面にそのまま戻る。プレイ中に開いて閉じても、盤面・行動の残り・兵は変わらない。
  * スマホの縦画面で、スライダーを指で動かせ、文字が読める。
* **持ち越し事項**:
  * 音量の初期値（BGM 0.5・効果音 0.7）は試遊で決め直す値（`_doc/COWORK_STATUS.md` 2章 A の BGM と効果音）。設定の初期値にそのまま使ってよい。
  * `README.md` の音の素材の出典・利用規約（`_doc/PROJECT_MILESTONE.md` の「公開の準備」。発注者が書く）。クレジットの文面と合わせる。
* **メモ**:
  * エンジンの UI 部品（`oz/ENGINE_API.md` 26章）を使う。見た目は、まず標準の見た目でよい。ゲームの絵柄に合わせる差し替え（`look`）をこのサブフェイズで入れるかは REQ 作成時に決める。
  * 保存はエンジンの `Storage`（22章）を使う。部品は保存しないので、値を書く関数の中で保存する（26章の値のつなぎ方）。
  * 演出の速さの実現の仕方（`timeScale` か、演出の時間を縮めるか）と、決着・ヒットストップ・音との関係は REQ 作成時に決める。どの速さでもルールの結果は変わらない（憲法 3章）。
  * メニューの窓をシーンとして積む形（`pushScene`）にすると、開いている間は背面の動き（玉・兵の待機）が止まる。それでよい。
  * 06-02 の DEBUG タブは、このメニューの窓の一番右に足す。タブを後から足せる作りにしておく。

### Phase 06-02: デバッグスタートと DEBUG タブの操作
* **目的**: 1つの定数で入り切りできるデバッグの入口を作り、DEBUG タブから兵・敵・行動・HP を操作し、FPS を出せるようにする。
* **実装要件**:
  * デバッグを有効にする定数が1つある。ON のとき、タイトル画面に「デバッグスタート」が出る。
  * 「デバッグスタート」から始めたときだけ、メニューの窓の一番右に DEBUG タブが出る。ふつうに「はじめる」から始めたときは出ない。
  * 定数を OFF にすると、「デバッグスタート」・DEBUG タブ・FPS の表示が出なくなり、デバッグの操作はどこからも呼べない。
  * DEBUG タブで、次のことができる。
    * 兵の数を指定して出す（攻撃・防御・修理のそれぞれ。理論上の最大まで）。
    * 敵を切り替える（ゴブリン・巨人・ドラゴンのどれからでも始められる）。
    * 敵の次の行動を指定する（攻撃・防御のスタンス・振りかぶり・回復・爪・吸い込み・ブレスなど、その敵が取る行動）。
    * 城と敵の HP を変える（1 にする、満タンにする、など）。
    * FPS の表示を出し入れする。いまの FPS の値も DEBUG タブの中に出る。
  * DEBUG タブで操作した後も、ゲームはそのまま続けて遊べる（攻防の結果・決着・次の敵への進み方は、ふつうのルールのとおり）。
* **持ち越し事項**:
  * PHASEOUT の `ENABLE_DEBUG_OVERLAY` は、タイトルのボタンしか消さなかった。バトリティアでは、入口・DEBUG タブ・FPS の表示を1つの定数で消す（`_doc/COWORK_STATUS.md` 2章 A。Survey の RES `_log/res/261121_1843_RES_Survey_エンジンへの要望の材料集め.md` 6章）。
  * `_doc/PROJECT_MILESTONE.md` の「デバッグモード」の項目。ここで扱い、完了したら片付ける。
  * （06-01 から）メニューの窓は `js/scenes/MenuScene.js`（窓だけを持つ）、標準のタブの一覧は `js/scenes/menuTabs.js` の `createMenuTabs()`（`[設定, クレジット]` を毎回新しく返す）。窓は `js/main.js` の `createMenu()` で作り、タイトルと盤面に渡している。DEBUG タブは `createMenu` でタブの一覧の後ろに足せば、窓とタブの一覧を書き直さずに済む（06-01 RES）。
  * （06-01 から）盤面の TURN の区画を押せるかは `js/scenes/boardFlow.js` の `canOpenMenu(game)`、当たりは `layout.turnHitTest`。FPS の表示の位置を決めるときは、TURN の区画（`js/view/layout.js` の `turnBox`・押せる範囲 `turnHit`）とも重ならないようにする。
* **メモ**:
  * ルールに触る操作（兵の数＝ゲージの値、敵、次の行動、HP）は、ルール層にデバッグ用の操作を作って呼ぶ。画面やシーンがルールの状態を直接書き換えない（憲法 3章）。
  * 定数を OFF にしたとき、デバッグ用のファイルを読み込まずに済む形（動的 `import` の可否を含む）にするかは、REQ 作成時に決める。
  * 理論上の最大の兵の数は、REQ 作成時にルールの値（行動の数・金貨で増える行動・札の数字・束の補正の上限）から求める。
  * FPS は `Engine.fpsVisible`・`Engine.fps`・`Engine.fpsPosition`（14章）を使う。表示の位置は、最上部のゲージや TURN の区画と重ならない隅にする。

### Phase 06-03: DEBUG タブのルールの値
* **目的**: 敵と城の数値を、DEBUG タブからその場で変えて試せるようにする（Phase 7 の数値の調整に備える）。
* **実装要件**:
  * DEBUG タブに、ルールの値を変える場所がある（タブの中を分けるか、スクロールする領域にまとめる）。
  * 変えられる値は、少なくとも、敵ごとの最大 HP・常時防御力・攻撃や防御のスタンスの量・行動の確率、巨人の周期と回復、ドラゴンの吸い込みの確率とブレス、城の最大 HP である。
  * 変えた値が、いつから効くかが画面で分かる（例: 「次のゲームから」「すぐ」）。
  * 変えた値は保存しない。ページを読み込み直すと `js/rules/config.js` の値に戻る。
  * 値を元に戻す操作がある。
* **持ち越し事項**:
  * （06-02 から）DEBUG タブは `js/scenes/debugTab.js`（部品の組み立て。スクロールする領域）・`js/view/debugLayout.js`（配置）・`js/view/debugText.js`（文字）で作り、`js/main.js` の `createDebugMenu` が標準のタブの後ろに足している。ルール層のデバッグ用の操作は `js/rules/debugControls.js`（予告を作る口は `js/rules/debugIntents.js`）。ルールの値を変える口も、同じようにルール層に置き、DEBUG タブは呼ぶだけにする（06-02 RES）。
  * （06-02 から）敵の切り替え（06-02）は、敵の種類の設定から新しい敵（HP 満タン）を作っている。ルールの値で最大 HP などを変えたとき、切り替えた敵に変えた値が効くかを決める。
  * （06-02 から）兵の数のスライダーの上限 63 は、`config.js` の数字の範囲・束の補正・行動回数・金貨の換算から求めた理論上の最大を、計算せず定数（`debugTab.js` の `TROOP_SLIDER.max`）で持っている。DEBUG タブで変えられる値にこれらを含めるなら、上限の扱いも決める（06-02 RES 5章）。
* **メモ**:
  * ルールの値の持ち主はルール層の設定のファイル（`js/rules/config.js`）。値を変える口はルール層に作り、画面は呼ぶだけにする（憲法 3章）。
  * どの値をすぐ効かせ、どの値を次のゲームから効かせるかは、REQ 作成時に決める（ゲームの途中で最大 HP を変えたときの HP の扱いなど）。
  * 遊び方の文章（`js/view/howToText.js`）の数字は、`config.js` の値を文字で書いたもの。DEBUG タブで変えた値は、遊び方の文章には反映しなくてよい。

### Phase 06-04: 重さの計測とキャンバスキャッシュ
* **目的**: 兵が最大の数のときの描画の重さを、キャッシュありとなしで比べて測り、キャンバスキャッシュを使ってスマホで 60fps 付近を保つ。
* **実装要件**:
  * 兵・ゴブリン・持ち物・シールドなど、たくさん描くスプライトを、キャンバスキャッシュ（`oz/ENGINE_API.md` 25章）で焼き付けて描ける。
  * DEBUG タブのチェックボックス1つで、焼き付けで描くか、元のスプライトを直接描くかを切り替えられる。見た目は、どちらでも同じに見える。
  * DEBUG タブで兵を理論上の最大の数にして、段取り（兵が待っている間）と攻防の演出の両方で、キャッシュありとなしの FPS を測る。測った結果（端末・兵の数・FPS）を RES に残す。
  * キャッシュありのとき、スマホで兵が最大の数でも、段取りと攻防の演出の間、60fps 付近が出ている。届かなければ、ほかの対策（描く物の数を減らす、など）を発注者と決める。
  * ウィンドウの大きさや画面の向きを変えても、絵がぼやけたり崩れたりしない。
* **持ち越し事項**:
  * 兵の数と重さ（`_doc/COWORK_STATUS.md` 2章 A。兵1体ごとに体と持ち物のスプライトを描き、段取りの間も待っている兵を描く）。ここで閉じる。
  * スプライトの線の太さ（`_doc/COWORK_STATUS.md` 2章 A）。焼き付けの倍率と、画面で描く大きさの関係に注意する。
  * （06-02 から）兵の数は DEBUG タブのスライダーで種類ごとに 0〜63（3つを最大にすると 189 体。3種類の合計の理論上の最大は 131）。チェックボックスは `js/scenes/debugTab.js` の部品に足す。FPS の値は DEBUG タブの中に出ていて、表示は左下（`'bottom-left'`）に出る（06-02 RES）。
  * （06-02 から・メモの訂正）陣地の兵の大きさは、数によって変わらない（`js/view/layout.js` の `TROOP_SIZE` の一定の大きさ。06-02 で確かめた）。下のメモの「兵は数によって大きさが変わる」は誤りなので、焼き付けの倍率は今の描く大きさ（攻防の演出の中の大きさを含む）から REQ 作成時に確かめる。
  * （06-03 から）DEBUG タブのルールの値で、ゴブリンの軍勢の最大 HP を 300 にすると群れを 300 体描き（攻防でも1体ずつ動く）、常時防御力を 20 にするとシールドマークが 20 個並ぶ。兵の最大の数に加えて、これらの多い場合も重さを測る対象にするか、REQ 作成時に決める（06-03 RES 5章）。
  * （06-03 から）DEBUG タブの中身の高さは 5504 になった（スクロールする領域 456）。キャッシュの切り替えのチェックボックスを足すときは、FPS の値の近く（ルールの値の並びの上）に置くと探しやすい。DEBUG タブは `js/scenes/debugTab.js` が組み立て、ルールの値の並びは `js/scenes/debugRuleSliders.js`（配置は `js/view/debugLayout.js` の `debugRuleLayout`）が FPS の値の後ろに足している（06-03 RES）。
* **メモ**:
  * キャッシュの入り切りは、エンジンの口ではなく、ゲーム側の描き分けで作る（Survey の RES 4章 R4。発注者の決定）。スプライトの描画を1か所に集めてある（`js/view/spriteView.js`）ので、そこで描き分ける。
  * 兵は数によって大きさが変わる。焼き付けの倍率をいくつ持つか、色ごとに焼き分けるか（25章の注意）は、REQ 作成時に決める。
  * スプライトの `bounds` をキャッシュの範囲に使うか（25章・23章）、兵とゴブリンの絵の範囲の値がスプライトの `bounds` と違う件（`_doc/COWORK_STATUS.md` 2章 A の資料の整合）は、REQ 作成時に確かめる。
  * iPhone の Safari には Canvas のメモリの上限がある（25章の注意）。測る端末に iPhone が入るなら、上限に当たらないかも見る。
  * 測る端末は発注者が決める。

### Phase 06-05: デバッグの入口を URL の `?debug` に統一
* **目的**: デバッグの入口を、URL の `?debug` の1つにまとめる。いまは URL の `?debug` と、`js/main.js` の定数 `DEBUG_TOOLS_ENABLED` の二重持ちになっている（発注者の指摘）。
* **実装要件**:
  * タイトル画面の「デバッグスタート」のボタンを消す。
  * デバッグを有効にする定数（`js/main.js` の `DEBUG_TOOLS_ENABLED`）を消す。
  * URL に `?debug` を付けて開いたときだけ、デバッグのゲームになる。`?debug=0` は、付いていないのと同じ扱いにする（エンジンの決まりに合わせる）。タイトルの「はじめる」から始めたゲームが、いまのデバッグスタートと同じゲームになる（DEBUG タブで変えたルールの値の写しを使う。メニューの窓の一番右に DEBUG タブが出る）。
  * `?debug` が付いていないときは、DEBUG タブ・FPS の表示・「DEBUG MODE」の表示は出ず、デバッグの操作はどこからも呼べない。
  * デバッグのときは、画面の右下に、赤く小さい文字で「DEBUG MODE」と出る。タイトル・遊び方・盤面・メニューの窓を開いている間も出ている。
  * デバッグで開いても、FPS の表示は消えた状態で始まる。今までどおり DEBUG タブから出し入れでき、左下に出る。
  * デバッグのときは、何も保存しない。保存された設定（音量・演出の速さ）は読み込んで使う。設定を変えるとその場で効き、ページを閉じるまで残るが、保存された値は書き換わらない。`?debug` を外して開き直すと、元の設定に戻っている。
* **持ち越し事項**:
  * 06-02 で作った「デバッグスタート」と定数（`_doc/COWORK_STATUS.md` 2章 A の「デバッグの定数」の注意）。ここで閉じる。
  * いまの `?debug` が、どこで読まれ、何を変えているか（発注者によると二重持ち。資料には書かれていない）は、REQ 作成時にコードで確かめる。
* **メモ**:
  * 261125 に OZ Engine を、開発モード（起動設定 `debug` と `Engine.debug`。`oz/ENGINE_API.md` 3章・14章）の入った版へ載せ替えた。URL を読むのは起動のとき1か所だけにして、結果を起動設定 `debug` に渡す。ほかの所は `Engine.debug` を読み、URL は読まない。`Engine.debug` は `Engine.start` の後でしか読めない（3章）ので、起動の前に行う準備とシーンを作る時期に注意する。
