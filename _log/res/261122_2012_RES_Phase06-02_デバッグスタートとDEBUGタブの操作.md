# RES: 作業計画・作業レポート (Phase 06-02) : デバッグスタートと DEBUG タブの操作
* 参照元REQ: `./_log/req/261122_2012_Phase06-02_デバッグスタートとDEBUGタブの操作.md`

## 1. 作業目的
1つの定数で入り切りできるデバッグの入口（タイトル画面の「デバッグスタート」）を作り、デバッグスタートから始めたゲームでだけ、メニューの窓の一番右に DEBUG タブを出す。DEBUG タブから、兵の数（攻撃・防御・修理のゲージ）・今の敵・敵の次の行動・城と敵の HP を操作でき、FPS の表示（`oz/ENGINE_API.md` 14章）を出し入れできるようにする。

* ルールに触る操作（ゲージ・敵・予告・HP）は、ルール層に作ったデバッグ用の操作だけで行う。DEBUG タブの部品（`write`・`onPress`）は、盤面のデバッグの口（シーンの補助）を呼ぶだけで、ルールの状態を直接書き換えない。
* ルールの数値（`js/rules/config.js`）は変えない。座標はすべて論理座標（720×1280）。部品の大きさと位置は定数に置く（試遊で決め直す値）。
* 定数が OFF のときは、タイトル画面・メニューの窓・盤面が 06-01 の後と同じ見た目と動きになる。コミットするときの値は ON。
* 窓の見た目はエンジンの標準のまま（`look` は渡さない）。「設定」「クレジット」タブの中身は変えない。

### 要件3: DEBUG タブ
* **盤面からメニューの作る関数への伝え方:** `BoardScene` は TURN の区画でメニューを積むとき、`this.createMenu({ game: this.game, releaseShow: this.releaseShow, flow: this.flow })` と、盤面の部品を1つのオブジェクト（型 `BoardMenuTarget`。`boardDebug.js` に `@typedef` を置き、`BoardScene.js` は `import('./boardDebug.js').BoardMenuTarget` で参照する）で渡す。
    * ふつうの盤面（`createBoard()`）には今の `createMenu`（引数を使わない）を渡すので、DEBUG タブは出ない。
    * デバッグスタートの盤面（`createDebugBoard()`）には `createDebugMenu` を渡す。`createDebugMenu(target)` は `new MenuScene({ layer: 'main', tabs: [...createMenuTabs(), createDebugTab(new BoardDebug(target))] })`。タブの並びは「設定」「クレジット」「DEBUG」で、窓は毎回新しく作るので毎回「設定」から始まる。
    * 渡す `releaseShow` は攻防のたびに作り直されるが、メニューは段取りの間だけ開け、開いている間は盤面の `update` が止まって攻防に入らないので、開いたときの参照のまま使ってよい（`BoardDebug` の JSDoc に書く）。
* **タブの中身（`debugTab.js` の `createDebugTab(debug)`）:** `{ label: DEBUG_TEXT.tab, build }` を返す。`build(tab)` は `tab.addScroll(DEBUG_LAYOUT.area)` で領域を1つ作り、その中に上から次の順で足す（位置は `DEBUG_LAYOUT`）。
    1. 兵の数の見出し（`addValue`。`label` は関数で、`debug.troopsLocked()` なら `DEBUG_TEXT.troopsLocked`、そうでなければ `DEBUG_TEXT.troopsHeading`。`read: () => ''`）
    2. 攻撃・防御・修理の兵のスライダー（要件4）
    3. 敵の見出し（`addValue`。`DEBUG_TEXT.enemy`、`read: () => ''`）と敵の選択肢の列（要件5）
    4. 次の行動の見出し（`addValue`。`DEBUG_TEXT.intent`）と次の行動の選択肢の列（要件6）
    5. 城の HP の表示と「1 にする」「満タンにする」のボタン、敵の HP の表示と2つのボタン（要件7）
    6. FPS を表示のチェックボックスと、FPS の値（要件8）
* **スクロールの中のスライダー:** 26章のとおり、領域の中のスライダーは縦に動かすとスクロール、横に動かすと値が変わり、動かさずに離すと押した位置の値になる。これに合わせ、スライダーは領域の幅いっぱい（右端の位置の表示の 12 を空けた幅）に置く。
* **操作した結果:** 部品の `write`・`onPress` は `BoardDebug` の操作を呼ぶだけ。ルール層の状態はその場で変わり、窓の部品の `read`・`label` は次の描画で追従する。段取りの間の見た目（陣地の兵・敵の待機・予告の札・HP のゲージ）は、ルール層の値をその場で読むか、`BoardDebug` が anim の口を呼んでその場で合わせるので、窓を閉じたときには変わっている。
* **使わないもの:** 行動の回数・TURN の番号・山札・捨て札・列・手札・金貨のゲージ・結果の集計は、どの操作も触らない。

### 要件4: 兵の数
* **ルール層（`debugControls.js`）:**
    * `troopGaugeIds(config)`: 兵になるゲージの識別子の並び（`config.gauges` から力こぶの換算のゲージ `config.muscleConversion.gauge` を除いたもの。今は `['attack', 'defense', 'heal']`）。
    * `setTroopGauge(game, gauge, count)`: 段取り中で、`gauge` が `troopGaugeIds(game.config)` に含まれ、`count` が 0 以上の整数のときだけ `game.gauges[gauge] = count` にして `true`。それ以外・今と同じ値なら何もせず `false`。行動の回数は使わない。上限はルール層では決めない（スライダーの範囲で決める）。
* **兵の見た目（anim）:**
    * `troopRoster.js` に `removeTroops(roster, kind, count)`: 種類 `kind` の兵のうち、番号（`index`）の大きい方から `count` 体（いる数まで）を `roster.units` と `roster.ranked[kind]` から取り除く。段取りの間の名簿（番号が 0 から続く）で使う前提を JSDoc に書く。家の位置は番号だけで決まる（`campSlot`）ので、残った兵は動かない。
    * `campTroops.js` に `setCount(kind, count, clock)`: いまの数（`roster.ranked[kind]` の長さ）より多ければ、足りない分を `spawnTroops(roster, kind, 足りない数, clock, 0)`（家の位置にすぐ現れ、玉は飛ばない）で足し、少なければ `removeTroops` で減らす。同じなら何もしない。変えたときは `this.swarm = new TroopSwarm(this.roster.units)`・`this.dirty = true`・`this.settledAt = Math.max(this.settledAt, clock)` にして、`this.sample(clock)` で今の時計の見た目を書く（作り直した入れ物の `visible` が 0 のまま描かれないため）。並び方・大きさは、ふつうに放って着いた兵と同じ（同じ名簿・同じ `campSlot`・同じ描く大きさ。数で大きさを変える決まりは今のコードにない）。
    * `releaseShow.js` に `setCampCount(kind, count)`: `this.camp.setCount(kind, count, this.clock)`。動いている間（`isBusy()`）に呼ばないことを JSDoc に書く（判断は呼ぶ側）。
* **動いている途中の扱い（食い違いを起こさない決め方）:** 玉・兵・金貨の数え上げのどれかが動いている間（`releaseShow.isBusy()`）は、兵の数を変えられない。
    * スライダーには `enabled` がない（26章）ので、`BoardDebug.setTroops` が `releaseShow.isBusy()` のとき何もしない。つまみは次の描画で `read`（ルール層の値）の位置に戻る。
    * そのことが分かるよう、兵の数の見出しの文字を「兵が動いている間は変えられません」に替える（`debug.troopsLocked()`）。窓を開いている間は背面の時計が止まるので、動いている途中に開いた窓では閉じるまで変えられない（閉じて動きが終わってから開き直す）。
    * 動いていないときは、ゲージの値（ルール層）と陣地の兵の数（`camp.counts()`）が同じなので、両方を同じ数にそろえれば、閉じた後の画面の兵の数・左上の人数の表示（`release.gaugeValues` がないので `game.gauges`）・攻防で使う数（`game.gauges` と `waitingCounts()`）が食い違わない。
* **`BoardDebug.setTroops(kind, count)`:** `releaseShow.isBusy()` なら何もしない → `setTroopGauge(game, kind, count)` が `false` なら何もしない → `releaseShow.setCampCount(kind, game.gauges[kind])`。
* **スライダー（`debugTab.js`）:** 種類ごとに `addSlider({ ...DEBUG_LAYOUT.troopSliders[kind], label: DEBUG_TEXT.troops[kind], min: TROOP_SLIDER.min, max: TROOP_SLIDER.max, step: TROOP_SLIDER.step, read: () => debug.troopCount(kind), write: (v) => debug.setTroops(kind, v) })`。値の文字は既定（`String(value)`。例「63」）。
    * `TROOP_SLIDER = Object.freeze({ min: 0, max: 63, step: 1 })` を `debugTab.js` に置く。JSDoc に「1種類あたりの理論上の最大（REQ の根拠: 7 枚の束を放つ +34 → 5 枚を置いて放つ +29）。`config.js` の値（数字の範囲・束の補正・行動回数・力こぶの換算）を変えたら見直す。DEBUG タブのスライダーの範囲で、ルールの値ではない」と書く。
    * 種類の並びは `troopGaugeIds` ではなく、`DEBUG_LAYOUT.troopSliders` の項目（`attack`・`defense`・`heal`）の順で足す（文字も配置もこの3つの名前で引く）。

### 要件5: 敵の切り替え
* **ルール層（`debugControls.js`）:**
    * `enemyChoices(config)`: `config.enemyOrder` の順に `{ index, name }`（`name` は `enemySpecAt(config, index).name`）の配列。
    * `switchEnemy(game, index)`: 段取り中で、`index` が 0 以上 `enemyOrder.length` 未満の整数で、`game.enemyIndex` と違うときだけ、`game.enemyIndex = index`、`game.enemy = createEnemy(enemyTypeIdAt(config, index), enemySpecAt(config, index))`（HP 満タン・決まりの状態は初期値）、`game.planIntent()`（新しい敵の決まりでふつうに予告。乱数は `Game` の乱数）をして `true`。それ以外は `false`。TURN・城・盤面・ゲージ・行動の回数・結果の集計は触らない。敵の順番は `enemyIndex` から続くので、倒せば次の敵・ドラゴンを倒せばクリアになる（`startNextPhase`・`isLastEnemy` は今のまま）。
* **段取りの間の見た目と BGM:**
    * `boardFlow.js` に `enterSwitchedEnemy(game)`: `this.stageEnemyIndex = game.enemyIndex`（ステージの始まりを出したことにする。これで `update` がステージの始まりの演出を出さず、`entranceLook` は見える・ずれなし）→ `playStageBgm(game.enemy.typeId)`（同じ曲ならエンジンが何もしないので、ゴブリンと巨人の間は流れたまま）。フェーズの始まりの印（`introPhase`）は触らない。
    * 敵の絵・ゴブリンの群れ（HP の数）・シールドマーク・予告の札・数え下ろし・最上部の HP のゲージは、描くときに `game.enemy`・`game.attackCountdown()` を読むので、そのまま新しい敵になる。待機の伸び縮み（`EnemyIdle`）は盤面の `update` で `game.enemy` を読み直すので、窓を閉じた後の最初の `update` から新しい敵に合う（窓を開いている間の背面は群れの伸び縮みが 1 のままでもよい。`drawHorde` は数が足りないとき 1 で描く）。
* **`BoardDebug.switchEnemy(index)`:** `switchEnemy(game, index)` が真なら `flow.enterSwitchedEnemy(game)`。
* **選択肢の列（`debugTab.js`）:** `addChoices({ ...DEBUG_LAYOUT.enemyChoices, choices: debug.enemyChoices().map((e) => ({ label: e.name, value: e.index })), read: () => debug.enemyIndex(), write: (v) => debug.switchEnemy(v) })`（横に並べる。今の敵が選ばれて見える。同じ値では `write` は呼ばれない）。

### 要件6: 敵の次の行動の指定
* **選択肢の識別子:** ゴブリンの軍勢（`weighted`）は行動の設定の `kind` の並び（今は `'attack'`・`'defend'`）、巨人（`cycle`）は `'windup'`・`'attack'`・`'attackHeal'`（`attackHeal` は決まりに `attackHeal` があり `amount > 0` のときだけ）、ドラゴン（`inhale`）は `'claw'`・`'inhale'`・`'breath'`。
* **`enemyBehaviors.js` の行動を作る関数（export）:** 今の決め方の中で行動のオブジェクトを作っている所を、次の関数に出して両方から使う（形と乱数の呼び方は今と同じ）。
    * `rollAmount(range, random)`（今の関数を export する）
    * `weightedAction(spec, random)` → `{ kind: spec.kind, amount: rollAmount(spec.range, random) }`（`pickWeighted` の戻り値をこれで作る）
    * `windupAction()` → `{ kind: 'windup', amount: 0 }`
    * `cycleAttackAction(behavior, random)` → `{ kind: 'attack', amount: rollAmount(behavior.attackRange, random) }`
    * `clawAction(behavior, random)` → `{ kind: 'attack', amount: rollAmount(behavior.claw.range, random), variant: 'claw' }`
    * `breathAction(behavior, random)` → `{ kind: 'attack', amount: rollAmount(behavior.breath.range, random), variant: 'breath', burn: behavior.breath.burn }`
    * `inhaleAction()` → `{ kind: 'windup', amount: 0, variant: 'inhale' }`
    * `cycle`・`inhale` の `planNext` はこれらを同じ順・同じ条件で呼ぶように書き換える（`inhale` の「`random() < inhaleChance` → 外れなら爪」の順も今のまま）。ふつうの遊びの展開（乱数の消費）は変わらない。
* **攻撃して回復:** 予告に任意の項目 `sureHeal: true` を付けると、`rollAttackHeal` が今の判定（攻撃でない・回復の設定がない・量が 0 以下なら 0）の後に、`action.sureHeal === true` なら乱数を呼ばず `heal.amount` を返す。回復の量は `config.js` の巨人の回復の量で、最大 HP での頭打ちは `battle.js` のまま。`combatants.js` の `EnemyAction` の型に `@property {boolean} [sureHeal]`（デバッグで「攻撃して回復」を指定した予告だけが持つ。攻撃の直後の回復が必ず当たる）を足す。次のフェーズの予告はふつうに作り直すので、印は1回の攻防で消える。
* **ルール層（`debugIntents.js`。純粋関数）:** 決まりの種類 → `{ ids(behavior), plan(behavior, id, random), chosen(behavior, intent) }` の凍結した表を持ち、次の3つを export する。未知の種類は `Error`。
    * `intentChoiceIds(behavior)`: 上の識別子の並び（毎回新しい配列）。
    * `planChosenIntent(behavior, id, random)`: `{ action, state }` を返す。
        * `weighted`: `behavior.actions` の中の `kind === id` の設定で `weightedAction`。状態は `{}`。
        * `cycle`: `'windup'` → `windupAction()`・状態 `{ countdown: behavior.cycleLength - 1 }`（周期の頭からやり直し。数え下ろしの表示は「攻撃まで あと 周期−1」）。`'attack'` → `cycleAttackAction`・状態 `{ countdown: 0 }`（このフェーズで攻撃。攻撃の後は今の `planNext` が周期の頭から始める）。`'attackHeal'` → `{ ...cycleAttackAction(...), sureHeal: true }`・状態 `{ countdown: 0 }`。
        * `inhale`: `'claw'` → `clawAction`、`'inhale'` → `inhaleAction()`、`'breath'` → `breathAction`。状態はどれも `{ lastVariant: action.variant }`（吸い込むの次は必ずブレス、ブレスの次は爪、爪の次はふつうの抽選。今の `planNext` のまま）。
        * 識別子が表にないときは `Error`（呼ぶ側が `intentChoiceIds` で確かめてから呼ぶ）。
    * `chosenIntentOf(behavior, intent)`: 今の予告に当たる識別子（`intent` が `null` なら `null`）。`weighted` は `intent.kind`、`cycle` は `windup` なら `'windup'`・攻撃で `sureHeal === true` なら `'attackHeal'`・ほかの攻撃は `'attack'`、`inhale` は `intent.variant ?? null`。
* **ルール層（`debugControls.js`）:**
    * `intentChoiceIdsOf(game)`: 今の敵の決まりの `intentChoiceIds`。
    * `intentChoiceSlotCount(config)`: `enemyOrder` の全部の敵の選択肢の数の最大（今は 3）。
    * `currentIntentChoice(game)`: 今の敵の決まりの `chosenIntentOf(behavior, game.enemy.intent)`。
    * `chooseEnemyIntent(game, id)`: 段取り中で、敵の HP が 0 より大きく、`id` が `intentChoiceIdsOf(game)` に含まれ、`currentIntentChoice(game)` と違うときだけ、`planChosenIntent(behavior, id, game.random)` の `action`・`state` を `game.enemy.intent`・`game.enemy.behaviorState` に入れて `true`。それ以外は `false`（今の予告と同じなら量の抽選もしない）。
* **窓を開いたまま敵を切り替えたとき（選択肢の列の作り方）:** 選択肢の列は1つだけ足し、選択肢は「枠の番号」（0 から `debug.intentSlotCount() - 1`。足すときに1回読む）を `value` にして、`label` を関数にする（26章の選択肢の `label` は描くたびに呼ぶ関数にできる）。
    * 枠 `i` の `label`: `debug.intentChoiceAt(i)` が識別子なら `intentChoiceText(識別子)`、`null`（今の敵の選択肢がその枠まで無い。ゴブリンの3つ目）なら `DEBUG_TEXT.noChoice`（「－」）。
    * `read`: `debug.selectedIntentSlot()`（今の予告に当たる識別子の、今の敵の並びの中の番号。無ければ -1 でどれも選ばれない）。巨人の「攻撃」と「攻撃して回復」は `sureHeal` で分かれるので、指定したかどうかで選ばれる見た目が分かれる（ふつうに決まった攻撃は「攻撃」）。
    * `write`: `debug.chooseIntentSlot(i)`（枠の番号を今の敵の識別子に直して `chooseEnemyIntent`。識別子の無い枠では何もしない）。
    * 敵を切り替えると、次の描画から `label`・`read` が新しい敵の並びで答えるので、選択肢が新しい敵のものになる。
* 予告の札・数え下ろしは `game.enemy.intent`・`game.attackCountdown()` を描くときに読むので、指定したらそのまま変わる。

## 5. 懸念事項・要確認ポイント
* **兵の数のスライダーの範囲 63:** `debugTab.js` の `TROOP_SLIDER.max` に置く（REQ の発注者の決定）。`config.js` の値から求めた理論上の最大だが、式では計算せず定数で持つので、`config.js` の数字の範囲・束の補正・行動回数・力こぶの換算を変えたら手で見直す（JSDoc に書く）。
* **兵が動いている間のスライダー:** 26章のスライダーには `enabled` がないため、動いている間は `write` が何もせず、つまみが次の描画で元の値に戻る（見出しの文字が「兵が動いている間は変えられません」に替わる）。動いている途中に開いた窓では、閉じて動きが終わるまで変えられない。試遊で分かりにくければ見せ方を決め直す。
* **ゴブリンの軍勢の次の行動の3つ目の枠:** 選択肢の列は1つで枠の数が 3（巨人・ドラゴン）なので、ゴブリンのときは3つ目の枠に「－」が出て、押しても何も起きない。目視で確かめてほしい。
* **選択肢の文字の幅:** 敵の選択肢（「ゴブリンの軍勢」）・次の行動の選択肢（「攻撃して回復」）は1つの幅が約 193 で、標準の見た目は文字を横に縮めて収める（26章）。読みにくければ、試遊で列の幅・文字の大きさ（窓の `textSize` は 06-01 のまま）を決め直す。
* **FPS の表示の隅:** 左下（`'bottom-left'`）にしたので、1本目の列の放つボタンの近くに文字が重なって見える（入力は受けない）。上の隅は HP の数字と重なる。試遊で決め直す値。
* **「攻撃して回復」の乱数:** `sureHeal` の予告では回復の抽選の乱数を呼ばないので、その攻防の後の乱数の並びは、ふつうに決まった攻撃と違う（デバッグで指定したときだけ）。ふつうの遊びの乱数の並びは変わらない（行動を作る関数の書き出しで呼ぶ順を変えないことをタスク1で確かめる）。
* **兵の大きさ:** REQ の「数によって大きさが変わる、など」に当たる決まりは今のコードに見当たらない（陣地の兵は `layout.js` の `TROOP_SIZE` の一定の大きさ）。DEBUG タブで並べた兵も、ふつうに着いた兵と同じ名簿・同じ家の位置（`campSlot`）・同じ大きさで描く。
* **窓を開いている間の背面:** 敵を切り替えた直後、窓の後ろの盤面はすでに新しい敵で描かれるが、ゴブリンの群れの伸び縮みは盤面の `update` が再開するまで止まって見える（暗幕の下。閉じると動く）。
