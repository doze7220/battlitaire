# RES: 作業計画・作業レポート (Phase 06-04) : 重さの計測とキャンバスキャッシュ
* 参照元REQ: `./_log/req/261123_1540_Phase06-04_重さの計測とキャンバスキャッシュ.md`

## 1. 作業目的
兵・ゴブリン・持ち物・シールド・炎など、戦闘の段にたくさん描くスプライトを、キャンバスキャッシュ（`oz/ENGINE_API.md` 25章。以下「焼き付け」）で前もって焼き付け、毎フレームはその画像を貼るだけにして描けるようにする。DEBUG タブのチェックボックス「焼き付けで描く」で、焼き付けで描くか元のスプライトを直接描くかを切り替えられるようにし、兵が多いときの重さ（FPS）を、焼き付けあり・なしで発注者が Android のスマホ（Chrome）で測り、結果を本 RES に残す。

* 絵の位置・大きさ・動き（傾き・伸び縮み・濃さ・奥と手前の描き分け）は変えない。`SPRITE_TABLE` の範囲・`TROOP_SIZE`・持ち物の大きさとずれの割合・シールドマークの並べ方・スプライト（`assets/sprites/`）は変えない。
* 焼き付けで描くか直接描くかの描き分けは、描画層の1か所（`js/view/troopView.js` の `drawTroop`）だけで行う。呼ぶ側（`enemyView.js`・`battleStageView.js` など）に分岐を散らさない。
* 焼き付けと入り切りの設定は「描き方の資源・設定」で、ゲームの状態ではない。ルール層には置かない。保存しない。
* 60fps に届かなくても、今回は結果を残して報告するまでとし、ほかの対策は入れない。
* 座標はすべて論理座標（720×1280）。

### 要件1: 焼き付けで描くもの

#### 対象と、描く入口の1本化
* 対象は、`troopView.js` の `drawTroop` で描くすべての種類（`attack`・`defense`・`heal`・`enemy`・`enemyGuard`・`goblin`・`shield`・`flame`）と、`enemyView.js` の段取りの間のゴブリンの群れ（今も `drawTroop` の `'goblin'` で描く）と、シールドマーク（巨人・ドラゴン・ゴブリンの軍勢の常時防御力）。
  * 段取りの間に陣地で待つ兵（`boardView.js` → `battleStageView.js` → `drawTroopSwarm` → `drawTroop`）と、攻防の演出中の兵・ゴブリン・シールド・炎（`battleShowView.js` → `battleStageView.js` → `drawTroopSwarm` → `drawTroop`）は、どちらも `drawTroop` を通るので、`drawTroop` の中だけで描き分ければ両方が焼き付けになる。
  * シールドマークだけは今 `enemyView.js` の `drawShieldMark` が `drawSpriteCentered(ctx, SPRITE_IDS.shield, rect.x + rect.w / 2, rect.y + rect.h / 2, rect.w)` で直接描いている。これを `drawTroop(ctx, 'shield', rect.x + rect.w / 2, rect.y + rect.h, rect.w, 0, 1, 1, 1)` に置き換える。
    * 同じ位置・大きさになる理由: `drawTroop` → `drawTroopFigure` は `translate(x, footY)` の後に `drawSpriteCentered(shield, 0, -size / 2, size)` を描く。`shieldRects` の矩形は正方形（`w = h = size`）なので、中心の y は `rect.y + rect.h - rect.w / 2 = rect.y + rect.h / 2` で今と同じ。大きさ（長い方の辺）も `rect.w` で同じ。持ち物はない（`TROOP_LOOKS.shield.item` は `null`）。
    * 濃さ: `drawTroop` は `ctx.save()` の中で `globalAlpha = 1` にして描く。段取りの間の `drawEnemyFigure` は濃さを変えずに呼ばれている（ゴブリンの群れも同じく `drawTroop` で濃さ 1）ので、見た目は変わらない。
    * 攻防の演出中のシールド（名簿の `'shield'`）は今も `drawTroop` で、大きさは `enemyBody.js` が同じ `shieldRects(armor, shieldArea)` の `r.w` を渡している。段取りの間のシールドマークと同じ大きさの焼き付けを使える。
* 上のもの以外（カード・山札・城・巨人・ドラゴンの絵・背景・ロゴ・数字・予告の絵・ヒットマーク・玉・人数の表示のアイコン・燃える札の上の小さな炎（`boardView.js` の `drawSpriteCentered(SPRITE_IDS.fire, …)`）など）は今のまま直接描く（`drawTroop` を通らないので変わらない）。

#### 焼き付けの単位: 見た目（体＋持ち物）ごとに1枚、大きさごとに1枚
* 体と持ち物を**1枚にまとめて**焼き付ける。1体を描くのが画像1枚の貼り付けになり、描く回数が最も少ない（兵 189 体・ゴブリン 300 体で効く）。
* 焼き付けの識別子（`TROOP_LOOKS` に足す `bake`）は見た目の組で決める。同じ見た目の種類は1枚を共有する。

| 焼き付けの識別子 | 兵の種類 | 中身 |
| --- | --- | --- |
| `attack` | `attack` | 兵の体（`soldier`）＋剣（`gaugeSprite('attack')`） |
| `defense` | `defense` | 兵の体＋盾（`gaugeSprite('defense')`） |
| `heal` | `heal` | 兵の体＋ハンマー（`gaugeSprite('heal')`） |
| `goblin` | `enemy`・`enemyGuard`・`goblin` | ゴブリンの体（持ち物なし） |
| `shield` | `shield` | 盾の絵（持ち物なし） |
| `flame` | `flame` | 炎の絵（持ち物なし） |

* 色違いはない（どの種類も色は焼き付けの中身で決まり、描くときに変えるのは濃さ（`globalAlpha`）だけ）。

#### 倍率と大きさ: 今の描く大きさで、論理 px のまま焼き付ける（`scale: 1`）
* 焼き付ける描く処理（`source`）は、**足元を原点 (0, 0) に、今の描く大きさのまま、傾き 0・伸び縮み 1 で**兵1体を描く関数にする。中身は今の直接描く処理そのもの:
  `(ctx) => drawTroopFigure(ctx, look.body, look.item, 0, 0, size, 0, size * ITEM_SIZE_RATIO, size * ITEM_DX_RATIO, size * ITEM_DY_RATIO, 1, 1)`
* `bounds` は、この描く処理の座標（論理 px。足元が原点）での範囲（下の「焼き付ける範囲」）。`scale` は `1`。
  * 25章「自動の焼き直し」のとおり、焼き付ける画素数は `scale` と画面の画素の細かさからエンジンが決めるので、論理 px で焼けば、どの画面でも今の描く大きさに合った細かさになる。描くときの倍率は呼吸の伸び縮み（1 の近く）だけなので、25章の注意（`scale` と大きく違う倍率で描くとぼやける・線が淡くなる）に当たらない。
* 大きさの種類:
  * `shield` 以外の5つは、配置の兵の大きさ（`battleLayout.troops.size`＝`TROOP_SIZE`＝24）の1つだけ。兵・ゴブリン（群れ・名簿）・炎は、名簿の `size` が 0（配置の大きさを使う）か、`hordeSlots` の `size`（`TROOP_SIZE`）で描かれている。
  * `shield` は、シールドマークの数（常時防御力）と並べ先の矩形で大きさが変わる（`shieldRects` の1マスの 0.8 倍）。並べ先は、ゴブリンの軍勢の群れの矩形（`battleLayout.enemy`）と、巨人・ドラゴンの絵の `shieldArea`（`battleLayout.enemyFigures[typeId].shieldArea`）。`createTroopBakes` は、それぞれの並べ先について数 1〜`SHIELD_BAKE_MAX_COUNT`（20。DEBUG タブの常時防御力のスライダーの最大 `RULE_SLIDERS.armor.max` に合わせた値）の `shieldRects(n, body)` を求め、出てくる大きさ（`rect.w`）を重ねずに集めて、その大きさごとに1枚ずつ焼き付ける（今の配置では、ゴブリンの軍勢で約 21.4、巨人・ドラゴンで約 15.4 と 12 の、合わせて 3〜5 種類ほど）。
  * 数が `SHIELD_BAKE_MAX_COUNT` を超えるなど、焼き付けていない大きさを描くときは、`findTroopBake` が `null` を返し、今のとおり直接描く（見た目は同じ。重さだけ変わる）。
* 大きさの照合は、`|焼き付けの大きさ - size| <= 1e-6`（同じ関数・同じ値から計算した数どうしなので同じ数になる。念のため差で比べる）。

#### 焼き付ける範囲（線の太さを含む）
* `spriteView.js` に `troopFigureBakeBounds(bodyId, itemId, size, itemSize, itemDX, itemDY)` を足す。`drawTroopFigure(ctx, bodyId, itemId, 0, 0, size, 0, itemSize, itemDX, itemDY, 1, 1)` が描く範囲を、論理 px（足元が原点）の `{ minX, minY, maxX, maxY }` で返す。
  * 部品（体・持ち物）ごとに、`drawSpriteCentered` と同じ変換（倍率 `s = 描く大きさ / max(表の幅, 表の高さ)`、表の範囲の中心を描く中心にそろえる）で、**焼き付けの元の範囲**を移した矩形を求め、2つ（持ち物がなければ1つ）を合わせ、四方に余白 `BAKE_EDGE_PAD`（論理 px で 1）を足す。
  * 焼き付けの元の範囲 = 表（`SPRITE_TABLE`）の範囲と、スプライトの `bounds`（OZ Vector Editor の書き出し。線の太さの半分を含む。23章で、キャンバスキャッシュの範囲として読んでよいとされる）を合わせた範囲。`bounds` が `null` や形の違うものなら、表の範囲だけを使う。
    * 兵・ゴブリンの表（x ±99・y ±98）は線の太さを含まないので、`bounds` と合わせることで線のふちが切れない（今のスプライトの `bounds` は x ±106・y ±105。剣・盾・ハンマーも `bounds` が表より少し広い）。尖った角の線（`miter`）が `bounds` から少しはみ出す分は、余白 1px（体の倍率でスプライトの約 8 単位、持ち物で約 12 単位）で収まる。
  * 描く位置・大きさの基準は表の範囲のまま（`drawTroopFigure` をそのまま使うので変わらない）。`bounds` を読むのは焼き付ける範囲を求めるときだけで、描く位置・大きさには使わない。
* `bounds` を読むのは `spriteView.js` の中だけ（`assets/sprites/` を import するのが `spriteView.js` だけなのは変わらない）。

#### 描き分け（`troopView.js` の `drawTroop`）
* `drawTroop(ctx, kind, x, footY, size, tilt, alpha, scaleX, scaleY)` の頭で見た目を引いた後、`const bake = findTroopBake(look.bake, size);` を呼ぶ。
  * `bake !== null` のとき: `ctx.save()` → `ctx.globalAlpha = alpha` → `ctx.translate(x, footY)` → `tilt !== 0` なら `ctx.rotate(tilt)` → 伸び縮みが 1 でなければ `ctx.scale(scaleX, scaleY)` → `bake.draw(ctx)` → `ctx.restore()`。これは今の `drawTroopFigure` の変換と同じ順・同じ軸（足元）なので、位置・大きさ・傾き・伸び縮み・濃さは今と同じになる。
  * `bake === null` のとき（設定が「外す」、入れ物がない、焼き付けていない大きさ）: 今のとおり `drawTroopFigure` で直接描く。
* `findTroopBake` は、設定が「入れた」で、いま使っている入れ物があり、その識別子と大きさの焼き付けがあるときだけ焼き付けを返す。設定と入れ物の有無はここで見るので、`drawTroop` の分岐は `bake !== null` の1つだけ。
* `drawTroopSwarm`・`enemyView.js`・`battleStageView.js` は分岐を持たない。
* 毎フレームの重さ: 1体ごとに `Map` を1回引き、大きさの並び（`shield` 以外は1つ、`shield` は数個）をたどるだけ。オブジェクト・文字列は作らない。

#### 作る場所・持ち主・手放す時期
* 持ち主は盤面のシーン（`BoardScene`）。`init` の最後で `this.troopBakes = createTroopBakes(this.layout.battle)` を呼び、新しく書く `destroy()` で `this.troopBakes.dispose()` して `null` にする（`BoardScene` は `Scene` を直接継承しているので `super.init()`・`super.destroy()` は要らない。25章「作れる時期」は基底クラスで作る場合の決まり）。
  * `init` は `Engine.start` の後に呼ばれる（25章「作れる時期」）。
  * 攻防の演出のシーン（`BattleShowScene`）とメニューの窓（`MenuScene`）は盤面の上に `pushScene` で積まれ、その間 `BoardScene` は外れない（6章）ので、攻防の演出中も同じ焼き付けで描ける。`BattleShowScene` は焼き付けを持たない（変えない）。
  * 決着の後のタップの `Engine.changeScene`（TITLE へ）は、最前面から順に全シーンの `destroy()` を呼んでから新しいシーンの `init()` を呼ぶ（6章）。`BoardScene.destroy` で手放した後に兵を描くことはない。
  * タイトル画面・遊び方の画面・BOOT は兵を描かないので、入れ物がなくても困らない（`findTroopBake` は `null`。直接描く道もそのまま残る）。
* 入れ物（`TroopBakeSet`）は `troopBakes.js` のモジュールの中に「いま使っている入れ物」（`current`）として1つだけ覚え、`drawTroop` は引数を増やさずに引ける。`openTroopBakes` で作った入れ物が `current` になり、`dispose()` はその入れ物が `current` のときだけ `current` を `null` に戻す（手放した後の焼き付けを引かない）。`dispose()` は2回目以降何もしない。
* 量とメモリ: 焼き付けは 10 枚ほど（兵の見た目5つ×1、シールド 3〜5 つ）。どれも一辺 31 論理 px ほどまで（いちばん大きい防御（体＋盾）で約 30.2 論理 px）で、画面の画素の倍率 3 でも 1 枚 約 91×91 画素（約 33KB）、合わせて 0.5MB に届かない。ゲームごとに作り直して手放すので、たまり続けない（25章の注意・iPhone の Safari の上限に当たらない）。
* ウィンドウの大きさ・画面の向きを変えたときは、エンジンが次に描くときに焼き直す（25章「自動の焼き直し」）。描く処理は `size` などを閉じ込めた関数なので、何度呼ばれても同じ絵を描く。ゲーム側は何もしない（`refresh()` は使わない。色や見た目を後から変えないため）。

### 要件2: 焼き付けの入り切り（DEBUG タブ）
* 設定の持ち主は、いま使っている入れ物（`TroopBakeSet` の `enabled`。作ったときは `true`）。`troopBakes.js` が次の2つを出す。
  * `troopBakesEnabled()`: いま使っている入れ物があり、その `enabled` が真なら `true`。読むだけ（状態を変えない）。
  * `setTroopBakesEnabled(on)`: いま使っている入れ物の `enabled` を `on` にする（入れ物がなければ何もしない）。呼ぶのは DEBUG タブのチェックボックスの `write` の中だけ。
* 入れ物は盤面ごとに作られるので、新しいゲーム（「はじめる」・デバッグスタートのどちら）も「入れた」状態で始まる。ページを読み込み直しても「入れた」から。`Storage` には書かない。
  * デバッグの定数が OFF のとき・「はじめる」のゲームでは DEBUG タブがないので、いつも焼き付けで描く。デバッグスタートのゲームで外しても、次のゲームでは「入れた」に戻る（「はじめる」のゲームが直接描きになることはない）。
  * デバッグスタートの1つのゲームの中では、段取りの間に切り替えた設定が、攻防の演出中も、次に段取りに戻ったときも、同じ入れ物の値なので変わらない。
* 切り替えはすぐ効く: `drawTroop` が描くたびに `findTroopBake` で設定を読むので、チェックボックスを押した次の描画から変わる。
* DEBUG タブの部品:
  * `debugText.js` の `DEBUG_TEXT` に `bakedDrawing: '焼き付けで描く'` を足す（JSDoc の型にも足す）。
  * `debugLayout.js`: `FPS_VALUE_Y` の下に `BAKE_CHECK_Y = FPS_VALUE_Y + LABEL_H + GAP`（今の値で 1428）を足し、`DEBUG_LAYOUT.bakeCheckbox = rect(BAKE_CHECK_Y, CHECK_H)` を足す。`debugRuleLayout` の元に戻すボタンの y を `BAKE_CHECK_Y + CHECK_H + GAP`（今の値で 1532。今より 104 下）にする。JSDoc の位置の例を直す（ボタン y=1532、城の見出し 1636・スライダー 1708、ゴブリンの軍勢の見出し 1856・スライダー 1928 から 148 おき、…、ドラゴンの最後のスライダー 5476）。ほかの矩形は変えない。
  * `debugTab.js`: FPS の値（`addValue`）の後、`addRuleSliders` の前に、`area.addCheckbox({ ...DEBUG_LAYOUT.bakeCheckbox, label: DEBUG_TEXT.bakedDrawing, read: () => troopBakesEnabled(), write: (on) => setTroopBakesEnabled(on) })` を足す（`../view/troopBakes.js` から import）。`read` は状態を変えない。06-02・06-03 の部品の動きは変えない（チェックボックスを足した分、ルールの値の並びが下へずれるだけ）。

## 5. 懸念事項・要確認ポイント
* **濃さが 1 より小さいときの重なり**: 体と持ち物を1枚に焼き付けるので、兵が消えていく間（濃さが 1 より小さい間）は、直接描くとき（体と持ち物を別々に薄く重ねるので、持ち物の下に体が少し透ける）と違い、持ち物の下の体は透けない。短い間で小さい絵なので見分けにくいと考えるが、テストプレイで目立つなら知らせてほしい。
* **伸び縮み・傾きの補間**: 呼吸の伸び縮み・揺れの傾きは、焼き付けた画像に `ctx` の変換を掛けて描くので、画像の補間でわずかに柔らかく見えることがある。変換のないとき（伸び縮み 1・傾き 0）は、位置が画面の画素に丸められる（25章）ため、動いている兵がわずかに画素単位で動くことがある。どちらも画面の画素の倍率が高いスマホでは見えにくいと考える。
* **シールドの大きさ**: 常時防御力が 21 以上（DEBUG タブのスライダーの最大 20 を超える値）や、配置を変えて新しい大きさが出たときは、その大きさの焼き付けがなく、直接描く（見た目は同じで重さだけ変わる）。`SHIELD_BAKE_MAX_COUNT` はスライダーの最大と手で合わせる。
* **兵・ゴブリンの `bounds` の値**: 開発資料と `spriteView.js` の JSDoc では、兵（`unit_solder.js`）とゴブリン（`unit_goblin.js`）の `bounds` を x ±101・y ±100 と書いているが、今のスプライトの `bounds` は x ±106・y ±105（剣・盾・ハンマーも表より少し広い）。表の値・描く大きさは変えず、焼き付ける範囲にだけ `bounds` を使うので見た目には影響しない。記述はタスク1・タスク8で今の値に直す。
* **初めのチェックボックスの状態**: 「焼き付けで描く」は盤面（ゲーム）ごとに「入れた」から始まる（デバッグスタートのゲームで外しても、次のゲームでは入れた状態に戻る）。1つのゲームの中では、段取りの間・攻防の演出中・次の段取りで同じ設定。
* **タスク1の確認**: 開発資料の更新予定（1章の `bounds` の値・線の太さ 16・約 7%）は、タスク1で確かめた値と一致している。追加の更新予定はなし。
* **兵が半透明（alpha<1）のときの見た目の違い**: 兵が出てくるときのフェードイン（`js/anim/troopMotion.js` の `out.alpha`）などで濃さが 1 より小さいとき、直接描くと体と持ち物・線と塗りの重なりが透けるが、焼き付けは1枚の画像に alpha を1回掛けるので重なりは透けない。実装は直さない。テストプレイで、出てくるときの見た目の違いを PC で見てもらう（上の「濃さが 1 より小さいときの重なり」と同じ性質）。
* **シールドの焼き付けの数とメモリ**: 並べ先（群れの矩形 `enemy`・巨人・ドラゴンの `shieldArea` の3つ）× 数 1〜20 の1マスの大きさを、`troopView.js` の `bakeSizes` と同じ式（重複は 1e-6 以内で除く）で、実際の `createLayout`（720×1280）の値から数えた（スクラッチで計算。コードは足していない）。群れの矩形は 21.44 の1つ、巨人は 15.44 と 12.00、ドラゴンは 15.42 と 12.00 で、重複を除くと **4つ**（21.44・15.44・15.42・12.00）。範囲はタスク1の値（一辺 約 12〜24 論理 px）で、1枚あたり約 12×14〜20×24 論理 px。4枚で約 1200 論理 px² × 4 バイト ＝ 約 5KB（画面の画素の倍率が 3 なら約 9 倍で約 45KB）。兵・ゴブリンなど全部を合わせても数十枚に満たず、メモリは問題にならない。15.44 と 15.42 は別々の大きさとして2枚焼かれる。
* **タスク7（計測の結果）**: 場面ごとの数値と端末名の報告がなく、焼き付けありで 60fps 付近に届いたかは確定できない（所見は「問題なさそう」）。どの場面で何が出ているときに下がるかの報告もなく、ほかの対策・対象の拡大は入れていない。
