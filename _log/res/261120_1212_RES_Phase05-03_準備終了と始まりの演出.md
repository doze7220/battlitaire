## 1. 作業目的
段取りの終わり方を「行動を使い切ると『準備終了』が出て、タップで攻防」に変え、攻防（BATTLE!）・フェーズ・ステージの始まりを、ロゴのスプライトを使った短い演出で見せる。あわせて、途中の敵を倒した後の案内から「次は○○」を消し、遊び方の文章を新しい画面（05-01）と流れ（今回）に合わせる。
* ロゴ（準備終了・BATTLE!・PHASE・STAGE・敵の名前3つ）と数字（0〜9）の 17 個のスプライト JS を、手で書いた仮のもの（直線だけの太いブロック体の英字・数字。OZ Vector Editor の「開く」で開いて編集できる形）として作る。後で発注者がエディタで描き直して同じ名前で差し替えても、ゲーム側のコードを変えずに描けるようにする。
* 「準備終了」と「BATTLE!」が出た瞬間に、新しい名前の効果音を鳴らす（今はどちらも行動終了の音のファイル）。ステージの曲は、ステージの始まりの演出と同じ時刻に流し始める。

ルール層（`js/rules/`）は変えない。演出の途中のどの時点でも、ルールの結果は変わらない。演出の長さはすべて設定の値にまとめ、試遊（後のサブフェイズ）で決め直す。タイトルからクリア・負けまで、スマホの縦画面と PC で通しで遊べることを保つ。

## 2. アーキテクチャ設計

### 今の流れ（調べた結果）
* **攻防に入るまで**: `BoardScene.update` の最後で、`game.canResolveBattle()`（段階が `'planning'` で行動を使い切った）かつ `!animator.isBusy()` かつ `!releaseShow.isBusy()` なら `startBattle()` を呼ぶ。`startBattle` は 攻防の前の値の写し（`snapshotBattle(game)`）→ 待っている兵の数（`releaseShow.waitingCounts()`）→ `game.resolveBattle()` → 行動終了の音（`playTurnEndSe()`）→ 放つ演出の作り直し → `BattleShowScene` を `Engine.pushScene` で積む。`onPointer` は、札が動いている間（`animator.isBusy()`・`releaseShow.isHoldingCards()`）は無視し、行動を使い切っていれば選択を外して戻る。
* **攻防の後**: `BattleShowScene.update` が、決着も撃破もなく `director.isReadyToLeave()` なら `game.startNextPhase()` → `Engine.popScene()`。撃破なら演出の終わりに `drawDefeat`（暗幕・「○○を倒した！」・「次は○○」・「タップで次へ」）を出し、`onPointer` のタップで `game.startNextPhase()`（ここで敵が入れ替わる。`game.phase` も 1 増える）→ `Engine.popScene()`。決着なら結果の板、タップで `Engine.changeScene(createTitle())`。`BattleShowScene` は今回変えない。
* **ステージの曲**: `BoardScene` が `stageBgmWaitMs`（init で `BGM_TIMING.startToStageMs`＝1200）を `update` の `dt` で減らし、0 になって `stageBgmEnemyIndex !== game.enemyIndex` なら `playStageBgm(game.enemy.typeId)`（`updateStageBgm`）。敵が入れ替わった後は、`popScene` の次のフレームの `update` で流れる。
* **エンジンの決まり（`oz/ENGINE_API.md`）**: 積むと背面のシーンは `update` が止まり `draw` は続く（6章）。シーンの操作があったフレームはティックが回らない（8章）。1フレームの順は「時間を進める → 入力を配る → `update` → `draw`」（19章）。このため、`BattleShowScene` が外れた直後のフレームでは、`BoardScene` の `update` が回る前に `draw` と（次のフレームの）入力が来ることがある（下の「フェーズ・ステージの始まりの待ち」で対処する）。
* **フェーズの番号**: `game.phase` は敵をまたいで数え続ける（敵が替わっても 1 に戻らない）。`game.enemyIndex` は 0 から。
* **配置**: 戦闘の段は 720×360（`BATTLE_H`、地面の線は y=260）。最上部のゲージは y 8〜58 付近、人数の表示（左上）と数え下ろしの枠（右上）は y 12〜52、予告の枠は x 360〜700・y 312〜352。敵の中心は x=620。巨人・ドラゴンの絵の左端は x≈540、ゴブリンの群れ（HP 30）の左端は x≈589。

**点の求め方**:
* ロゴ: 字の並びの幅 TW = Σ（字の幅）+ G ×（字の数 − 1）。字の幅は英字 4u、`!` は 1u。i 番目の字の左端 Lᵢ = −TW/2 + Σ_{j<i}（字 j の幅 + G）。点 (gx, gy) は (Lᵢ + gx·u, (gy − 3)·u)。
* 板: 閉じた線 (−hw, −hh)(hw, −hh)(hw, hh)(−hw, hh)。hw = TW/2 + PX、hh = 3u + PY。線 `#ffffff`・太さ 6、塗りは表の板の色。
* 数字: 点 (gx, gy) は ((gx − 2)·u, (gy − 3)·u)（x −18〜18、y −27〜27。縁を含めて x −26.5〜26.5、y −35.5〜35.5 で、枠 56×76 の中に入る）。
* 座標は小数第3位に丸める（`Math.round(v * 1000) / 1000`。`-0` は `0`）。
* 結果の大きさ（`bounds`。エディタの定義＝点の外接矩形を、線のある要素だけ線の太さの半分ずつ広げた和）: `logo_ready.js` x ±163・y ±53、`logo_battle.js` x ±202・y ±53（TW = 6×40 + 10 + 6×14 = 334）、`logo_phase.js`・`logo_stage.js`・`logo_name_giant.js` x ±117・y ±38（TW = 180）、`logo_name_goblins.js` x ±155・y ±38（TW = 256）、`logo_name_dragon.js` x ±136・y ±38（TW = 218）。数字は字の形によって違う（例 `digit_0.js` x ±26.5・y ±35.5）。スクリプトで要素から求める。

**図形の並び**（描く順＝`elements` の順＝`source.shapes` の順。`id` は `shape-1` から順の連番）:
* ロゴ: `shape-1` = 板 → 全部の字の縁の線（字の順・字の中の線の順）→ 全部の字の芯の線（同じ順）。
* 数字: 縁の線（線の順）→ 芯の線（同じ順）。
* 縁・芯の線は塗りなし（閉じた線も `fillColor: null`）。

* `export function drawDigits(ctx, value, cx, cy, scale)`: `value` が 0 以上の整数でなければ、または `scale <= 0` なら何もしない（エラーにしない）。`String(value)` の各桁を、幅 `DIGIT_CELL.w * scale` の間隔で左から並べ、並べた全体の中心を `cx` に、各桁の中心の y を `cy` にそろえる（i 桁目の中心 x = cx − 全体の幅/2 + (i + 0.5) × 間隔）。1桁ごとに `save`／`restore` で囲む。

**流れ**（`BoardFlow.update` が毎ティック、上から1つだけ判断する）:
1. BATTLE! が終わった（`banner.isBattleCallOver()`）→ BATTLE! を消して `true` を返す → `BoardScene` が `startBattle()`（攻防の前の値の写し → 待っている兵の数 → `resolveBattle()` → 放つ演出の作り直し → `BattleShowScene` を積む。今と同じ。行動終了の音は鳴らさない）。
2. 合図が出ている（`!banner.isIdle()`）→ 何もしない。
3. ステージを始めた敵の番号（`stageEnemyIndex`）が `game.enemyIndex` と違う → スタートの待ち（`stageWaitMs`）が残っていれば待つ。0 なら `stageEnemyIndex = game.enemyIndex`、`playStageBgm(game.enemy.typeId)`、`banner.showStage()`（ステージの曲と演出を同じ時刻に始める）。
4. 始まりを出したフェーズの番号（`introPhase`）が `game.phase` と違う → `introPhase = game.phase`、`banner.showPhase()`。
5. 段取りが止まっていて（札・玉・兵が全部止まった。今の自動の攻防の条件と同じ）`game.canResolveBattle()` → `banner.showReady()`、`playReadySe()`。
* ステージの始まりが終わると `banner` が空になり、同じ `update` の中で 4. に進むので、ステージの始まりの直後に続けてフェーズの始まりが出る（ゲームの最初・敵を倒した後）。攻防の後に自動で次のフェーズへ進んだときは、3. は当たらず 4. だけ。
* ゲームの最初は、`stageEnemyIndex` が `null` なので 3. でスタートの待ち（`BGM_TIMING.startToStageMs`）の間は待つ。

**タップ**（`BoardFlow.tap(game)`。`BoardScene.onPointer` の `'down'` の頭で呼ぶ。`false` なら選択を外して戻る。※実装では、`'down'` の判定と、札が動いている間の無視の判定（`animator.isBusy()`・`releaseShow.isHoldingCards()`）の後で呼んだ。準備終了は盤面が全部止まってから出るので、動作の結果は同じで、動いている間のタップで BATTLE! が始まらない側に倒した）:

* 「始まりの待ち」も見るのは、`BattleShowScene` が外れた直後のフレームでは `BoardScene.update` より先に入力が届くことがあり（エンジン 8章・19章）、その間に盤面を触れないようにするため。

### 合図の管理（`js/anim/bannerShow.js`。新規）
* `export function sampleBannerLook(kind, clock, out)`（純粋。`out` に書く。`BannerLook` = `{ kind, scale, alpha, dim }`。`kind` は `'ready'|'battle'|'stage'|'phase'|null`）:
    * `null`: `scale 1`・`alpha 0`・`dim 0`。
    * `'ready'`: t = clamp01(clock / readyPopMs)。`scale = easeOutBack(t)`、`alpha = 1`、`dim = t`。
    * `'battle'`: tp = clamp01(clock / battlePopMs)、tf = clamp01((clock − (battleMs − battleFadeMs)) / battleFadeMs)。`scale = easeOutBack(tp) × lerp(1, battleFadeScale, tf)`、`alpha = 1 − tf`、`dim = 0`。
    * `'phase'`・`'stage'`: 長さ d（`phaseMs`／`stageMs`）。ti = clamp01(clock / introFadeInMs)、to = clamp01((clock − (d − introFadeOutMs)) / introFadeOutMs)。`scale = lerp(introScaleFrom, 1, easeOutCubic(ti))`、`alpha = ti × (1 − to)`、`dim = 0`。
* `export class BannerShow`:
    * `constructor(enterDistance)`: `kind = null`・`clock = 0`・`enterDistance`（敵の入りの始めの右へのずれ px。配置から）・見た目の入れ物 `lookBox`（`sampleBannerLook` で書く）。
    * `showReady()`・`showBattle()`・`showStage()`・`showPhase()`: 種類を替えて時計を 0 にし、見た目を書く（中で共通の `begin(kind)`）。`clear()`: 種類を `null`、時計 0、見た目を書く。
    * `update(ms)`: 種類が `null` なら何もしない。時計に足し、`'stage'`・`'phase'` は長さに達したら `null` にする（`'ready'` は出したまま、`'battle'` は呼ぶ側が `clear()` するまで残す）。最後に見た目を書く。
    * `isIdle()`: 種類が `null`。`isWaitingTap()`: `'ready'` で時計 ≥ `readyPopMs`（出きった）。`isBattleCallOver()`: `'battle'` で時計 ≥ `battleMs`。
    * `enemyOffset()`: `'stage'` なら `enemyEntranceOffset(clock, enterDistance)`、ほかは 0。
    * `look()`: 見た目の入れ物を返す（読むだけ）。
* 描画せず、ゲームの状態・ルール層・`Sound` に触れない。

### 参照する責務
*   **憲法（`PROJECT_CONSTITUTION.md` 3章）からの要点**: ルール層は画面・エンジンを import せず、画面の側はルール層の状態を読むことと公開された操作を呼ぶことでだけ状態を変える。ルールの判定や計算を画面の側に書き写さない。演出はルール層が出した結果を見せるだけで、途中で結果を変えない。ルールの数値は `js/rules/config.js` 1か所（遊び方の文章は今の値を文字で書く決まり）。`update` の中で描画しない、`draw` の中で状態を変えない。経過時間は `update(dt)` の `dt` と `draw` の `time` だけ。`ctx` の状態の変更は `save`／`restore` で囲む。`window` にプロパティを足さない。すべてのソースファイルの先頭に3行以内の責務の JSDoc を書き、その責務を外れる処理を足さない。関数・クラス・データ構造には JSDoc を書く。エンジンは `import { … } from 'oz'` だけで使う。`js/` に `requestAnimationFrame`・`addEventListener`・`getContext`（REQ により `setTimeout`・`setInterval`・`performance.now()`・`Date.now()` も）を書かない。シーンの切り替えは `Engine.pushScene`・`popScene`・`changeScene` だけ。スプライトJSは、REQ で明示されたときだけ手で書いてよい（今回は REQ で明示。既定の export で `draw(ctx)` を持つ形）。

## 5. 懸念事項・要確認ポイント
1. **同じ音のファイルを2つの名前で読み込むこと**: `oz/ENGINE_API.md` 20章には、同じパスを別の名前で読むことを禁じる記述はなく、名前ごとに別々に管理されるので、`ready`・`battleStart` の両方を `turnEnd.wav` に向ける。ただし「読める」とはっきり書かれてはいない。読み込みに失敗した場合はコンソールに `[oz] Assets.load:` の警告が出て音が鳴らないだけ（エラーで止まらない）なので、テストプレイで準備終了と BATTLE! の両方で音が鳴ることを確かめてほしい。鳴らなければ、エンジンへの連絡票（憲法3章「エンジンの不足への対応」）か、仮の音のファイルを2つに分けること（今回は新しい音のファイルを作らない決まりなので、別の REQ）が必要になる。
2. **`tools/makeSounds.mjs` の説明との食い違い**: `makeSounds.mjs` の説明は「名前は `SOUND_FILES` の WAV の名前とそろえる」で、`turnEnd`（`turnEnd.wav`）を合成し続ける。今回 `SOUND_FILES` から `turnEnd` の名前を消すが、ファイル `turnEnd.wav` は `ready`・`battleStart` が使うので、合成し直しても動きは変わらない。`tools/` は変えてよい範囲に入らないので変えない。発注者が別の音に差し替えるときに、あわせて整理してほしい。
3. **攻防の始まりが BATTLE! の分だけ遅れる**: `resolveBattle` と攻防の演出のシーンを積むのは BATTLE! が消えた後（約 700ms 後）。その間は盤面を触れず放つ演出も止まっているので、写しと待っていた兵の数は今と同じ値になり、HP・人数の表示も先に変わらない。
4. **`BattleShowScene` が外れた直後の1フレーム**: エンジンの決まりで、`popScene` のあったフレームでは `BoardScene.update` が回らずに `draw` され、次のフレームでは `update` より先に入力が届く。このため「始まりの待ち」（ステージ・フェーズの始まりをまだ出していない）の間も盤面のタップを無視し、入れ替わった新しい敵は描かない（`BoardFlow.tap`・`entranceLook`）。この1フレームは合図なしの盤面が見える（16ms 程度）。ちらつきが気になるなら試遊で知らせてほしい。
5. **仮のロゴの見え方**: 字は直線だけの線で、`draw` の継ぎ目が `miter` に固定されるため、鋭い角を作らない形（N の上下に短い横線など）にしてある。色・太さ・大きさ（スマホの縦画面でロゴの字の高さは 準備終了・BATTLE! が約 60px、PHASE・STAGE・名前が約 42px、数字が約 54px（論理解像度））は目視で確かめてほしい。準備終了は画面の中央に等倍で出す（拡大の倍率をかけない）。大きくしたいときは、エディタで描き直すときに大きく描けば、ゲーム側のコードを変えずに大きくなる（約束の目安の中で）。
6. **準備終了の暗幕**: 準備終了が出ている間、画面全体を黒の 35% で暗くする（計画で決めた）。BATTLE! とフェーズ・ステージの始まりでは暗くしない。
7. **フェーズの始まりの予告の文字**: 今の予告の枠と同じ `enemyActionText` の文字（「攻撃 4」「吸い込む」「ブレス 11」など。「次の行動」の見出しは付けない）を白の縁取りで出す（ブレスも同じ色）。数え下ろしが 0 のフェーズは、今の数え下ろしの枠と同じ「攻撃！」になる。
8. **手で書いたスプライトとエディタの往復**: 手で書いたファイルもエディタの書き出しと同じ形にし、タスク1でエディタの取り出しを模して確かめる。実際に OZ Vector Editor の「開く」で開けるかは、テストプレイで確かめてほしい。
9. **遊び方の文章の量**: 1ページの行数を見積もりで収めている（1行 18 字）。8 ページ目「敵と予告」が見積もりで 17 行ともっとも多く余裕が最小なので、特に実機で確かめてほしい。実際の折り返しはテストプレイで確かめてほしい。
10. **敵の入りの距離**: 入りの始めのずれは戦闘の段の幅（720）にした。どの敵も始めは画面の右の外にいて、`easeOutCubic` のため、時間の前半の終わり頃に右端から見え始め、減速して止まる。入ってくる速さは試遊で `enemyEnterMs` を決め直してほしい。

### テストプレイで確かめること（発注者が見る点）
*   ゲームを始めると、スタートの音の後、ステージの曲と同時に、ゴブリンの軍勢が右の画面の外から入ってきて、「STAGE 1」とゴブリンの軍勢の名前のロゴ（仮は英字 GOBLINS）が出る。続けて「PHASE 1」と敵の次の行動が出る。これが終わるまで盤面は触れず、終わった後に操作できる。スタートの音の間（ステージの始まりの前）は敵が描かれず、盤面も触れない。
*   行動を使い切ると、札・玉・兵が全部着いた後に「準備終了」のロゴ（仮は英字 READY）がぽんと出て、音が鳴り、画面が少し暗くなる。出ている間は盤面を操作できず、画面のどこかをタップすると「BATTLE!」が出て音が鳴り、その後に攻防の演出が始まる。BATTLE! の間のタップでは何も起きない。
*   攻防の結果・HP の減り方・音のきっかけは、今と同じ。BATTLE! の前に HP や人数が先に変わらない。攻防に入る瞬間の「行動終了」の音は鳴らない（準備終了と BATTLE! の音だけ）。
*   攻防の後に次のフェーズへ進むと、「PHASE N」と敵の次の行動が出て、終わるまで盤面は触れない。巨人のときは「攻撃まで あとN」も出る。
*   途中の敵を倒すと「○○を倒した！」「タップで次へ」だけが出る（「次は○○」は出ない）。タップすると次の敵の曲が流れ始め、次の敵が入ってきて「STAGE 2」と名前のロゴ（仮は GIANT）が出て、続けて「PHASE N」が出る。ドラゴンでは「STAGE 3」と DRAGON、ドラゴンの曲。
*   17 個のロゴ・数字のスプライト（`assets/sprites/logo_*.js`・`digit_*.js`）を、OZ Vector Editor の「開く」で開いて編集できる。原点を中心に、板と字（数字は字だけ）が見える。
*   （任意）エディタでロゴを描き直して同じ名前で書き出し、差し替えて再読み込みすると、ゲームのロゴに反映される（ゲーム側のコードの変更なし）。
*   遊び方の文章が、新しい画面（最上部の HP・金貨のゲージ、行動のゲージ）と流れ（準備終了 → タップで攻防）に合っている。「行動終了」「早送り・スキップ」の記述がない。8ページで、どのページも本文が画面に収まる。
*   スマホの縦画面と PC で、タイトルからクリア・負けまで通しで遊べる。
