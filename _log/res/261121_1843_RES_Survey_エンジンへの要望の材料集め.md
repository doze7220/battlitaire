#### 2-3 観点ごとの今のエンジン（OZ Engine のリポジトリの `oz/ENGINE_API.md`）

**(1) キャンバスキャッシュの使い方（25章）**
* 作り方: `CanvasCache.create(source, { bounds, scale })`。`source` は関数（`source(ctx)`）か `draw(ctx)` を持つもの（スプライトJS・図形・文字）。`bounds` は `{minX,minY,maxX,maxY}`（必須。スプライトJS なら `sprite.bounds` をそのまま渡せる）。`scale` は既定 1。作ってすぐ焼く。
* 描き方: 戻り値（焼き付け）の `draw(ctx)` を、`translate`・`rotate`・`scale` を掛けてから呼ぶ。スプライトJS と同じ書き方。`scale` を呼ぶ側で掛けない。
* 焼き直し: ウィンドウの大きさ・画面の向きが変わると、次に描くときに自動で焼き直す。色や演出を変えたら `refresh()` を手で呼ぶ。
* 捨て方: `dispose()`（シーンの `destroy` で呼ぶ。2回目以降は何もしない。捨てた後の `draw`・`refresh` はエラー）。
* 作れる時期: `Engine.start` の後。シーンの `init` で作り、`destroy` で捨てる。
* 注意: 作れない時期や引数の誤りはエラー（`[oz] CanvasCache.create:` …）／`scale` と違う倍率で描くとぼやける／`bounds` の外は切れる（`miter` の角など）／アニメーションは対象にならない／色違いは色ごとに別の描く処理を渡して別に焼く／文字は Web フォントの読み込み後に焼く／1つにつき画像1枚分のメモリ（iPhone の Safari には上限がある）／`options` の知らない項目は読まない（エラーにもならない。`COWORK_STATUS.md` 3 章にも持ち越しとして記載）。
* できないこと・書かれていないこと: 画素を加工して色を差し替える（`MILESTONE` の「様子を見て判断する項目」で見送り）／複数の絵を1枚にまとめる（スプライトシート。同じく見送り）／`bounds`・`scale` を後から変えること（できない）／原点を別に指定すること（`source` の座標の原点そのまま。`bounds` だけで範囲を決める）／焼き付けた画像の大きさを知ること（解像度は利用側に公開しない）。

**(2) 実行中の入り切り**
* エンジンに入り切りの口は**ない**（25章に無し。`COWORK_STATUS_CLOSED.md` 102 行で、Phase 04 の見比べ用の切り替えは土台から消されたとある）。
* 焼き付けと元のスプライトを描き分ければ同じことができるか: 資料の記述から言えるのは、焼き付けは「スプライトJSと同じ書き方（位置と角度を付けて `draw(ctx)` を呼ぶ）」で描ける（25章冒頭）こと、`source` を別に持てば元のスプライトも同じ `draw(ctx)` で描けること。したがって、ゲーム側が `use ? 焼き付け.draw(ctx) : スプライト.draw(ctx)` と描き分けることは、資料の範囲では可能に見える（推測）。ただし次の点は資料に書かれていない: 切り替えの間も焼き付けを持ち続けるときのメモリ、OFF の間に焼き直しが走るか（「次にその焼き付けを描くときに焼き直す」ので、OFF の間は描かないため焼き直されない、と読める）、ON に戻したときの最初の1回の遅さ。また、焼き付けを作るのは `init`（`Engine.start` の後）に限る。
* 憲法上は、描き分けは `js/` の描画の側に書く話で、エンジンの不足とは言い切れない。ただし「描画の重さを比べる」目的では、直描き・焼き付けの切り替えをエンジンの標準の形として持つほうが、焼き付けの有無が `CanvasCache` の中の自動の焼き直しを含めて公平に比べられる（これは推測）。

**(3) FPS の出し入れ**
* できない。14章「`debug: true` で起動すると、左上に FPS が最前面で表示される。実行中には切り替えられない」。

**(5) ドラッグ・スクロールに使えるポインタ入力（16章）**
* `onPointer({type, x, y})` に `'down'`・`'move'`・`'up'` が届く。押したまま動かすことも、離すこともできる。押さずにマウスを動かしても `'move'` が届く（スマホのタッチには無い）。連続した `'move'` は1フレームに1つにまとめられることがある。
* 押したまま canvas の外へ出ても `'up'` が届く（座標は範囲外の値になることがある）。押下の中断も `'up'` で届く。
* 複数の指: `onPointer` は単一ポインタ。パッドの外で2本以上押しているときは、ほかに押しているポインタが無いときに押し始めた1本だけが、離すまで届く。バーチャルパッドを有効にした場合は指ごとに受け取るが、`onPointer` にはパッドが処理しなかった指だけが届く。複数の指でスライダー2本を同時に動かすような使い方は、資料の範囲では書かれていない。
* ボタンの `onPress` が反応した押下は、離すまでの `'move'`・`'up'` も含めて `onPointer` に届かない（18章）。スライダーやタブの上にボタンを敷く場合は、この点に注意が要る。
* タッチのスクロール・拡大の抑止（`touch-action: none` など）、長押しメニューの停止はエンジンがやる。
* 書かれていないこと: 押下の最初の位置を覚えておく部品、タップとドラッグの区別（距離の閾値）、慣性スクロール。どれもゲーム側が `onPointer` の値から書くことになる。

* **要望の内容**: 実行中に、焼き付けで描く場合と、元のスプライトを直接描く場合を切り替えて、同じ場面の重さを比べられる。調整パネルのチェックボックス1つで切り替える。

## 6. 懸念事項・今後の修正における注意点
* **PHASEOUT は参考として限られる**: 窓・タブ・スイッチ・ボタンの形は参考になるが、スライダー・ドラッグ・スクロール・ホバー・押下の見た目・差し替えできる見た目はなく、バトリティアが欲しい部品の半分ほどは新規に設計することになる。「選択肢のボタンの列」「スイッチ」はゲームの設定の値と直接つながっており、ルール層と画面を分けるバトリティアの憲法にはそのまま使えない。
* **リリースでの消し方**: PHASEOUT の `ENABLE_DEBUG_OVERLAY` は、タイトルの DEBUG START ボタンしか消さない。バトリティアで「1つの定数で全部消える」を実現するには、調整パネルを開く入口、パネルのシーン、FPS の表示（`debug`）の全部を同じ定数から条件づけ、読み込みだけされるファイルが残らないように、動的 `import` の可否も含めて決める必要がある（動的 `import` は `from 'oz'` の規則とは別の話で、この Survey では確かめていない）。
* **窓を開いている間の入力**: エンジンでは、`pushScene` で積んだ窓のシーンが最前面になり、背面のシーンの入力・ボタンは反応しない（6・18章）。PHASEOUT のように、窓の外を押したら閉じる動きや、背面の画面を止める動きは、窓のシーン側に書く。ただし、窓を積んだ直後の同じフレームの残りの入力は新しいシーンに届く（8章）。
* **ボタンと `onPointer` の関係（18章）**: ボタンに反応した押下は、離すまで `onPointer` に届かない。調整パネルにスライダー（`onPointer` でドラッグ）とボタン（`addButton`）を混ぜる場合は、重ならない配置にするか、ボタンを使わず `onPointer` で判定する。
* **時間の扱い**: PHASEOUT の FPS 計算は `performance.now()` を使うが、バトリティアは憲法で禁止（`dt`・`time` だけ）。参考にするときはそのまま移せない。
* **載せ替えの手順**: `oz/` の置き換えは発注者が行い、`oz/FINGERPRINTS.txt` の差が4つ（`ENGINE_API.md`・`index.js`・`Engine.js`・`CanvasCache.js`）であることが、載せ替えの後の `OK` の確認の目安になる。`Engine.js` の内部が変わっているので、載せ替え後は起動と遊びの確認（ボタン・バーチャルパッド・音）を通しで行う。
* **調べていないこと**: スマホの実機での PHASEOUT のデバッグ画面の操作感、PHASEOUT の `DebugWindowModeChange` の指示書が実装済みかどうか、`PROJECT_ARCHITECTURE.md`（バトリティア）の記載、エンジンの内部（`oz/src/`）。
